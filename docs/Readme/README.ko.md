## 제품 소개

### 인증서 만료로 비즈니스가 멈추지 않도록

수백 대의 서버, 수십 종의 애플리케이션 유형, 서로 다른 네트워크 환경—인증서 만료가 다가올 때 어떻게 대응하십니까? 수동 갱신은 시간이 오래 걸리고 오류가 발생하기 쉬우며, 프로덕션 시스템을 다운시킬 수도 있습니다. TLSFlow는 인증서를 통합 관리하고 배포를 자동화하며, 문제가 발생하면 자동으로 롤백하여 인증서 갱신이 시한폭탄이 되지 않도록 도와줍니다.

플러그인 시스템과 워크플로우 오케스트레이션을 통해 다양한 웹 서버, 애플리케이션 서버, 로드밸런서, 게이트웨이 장비, 클라우드 플랫폼, 컨테이너 환경을 확장 가능하게 지원합니다.

| **갱신 실패 시 자동 롤백** | 갱신 전 자동 백업, 갱신 후 자동 검증을 수행하며 문제 발견 시 즉시 원래 설정으로 되돌려 비즈니스 중단 위험을 낮춥니다. |

## 페인 포인트와 과제

### 47일 인증서 시대가 다가온다

CA/B Forum은 2025년 4월 11일 SC081v3를 통과시켜, 공인 신뢰 TLS/SSL 인증서의 최대 유효기간을 단계적으로 다음과 같이 단축합니다：

| 단계 | 최대 유효기간 | 시행일 | 예상 연간 갱신 횟수 |
| --- | ---: | --- | ---: |
| 현재 | 1년 | 현재 | 약 1회 |
| 1단계 | 200일 | 2026-03-15 | 약 2회 |
| 2단계 | 100일 | 2027-03-15 | 약 4회 |
| 3단계 | 47일 | 2029-03-15 | 약 8회 |

갱신 빈도가 배로 늘어난다는 것은 신청, 배포, 검증, 롤백이 재현 가능한 자동화 프로세스로 정립되어야 한다는 의미입니다.

### 운영 지원 담당자: 조직 내부에 관리해야 할 인증서가 몇 개나 됩니까?

- 퍼블릭 도메인이 여러 클라우드 사업자에 분산되어 있고, 사내 네트워크 게이트웨이는 각 지사에 흩어져 있습니다.
- 인증서 정보가 Excel, 이메일, 공유 폴더에 산재해 있어 수량, 만료일, 배포 위치를 집계하기 어렵습니다.
- 실사할 때마다 임시로 취합해야 하므로 누락, 중복, 책임 불명확이 발생하기 쉽습니다.

**TLSFlow 솔루션**：인증서 자산 센터를 제공하여 모든 인증서와 그 배포 위치를 통합 관리합니다.

### 애플리케이션 구축 담당자: 다가오는 47일 인증서 시대에 어떻게 대응해야 합니까?

- 현재 인증서는 보통 연 1회 갱신하며, 애플리케이션 200개를 건당 2시간으로 계산하면 한 번의 라운드에 약 400시간이 필요합니다.
- 유효기간이 47일로 단축되면 연간 약 8회 갱신이 필요해져 반복되는 인건비가 그만큼 커집니다.
- 통합된 자동화 프로세스가 없으면 신청, 업로드, 설정, 재시작, 검증을 지속적으로 완수하기 어렵습니다.

**TLSFlow 솔루션**：배포 프로세스를 자동화하여 한 번의 갱신 소요 시간을 시간 단위에서 분 단위로 단축합니다.

### 애플리케이션 유지보수 담당자: 인증서 만료 또는 설치 실패로 비즈니스 중단이 발생한 적이 있습니까?

- 인증서 만료는 웹사이트 접속 불가, 모바일 앱 API 실패, 파트너 API 중단을 유발할 수 있습니다.
- 수동 갱신은 단계가 많아 설정 오류와 지연된 검증이 문제를 프로덕션 환경으로 옮기기 쉽습니다.
- 신속히 대응하더라도 이미 몇 시간 동안 비즈니스가 중단되어 불만과 고객 신뢰 저하로 이어질 수 있습니다.
- 통일된 변경 기록과 복구 근거가 없어 문제 해결, 롤백, 사후 분석 모두 수작업 경험에만 의존하게 됩니다.

**TLSFlow 솔루션**：만료 경고, 배포 후 자동 검증, 실패 롤백 메커니즘을 제공합니다.

### 정보보안 담당자: 사내 네트워크에서 와일드카드 인증서가 광범위하게 사용될 때 어떤 보안 위험이 있습니까?

- 동일한 와일드카드 인증서와 개인 키가 수십, 심지어 수백 대의 사내 서버에 복제됩니다.
- 서버 중 하나라도 침해되거나 백업이 유출되거나 오작동이 발생하면 개인 키 유출로 이어질 수 있습니다.
- 배포 범위를 추적할 수 없어, 인증서를 폐기해야 할 경우 영향 평가와 전사적 조사가 어려워집니다.
- 개인 키 사용 경계와 실제 배포 대상이 명확하지 않아 감사, 순환, 컴플라이언스 책임 이행이 어렵습니다.

**TLSFlow 솔루션**：내부 프라이빗 인증서와 퍼블릭 와일드카드 인증서를 자동화 배포와 결합할 것을 권장하여 개인 키 유출 위험을 낮춥니다.

### 팀 관리자: 우리 팀은 47일 인증서 시대까지 얼마나 준비되어 있습니까?

- 먼저 자산 목록이 완전한지, 인증서, 서버, 애플리케이션, 담당자가 서로 매핑되는지 확인합니다.
- 다음으로 자동화 커버리지를 평가하여 개인 경험, 임시 스크립트, 수동 로그인에 대한 의존도를 줄입니다.
- 마지막으로 팀이 신속한 대응, 승인 추적, 실패 롤백 역량을 갖추고 있는지 검증합니다.
- 만료 알림, 배포 검증, 실행 기록을 통합된 클로즈드 루프에 편입해야 47일 주기에 지속적으로 대응할 수 있습니다.

**TLSFlow 솔루션**：자산 실사부터 자동 배포, 모니터링 경고에 이르는 완전한 솔루션을 제공합니다.

## 기능 소개

### TLSFlow가 할 수 있는 것

| 기능 | 설명 |
| --- | --- |
| **인증서 자산 통합 관리** | 인증서 자산, 버전, 형식 변환, 신뢰 체인 검증을 통합 관리합니다. PEM/PFX/JKS/P7B 등 다양한 형식을 지원하며 인증서 만료를 자동 감지하고 이전 버전을 아카이빙합니다. |
| **다중 소스 인증서 연동** | 수동 가져오기, 내부 CA(OpenSSL/ACME), 클라우드 사업자 인증서(Alibaba Cloud CDN), Microsoft AD CS 등 다양한 인증서 소스를 지원하며 인증서 체인을 자동 분석하여 관리 대상 자산에 매핑합니다. |
| **이질적 환경 애플리케이션 탐지** | Agent를 통해 각종 웹 서버, 애플리케이션 서버, 로드밸런서 등의 애플리케이션 자산을 자동으로 탐지하고 현재 인증서 바인딩과 호환성을 식별합니다. |
| **워크플로우 자동화 배포** | DSL 기반으로 인증서 배포 워크플로우를 오케스트레이션합니다. SSH 원격 실행, CURL API 호출, 파일 전송을 지원하며 사전 점검, 백업, 검증, 롤백 보장 기능이 내장되어 있습니다. |
| **확장 가능한 플러그인 시스템** | 웹 서버, 애플리케이션 미들웨어, 로드밸런서, 게이트웨이 장비, 클라우드 플랫폼 등을 포괄하는 20개의 고빈도 애플리케이션 플러그인이 내장되어 있으며, 사용자 정의 플러그인 확장을 지원하여 어떤 대상 환경에도 적응할 수 있습니다. |
| **지속적인 모니터링과 경고** | 인증서 만료, 바인딩 드리프트, 체인 검증 실패, 배포 오류를 실시간 모니터링합니다. 이메일/Webhook/DingTalk/WeCom/Feishu/Slack/Telegram 등 다중 채널로 경고를 전송합니다. |
| **승인 워크플로우와 감사** | 위험 등급과 작업 유형(플러그인 설치/활성화, 워크플로우 실행, 롤백 작업)에 따라 승인을 트리거할 수 있으며, 작업 로그와 실행 스냅샷을 완전하게 기록합니다. |
| **세밀한 권한 제어** | RBAC + 객체 인가 모델을 기반으로 인증서 자산, 애플리케이션, Agent 차원에서 권한을 부여하며 테넌트 격리와 부서 간 협업을 지원합니다. |

### 실제 시나리오의 페인 포인트

| 겪을 수 있는 문제 | TLSFlow의 해결 방법 |
| --- | --- |
| 인증서 정보가 메일, Excel, 공유 드라이브에 흩어져 있어 필요할 때 찾을 수 없음 | 모든 인증서를 통합 관리하며 검색만으로 사용 위치와 담당자를 확인할 수 있습니다. |
| 갱신 후 적용되었는지 알 수 없고, 사용자 불만이 들어와야 설정 오류를 발견함 | 갱신 후 자동으로 HTTPS에 접속하여 지문이 올바른지 확인한 뒤 완료로 표시합니다. |
| 문제가 발생해도 누가 무엇을 변경했는지 알 수 없어 추적이 불가능함 | 매 갱신마다 작업자, 시각, 변경 내용을 기록하여 언제든 조회할 수 있습니다. |
| 프로덕션 구역이 외부 네트워크 접근을 차단하여 Agent를 설치할 수 없고 수동 로그인만 가능함 | Gateway를 통해 능동 연결하거나 SSH로 직접 프록시 없이 배포할 수 있습니다. |

## 제품 강점

### TLSFlow가 기업에 더 적합한 이유

- **레거시 시스템도 관리 가능**：많은 시스템이 Agent를 설치할 수 없고 네트워크에는 격리 구역이 존재합니다. TLSFlow는 다양한 연동 방식을 제공하여 레거시 시스템과 격리된 네트워크를 대규모 개조 없이도 관리 범위에 포함시킬 수 있습니다.
- **인증서 갱신 실패 시 자동 롤백**：갱신 전 자동 백업을 수행하고, 검증 실패 시 백업 목록과 체크포인트를 기반으로 원래 설정을 자동 복원합니다. 실패 정책의 자동 트리거와 수동 롤백 방식을 모두 지원하여 비즈니스가 중단된 뒤 허둥지둥 롤백하는 상황을 방지합니다.
- **일반적인 애플리케이션과 특수한 애플리케이션 모두 관리 가능**：고빈도 애플리케이션은 내장 플러그인으로 바로 사용하고, 특수 장비나 특별한 프로세스는 워크플로우 DSL로 갱신 절차를 직접 오케스트레이션하여 무한히 확장할 수 있습니다.
- **인증서 연관 관계를 한눈에 확인**：각 인증서가 특정 서버, 사이트, 애플리케이션에 바인딩되어 있어 문제가 발생하면 영향 범위를 빠르게 파악할 수 있습니다.
- **완전한 권한 제어**：역할별로 서로 다른 권한을 가지며 민감한 작업은 정책에 따라 승인이 필요합니다. 비밀번호와 개인 키는 로그에 평문으로 표시되지 않습니다.
- **완비된 감사 로그**：매 갱신마다 실행 단계, 사용된 인증서, 설정 변경 내역을 확인할 수 있어 문제가 생겼을 때 되짚어볼 수 있으며 블랙박스식 작업이 아닙니다.

## 적용 시나리오

- **복잡한 이질적 환경**：여러 종류의 웹 서버, 애플리케이션 미들웨어, 로드밸런서, 게이트웨이 장비, 클라우드 플랫폼이 공존하여 수동 유지보수로는 지속하기 어려운 경우.
- **격리 구역과 레거시 시스템이 존재하는 경우**：프로덕션 구역에는 소프트웨어를 임의로 설치할 수 없고 레거시 시스템도 업그레이드할 수 없지만 인증서는 여전히 갱신이 필요한 경우.
- **완전히 단절된 사내 네트워크**：프로덕션 환경이 인터넷과 물리적으로 격리되어 있어 퍼블릭 클라우드 온라인 인증서 서비스를 사용할 수 없는 경우.
- **승인과 기록이 필요한 경우**：인증서 변경은 민감한 작업이므로 승인 워크플로우, 작업 추적, 완전한 이력 관리가 필요한 경우.

인증서 갱신을 시한폭탄으로 남겨두지 마십시오. TLSFlow는 통합된 자산 관리, 자동 배포, 안전한 롤백, 지속적인 경고를 통해 점점 짧아지는 인증서 순환 주기에 팀이 대응할 수 있도록 돕습니다.

## 빠른 시작

### 사전 조건

- Linux, macOS 또는 NAS 호스트
- Docker CLI；표준 배포는 추가로 Docker Compose v2 필요
- 대상 장비 및 인증서 서비스에 접근 가능
- 프로덕션 환경에서는 무작위로 생성되어 장기간 변경되지 않는 런타임 키를 사용

사전 빌드된 이미지를 배포할 때는 Node.js, Go, Buildx, 소스 코드가 필요하지 않습니다.

### 단일 노드 배포

애플리케이션 자산 50개 이하의 소규모 환경에 적합하며, PGlite 내장 데이터베이스를 사용하고 단일 컨테이너로 실행됩니다.

빠른 시작(Docker 명명된 볼륨 사용)：

```bash
docker run -d \
  --name tlsflow-small \
  --restart unless-stopped \
  -p 8085:3003 \
  -e GCAC_PUBLIC_BASE_URL=http://your-host:8085 \
  -e GCAC_SECRET_KEK=your-random-kek \
  -v tlsflow-small-data:/app/data \
  tlsflow/gcac-small:latest
```

**중요**：
- 프로덕션 환경에서는 반드시 `GCAC_SECRET_KEK`를 무작위 키로 교체해야 합니다
- 관리자 비밀번호는 최초 접속 시 초기화 마법사를 통해 설정됩니다
- 기본 접속 주소：`http://<호스트 주소>:8085/`

상세한 파라미터 설정, 호스트 디렉터리 바인딩, HTTPS 리버스 프록시 등의 시나리오는 전체 문서를 참조하십시오.

### 표준 배포

정식 환경 및 멀티 테넌트 시나리오에 적합하며, PostgreSQL 16 데이터베이스를 사용하고 Browser Runtime 브라우저 세션을 지원합니다.

**1. 설정 파일 준비**

```bash
cp docker/.env.example docker/.env
```

`docker/.env`를 편집하여 최소한 다음 항목을 입력합니다：
- `GCAC_RELEASE_VERSION`：이미지 태그(프로덕션 환경에서는 고정 버전 사용)
- `GCAC_PUBLIC_BASE_URL`：Agent가 접근할 수 있는 웹 주소
- `POSTGRES_PASSWORD`：데이터베이스 비밀번호
- `GCAC_TOKEN_SECRET`：로그인 토큰 서명 키
- `GCAC_SECRET_KEK`：암호화 루트 키(장기간 변경되지 않아야 함)

**2. 서비스 시작**

```bash
cd docker
docker compose pull
docker compose up -d
```

**3. 검증**

```bash
docker compose ps
docker compose logs --tail=200 db backend web
```

`db` 상태가 `healthy`인지 확인하고 `http://<호스트 주소>:8085/`에 접속하여 초기화 마법사를 완료합니다.

**Browser Runtime**(선택 사항)：브라우저 로그인 자격 증명이 필요한 경우, `.env`에서 `BROWSER_RUNTIME_ENABLED=true`를 설정하고 `BROWSER_RUNTIME_SHARED_SECRET`을 입력한 뒤 `docker compose up -d`를 실행합니다.

상세한 리소스 설정, 데이터 디렉터리, 백업 및 복구 등에 대한 설명은 전체 문서를 참조하십시오.

## 2차 개발 및 확장

### 올바른 확장 방식 선택

1. **일반 시스템 또는 인증 환경 추가**：기존 Agent, SSH, CURL, 플랫폼 기능을 우선 재사용하고 호환성 카탈로그를 통해 설정과 검증 기록을 추가하여 핵심 코드 변경을 최소화합니다.
2. **고빈도 제품 추가**：장비 연결, 신원 확인, 읽기 전용 탐지, 애플리케이션 자산 매핑, 배포 계획, 대상 검증을 캡슐화한 제품 플러그인을 개발합니다.
3. **소수 장비 또는 내부 API 추가**：SSH, SFTP, SCP, CURL, 조건, 변환, 대기, 수동 확인, 추출, 어설션 등 통제된 단계를 사용하여 버전 관리되는 Workflow DSL을 작성합니다.
4. **새로운 실행 경계가 반드시 필요한 경우**：새로운 Agent 제품 라인이나 호스트 기능이 필요한지 평가한 뒤, 먼저 프로토콜, 권한, 감사, 롤백 계약을 완비합니다.

### 플러그인 개발 경계

- 플러그인은 `Manifest`를 통해 신원, 버전, 기능, 권한, 호환 범위를 선언합니다.
- 플러그인은 기본적으로 호스트가 제공하는 Host API, Secret, Artifact, 감사, 잠금, 실행 인가만을 사용합니다.
- 내장 플러그인은 `backend/src/modules/plugins/builtin-plugins/<pluginId>/`에 위치합니다.
- 사용자 플러그인은 `data/plugins/`에 배치되며 통합 플러그인 패키지 가져오기 인터페이스를 통해 게시됩니다.
- 플러그인 워크플로우 리소스는 플러그인 버전과 동기화되어야 하며, 게시 전 인증서 갱신 프로세스 테스트를 완료하고 반복 기록을 보관해야 합니다.
- 플러그인은 호스트를 우회하여 테넌트 데이터, 평문 자격 증명을 직접 읽거나 호스트 프로세스를 임의로 실행할 수 없습니다.

진입 문서：[플러그인 개발](../../docs/Documentation/developer/plugin-development.md), [호스트 플러그인 기능](../../docs/Documentation/developer/host-plugin-capabilities.md), [워크플로우 개발](../../docs/Documentation/developer/workflow-development.md).

### 워크플로우 DSL 경계

워크플로우 템플릿은 프로젝트 전용 프로토콜 `gcac.workflow/v1`을 사용합니다. 템플릿 소스는 다음만 허용됩니다：

- 내장 템플릿：`backend/src/modules/workflow-templates/builtin-workflows`
- 사용자 가져오기 템플릿：`data/workflows`(필요 시 런타임에 생성되며, 내장 템플릿 디렉터리가 아님)

비밀번호, 토큰, 개인 키, 인증서 산출물은 `SecretRef` 또는 Artifact Slot을 통해 참조해야 하며 DSL, 일반 변수, 로그, 실행 스냅샷에 기록해서는 안 됩니다. 배포 프로세스는 `prepare → backup → install → refresh → verify` 단계를 유지해야 하며, 롤백은 원본 워크플로우 버전과 입력 스냅샷을 사용합니다.

### 로컬 개발 및 검증

본 리포지토리는 개발 서비스를 README 배포의 일부로 자동 시작할 것을 요구하지 않습니다. 일반적인 빌드 및 테스트 진입점은 다음과 같습니다：

```bash

# 프론트엔드 타입 체크 및 프로덕션 빌드
```

백엔드 전체 테스트, 호환성 아키텍처 검사, 플러그인 버전 검사, Agent 빌드는 추가적인 환경 요구사항이 있으므로 해당 모듈 문서와 프로젝트 규범에 따라 실행하십시오. 테스트 통과가 실제 벤더 장비, 외부 CA, 격리 네트워크, 프로덕션 롤백 검수의 완료를 의미하지는 않습니다.

## 보안 및 프로덕션 경계

- `GCAC_SECRET_KEK`는 런타임 보안 자료의 복호화 루트 키이며 별도로 백업해야 하고, 코드, 로그, 공개 문서, 브라우저에 기록해서는 안 됩니다.
- 라이선스 발급 개인 키를 리포지토리, 이미지 또는 컨테이너 환경 변수에 넣지 마십시오；공개 배포에는 라이선스 신뢰 공개 키만 필요합니다.
- 표준판 Browser Runtime은 사내 네트워크와 웹 프록시를 통해서만 접근해야 합니다.
- 인증서, 개인 키, 토큰, PFX/JKS 비밀번호 등 민감한 자료는 일반 변수, 실행 로그, 워크플로우 템플릿에 포함되어서는 안 됩니다.
- 대상 버전, 권한 조건, 실행 채널 및 실제 호환성은 별도로 검수해야 합니다；정적 코드, 스키마, 유닛 테스트는 현장 검증을 대체할 수 없습니다.
- 표준 Compose 토폴로지는 단일 노드 운영을 대상으로 하며 자동 페일오버 클러스터링을 제공하지 않습니다；업그레이드 및 복구 전에는 데이터베이스, 워크플로우, 사용자 플러그인, 런타임 보안 자료를 백업해야 합니다.
- ACME, 외부 CA, 벤더 API, 복잡한 네트워크에 대한 기능은 버전에 따라 계속 진화하므로 최신 사용자 문서, 플러그인 호환성 카탈로그, 실제 환경 결과를 기준으로 하십시오.
