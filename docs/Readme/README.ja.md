## 製品紹介

### 証明書の期限切れが、ビジネスを止めてしまう前に

数百台のサーバー、数十種類のアプリケーション、異なるネットワーク環境——証明書の期限が迫っているのにどうする？手作業での更新は間に合わず、ミスも起こりやすく、本番環境をダウンさせる可能性もある。TLSFlowは証明書を一元管理し、自動デプロイし、問題発生時は自動ロールバック。証明書更新がもう時限爆弾にならない。

プラグインシステムとワークフロー編成により、各種Webサーバー、アプリケーションサーバー、ロードバランサー、ゲートウェイデバイス、クラウドプラットフォーム、コンテナ環境を拡張サポート。

### 製品価値

| 価値 | 説明 |
| --- | --- |
| **証明書の総数を把握** | Excelやメールを探す必要なし。すべての証明書がどのマシンにあり、どのアプリケーションにバインドされ、いつ期限切れになるか、一目瞭然。 |
| **一括自動更新** | Windows、Linux、クラウドプラットフォーム、ネットワークデバイスすべてに自動デプロイ。深夜にSSHで一台ずつ手作業で操作する必要なし。 |
| **更新失敗時の自動ロールバック** | 更新前に自動バックアップ、更新後に自動検証。問題発見時は即座に元の設定に戻し、ビジネス中断リスクを軽減。 |
| **期限切れ前の事前通知** | 期限が近づくと自動リマインダー、デプロイ失敗時は即座にアラート。WeChat、メール、DingTalkなど各種チャネルで通知受信。 |

## 課題とチャレンジ

### 47日間証明書時代の到来

CA/B Forumは2025年4月11日にSC081v3を承認し、公的信頼されるTLS/SSL証明書の最長有効期間を段階的に短縮：

| フェーズ | 最長有効期間 | 発効日 | 年間更新回数（推定） |
| --- | ---: | --- | ---: |
| 現在 | 1年 | 現在 | 約1回 |
| 第1フェーズ | 200日 | 2026-03-15 | 約2回 |
| 第2フェーズ | 100日 | 2027-03-15 | 約4回 |
| 第3フェーズ | 47日 | 2029-03-15 | 約8回 |

更新頻度が倍増すれば、申請、デプロイ、検証、ロールバックすべてが再現可能な自動化プロセスとして確立する必要がある。

### 運用サポート担当者：企業内で管理すべき証明書は何枚？

- パブリックドメインは複数のクラウドベンダーに分散、内部ネットワークゲートウェイは各支社に点在
- 証明書情報はExcel、メール、共有フォルダに散在し、数量、有効期限、デプロイ場所の把握が困難
- 棚卸しのたびに臨時で情報をかき集め、漏れ、重複、責任不明確が発生しがち

**TLSFlow解決策**：証明書資産センターを提供し、すべての証明書とそのデプロイ場所を統合管理。

### アプリケーション実装担当者：47日間証明書時代にどう対応？

- 現在の証明書は通常年1回更新。200アプリケーションで1回2時間なら、1ラウンド約400時間
- 有効期間が47日に短縮されると年間約8回更新が必要となり、重複する人的コストも同時に拡大
- 統一された自動化プロセスがなければ、申請、アップロード、設定、再起動、検証を継続的に完了することは困難

**TLSFlow解決策**：自動化デプロイプロセスにより、1回の更新時間を時間単位から分単位に短縮。

### アプリケーション保守担当者：証明書期限切れやインストール失敗で業務中断が起きたことは？

- 証明書期限切れはWebサイトアクセス不能、モバイルアプリAPI失敗、パートナーAPI中断を引き起こす可能性
- 手作業更新は工程が多く、設定ミスや検証遅延が本番環境に問題を持ち込みやすい
- 迅速に対処しても、業務はすでに数時間中断し、クレームや顧客からの疑念を招く
- 統一された変更記録と復旧根拠がなければ、トラブルシューティング、ロールバック、振り返りはすべて人的経験に依存

**TLSFlow解決策**：期限切れ事前警告、デプロイ後自動検証、失敗時ロールバック機構を提供。

### 情報セキュリティ担当者：ワイルドカード証明書が内部ネットワークで大量使用されている場合のセキュリティリスクは？

- 同一のワイルドカード証明書と秘密鍵が数十台、場合によっては数百台の内部ネットワークサーバーにコピーされている
- いずれか1台のサーバーが侵害されたり、バックアップが漏洩したり、誤操作があれば、秘密鍵が拡散する可能性
- デプロイ範囲が追跡不可能で、証明書を失効させる必要が生じた場合、影響評価と全ネットワーク調査が困難に
- 秘密鍵使用境界と実際のデプロイ主体が不明確で、監査、ローテーション、コンプライアンス責任の実施が困難

**TLSFlow解決策**：内部プライベート証明書、パブリックワイルドカード証明書、自動化デプロイの組み合わせを推奨し、秘密鍵拡散リスクを軽減。

### チーム管理者：チームは47日間証明書時代にどれだけ近づいている？

- まず資産リストが完全か確認。証明書、サーバー、アプリケーション、責任者が対応付けられているか
- 次に自動化カバレッジを評価。個人の経験、一時的なスクリプト、手動ログインへの依存を削減
- 最後にチームが迅速な対応、承認記録、失敗ロールバック能力を備えているか検証
- 期限リマインダー、デプロイ検証、実行記録を統一されたクローズドループに組み込んで初めて、47日周期に継続的に対応可能

**TLSFlow解決策**：資産棚卸し、自動デプロイ、監視アラートまでの完全なソリューションを提供。

| **多様な証明書ソース接続** | 手動インポート、内部CA（OpenSSL/ACME）、クラウドベンダー証明書（Alibaba Cloud CDN）、Microsoft AD CSなど多様な証明書ソースをサポート。証明書チェーンを自動解析し、管理対象資産にマッピング。 |
| **異種環境アプリケーション検出** | Agentを通じて各種Webサーバー、アプリケーションサーバー、ロードバランサーなどのアプリケーション資産を自動検出。現在の証明書バインディングと互換性を識別。 |
| **ワークフロー自動化デプロイ** | DSLベースで証明書デプロイワークフローを編成。SSHリモート実行、CURL API呼び出し、ファイル転送をサポート。事前チェック、バックアップ、検証、ロールバック保証を内蔵。 |
| **拡張可能プラグインシステム** | 20の高頻度アプリケーションプラグインを内蔵。Webサーバー、アプリケーションミドルウェア、ロードバランサー、ゲートウェイデバイス、クラウドプラットフォームなどのシナリオをカバー。ユーザーカスタムプラグイン拡張により任意のターゲット環境に対応。 |
| **継続的監視とアラート** | 証明書期限切れ、バインディングドリフト、チェーン検証失敗、デプロイ異常をリアルタイム監視。メール/Webhook/DingTalk/WeChat Work/Feishu/Slack/Telegram多チャネルでアラート配信。 |
| **承認フローと監査** | リスクレベルと操作タイプに応じて承認をトリガー（プラグインインストール/有効化、ワークフロー実行、ロールバック操作）。操作ログと実行スナップショットを完全記録。 |
| **きめ細かい権限管理** | RBAC + オブジェクト認可モデルに基づき、証明書資産、アプリケーション、Agent次元で権限を割り当て。テナント分離と部門横断コラボレーションをサポート。 |

### 実際のシナリオでの課題

| よくある問題 | TLSFlowの解決方法 |
| --- | --- |
| 証明書情報がメール、Excel、共有ディスクに散在し、急に見つからない | すべての証明書を集中管理、検索で使用場所と責任者をすぐに特定。 |
| 更新後に反映されているか不明、ユーザークレームで初めて設定ミスが発覚 | 更新後に自動でHTTPSアクセス、フィンガープリント正常確認で完了。 |
| 問題発生時に誰が何を変更したか不明、追跡不可能 | 毎回の更新で操作者、時刻、変更内容を記録、いつでも確認可能。 |
| 本番環境は外部ネットワークアクセス禁止、Agentインストール不可、手動ログインのみ | Gatewayで能動接続、またはSSH経由でプロキシ不要の直接デプロイ。 |

## 製品の優位性

### なぜ TLSFlow は企業に適しているのか

- **レガシーシステムも管理可能**：多くのシステムは Agent をインストールできず、ネットワークには分離ゾーンがあります。TLSFlow は複数の統合方法を提供し、レガシーシステムと分離ネットワークを大規模な改修なしで管理下に置くことができます。
- **証明書更新失敗時の自動ロールバック**：更新前の自動バックアップ、検証失敗時にバックアップリストとチェックポイントに基づいて元の構成を自動復元。失敗ポリシーの自動トリガーと手動ロールバックの両方をサポートし、ビジネス中断後に慌ててロールバックする事態を回避。
- **一般的および特殊なアプリケーションの両方を管理可能**：高頻度アプリケーションは組み込みプラグインで直接使用、ニッチデバイスと特殊プロセスはワークフロー DSL で更新手順を独自にオーケストレーションし、無限に拡張可能。
- **証明書の関連付けが一目瞭然**：各証明書を特定のサーバー、サイト、アプリケーションにバインドし、問題が発生したときに影響範囲を迅速に確認。
- **完全なアクセス制御**：異なる役割が異なる権限を持ち、機密操作はポリシーベースの承認が必要。パスワードと秘密鍵はログに平文で表示されません。
- **包括的な監査ログ**：各更新で実行手順、使用した証明書、構成変更を確認でき、問題が発生したときにレビュー可能—ブラックボックス操作ではありません。

## 適用シナリオ

- **複雑な異機種環境**：複数の Web サーバー、アプリケーションミドルウェア、ロードバランサー、ゲートウェイデバイス、クラウドプラットフォームが共存し、手動保守が持続不可能;
- **分離ゾーンとレガシーシステムの存在**：本番ゾーンではソフトウェアのインストールが制限され、レガシーシステムもアップグレードできませんが、証明書は更新が必要;
- **完全にエアギャップされた内部ネットワーク**：本番環境がインターネットから物理的に隔離されており、パブリッククラウドオンライン証明書サービスを使用できない;
- **承認と記録の要件**：証明書の変更は機密操作であり、承認ワークフロー、操作トレーサビリティ、完全な監査証跡が必要。

証明書更新を時限爆弾にしないでください。TLSFlow は、統一されたアセット管理、自動デプロイ、安全なロールバック、継続的なアラートを使用して、チームがますます短くなる証明書ローテーションサイクルに対処できるよう支援します。

## クイックスタート

### 前提条件

- Linux、macOS、または NAS ホスト
- Docker CLI；標準デプロイには追加で Docker Compose v2 が必要
- ターゲットデバイスと証明書サービスへのアクセス
- 本番環境ではランダムで長期間変更しないランタイムキーを使用

事前ビルドされたイメージのデプロイには Node.js、Go、Buildx、ソースコードは不要です。

### シングルノードデプロイ

50以下のアプリケーションアセットの小規模環境に適しており、PGlite 組み込みデータベースを使用し、単一コンテナで動作します。

クイックスタート(Docker 名前付きボリュームを使用)：

```bash
docker run -d \
  --name tlsflow-small \
  --restart unless-stopped \
  -p 8085:3003 \
  -e GCAC_PUBLIC_BASE_URL=http://your-host:8085 \
  -e GCAC_SECRET_KEK=your-random-kek \
  -v tlsflow-small-data:/app/data \
  tlsflow/gcac-small:latest
```

**重要**：
- 本番環境では `GCAC_SECRET_KEK` をランダムキーに置き換える必要があります
- 管理者パスワードは初回アクセス時に初期化ウィザードで設定
- デフォルトアクセスアドレス：`http://<ホストアドレス>:8085/`

詳細なパラメータ構成、ホストディレクトリバインディング、HTTPS リバースプロキシなどのシナリオについては、完全なドキュメントを参照してください。

### 標準デプロイ

本番環境とマルチテナントシナリオに適しており、PostgreSQL 16 データベースを使用し、Browser Runtime ブラウザセッションをサポートします。

**1. 構成ファイルの準備**

```bash
cp docker/.env.example docker/.env
```

`docker/.env` を編集し、少なくとも以下を入力：
- `GCAC_RELEASE_VERSION`：イメージタグ(本番環境では固定バージョンを使用)
- `GCAC_PUBLIC_BASE_URL`：Agent がアクセス可能な Web アドレス
- `POSTGRES_PASSWORD`：データベースパスワード
- `GCAC_TOKEN_SECRET`：ログイントークン署名キー
- `GCAC_SECRET_KEK`：暗号化ルートキー(長期間変更しないこと)

**2. サービスの起動**

```bash
cd docker
docker compose pull
docker compose up -d
```

**3. 検証**

```bash
docker compose ps
docker compose logs --tail=200 db backend web
```

`db` のステータスが `healthy` であることを確認し、`http://<ホストアドレス>:8085/` にアクセスして初期化ウィザードを完了します。

**Browser Runtime**(オプション)：ブラウザログイン資格情報が必要な場合、`.env` で `BROWSER_RUNTIME_ENABLED=true` を設定し、`BROWSER_RUNTIME_SHARED_SECRET` を入力してから `docker compose up -d` を実行します。

詳細なリソース構成、データディレクトリ、バックアップと復元については、完全なドキュメントを参照してください。

## 二次開発と拡張

### 適切な拡張方法の選択

1. **通常のシステムまたは認証環境の追加**：既存の Agent、SSH、CURL、プラットフォーム機能を優先的に再利用し、互換性ディレクトリを通じて構成と検証レコードを追加し、コアコードの変更をゼロに近づけます。
2. **高頻度製品の追加**：デバイス接続、ID 確認、読み取り専用検出、アプリケーションアセットマッピング、デプロイ計画、ターゲット検証をカプセル化する製品プラグインを開発。
3. **ニッチデバイスまたは内部 API の追加**：SSH、SFTP、SCP、CURL、条件、変換、待機、手動確認、抽出、アサーションなどの制御されたステップを使用して、バージョン管理された Workflow DSL を作成。
4. **真に新しい実行境界が必要**：その後、新しい Agent プロダクトラインまたはホスト機能が必要かどうかを評価し、まずプロトコル、権限、監査、ロールバック契約を完成させます。

### プラグイン開発境界

- プラグインは `Manifest` を通じて ID、バージョン、機能、権限、互換性範囲を宣言;
- プラグインはデフォルトでホストが提供する Host API、Secret、Artifact、監査、ロック、実行認可のみを使用;
- 組み込みプラグインは `backend/src/modules/plugins/builtin-plugins/<pluginId>/` に配置;
- ユーザープラグインは `data/plugins/` に配置され、統一されたプラグインパッケージインポートインターフェースを通じて公開;
- プラグインワークフローリソースはプラグインバージョンと同期する必要があり、リリース前に証明書更新プロセステストを完了し、イテレーション記録を保存する必要があります;
- プラグインはホストをバイパスしてテナントデータ、平文資格情報を直接読み取ったり、ホストプロセスを任意に実行したりすることはできません。

エントリドキュメント：[プラグイン開発](../../docs/Documentation/developer/plugin-development.md)、[ホストプラグイン機能](../../docs/Documentation/developer/host-plugin-capabilities.md)、[ワークフロー開発](../../docs/Documentation/developer/workflow-development.md)。

### ワークフロー DSL 境界

ワークフローテンプレートはプロジェクト固有のプロトコル `gcac.workflow/v1` を使用します。テンプレートソースは以下のみ：

- 組み込みテンプレート：`backend/src/modules/workflow-templates/builtin-workflows`;
- ユーザーインポートテンプレート：`data/workflows`(必要に応じてランタイムで作成、組み込みテンプレートディレクトリではない)。

パスワード、トークン、秘密鍵、証明書アーティファクトは `SecretRef` または Artifact Slot を通じて参照する必要があり、DSL、通常の変数、ログ、実行スナップショットに書き込むことはできません。デプロイプロセスは `prepare → backup → install → refresh → verify` フェーズを維持し、ロールバックは元のワークフローバージョンと入力スナップショットを使用します。

### ローカル開発と検証

リポジトリは、開発サービスを README 配信の一部として自動的に起動することを要求しません。一般的なビルドとテストエントリポイント：

```bash
# バックエンドビルド
npm --prefix backend run build

# フロントエンドタイプチェックと本番ビルド
npm --prefix web run build

# Browser Runtime ビルド
npm --prefix browser-runtime run build

# TLS Inspector テスト
npm --prefix tls-inspector test

# フロントエンドユニットおよび契約テスト
npm --prefix web run test:unit
```

バックエンド完全テスト、互換性アーキテクチャチェック、プラグインバージョンチェック、Agent ビルドには追加の環境要件があります—対応するモジュールドキュメントとプロジェクト仕様に従ってください。テスト合格は、実際のベンダーデバイス、外部 CA、分離ネットワーク、または本番ロールバック受け入れの完了と同じではありません。

## セキュリティと本番境界

- `GCAC_SECRET_KEK` はランタイムセキュリティ資料の復号化ルートキーであり、独立してバックアップする必要があり、コード、ログ、公開ドキュメント、ブラウザへの書き込みは禁止;
- ライセンス署名秘密鍵をリポジトリ、イメージ、またはコンテナ環境変数に配置しないでください；公開デプロイにはライセンス信頼公開鍵のみが必要;
- 標準 Browser Runtime は内部ネットワークと Web プロキシを通じてのみアクセスする必要があります;
- 証明書、秘密鍵、トークン、PFX/JKS パスワードなどの機密資料は、通常の変数、実行ログ、ワークフローテンプレートに入れてはいけません;
- ターゲットバージョン、権限条件、実行チャネル、実際の互換性は個別に受け入れる必要があります；静的コード、Schema、ユニットテストは現場検証の代わりにはなりません;
- 標準 Compose トポロジはシングルノード運用向けであり、自動フェイルオーバークラスタリングを提供しません；アップグレードと復元の前にデータベース、ワークフロー、ユーザープラグイン、ランタイムセキュリティ資料をバックアップする必要があります;
- ACME、外部 CA、ベンダー API、複雑なネットワークの機能はバージョンとともに進化します—現在のユーザードキュメント、プラグイン互換性ディレクトリ、実際の環境結果を参照してください。

## プロジェクトの位置づけ

TLSFlow はすべての CA、Kubernetes コントローラー、軽量 ACME ツールを置き換えようとはしません。その価値は、「証明書発行後」最も制御不能になりやすい部分—アセット関係、異機種ターゲットデプロイ、事前チェック、検証、ロールバック、承認、監査、継続的な監視—を統一された、透明で、拡張可能な企業プロセスに変えることにあります。

**構造化アセットで「証明書がどこにあるか」に答え、プラグインとワークフローで「どうデプロイするか」に答え、事前チェックと検証で「デプロイが安全で効果的か」に答え、ロールバックと監査で「問題が発生したときにどう追跡し復元するか」に答えます。**
