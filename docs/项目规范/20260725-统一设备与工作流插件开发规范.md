# 统一设备与工作流插件开发规范

## 1. 文档目的

本文规定 GCAC 统一插件（Unified Plugin，统一插件）的分类、包结构、生命周期、设备管理能力、Workflow DSL（工作流领域专用语言）能力、Managed/Standalone 双模式、表单、展示、发现、证书产物、安全、可观测性和第三方目标归集规则。

本规范适用于内置插件与用户插件。插件来源只改变信任、发布和支持责任，不改变运行时安全边界。

## 2. 核心模型

插件必须独立声明以下维度：

- Runtime：`AGENT_ATOMIC` 或 `WORKFLOW_DSL`。
- Source：`BUILTIN` 或 `USER`。
- Scope：`MANAGED`、`STANDALONE` 或 `BOTH`。
- Trust：`OFFICIAL_SIGNED`、`USER_SIGNED` 或 `UNSIGNED`。
- Support：`OFFICIAL`、`COMMUNITY` 或 `SELF_MANAGED`。
- Capability：设备连接、发现、证书发现、部署、验证、回滚等标准能力。

禁止通过插件名称、厂商字符串、DeviceFamily 或 ProviderType 推导运行时和实现类。

## 3. 包与版本

统一 Manifest 使用 `gcac.plugin-manifest/v1`。每个版本必须不可变，并保存 Manifest SHA-256、资源 SHA-256、包 SHA-256、权限审批状态、来源和验证报告。

Manifest 可通过顶层 `logoUrl` 声明插件市场 LOGO。该字段只允许 HTTP(S) URL 或浏览器可访问的本地 Web 路径，例如 `/plugin-logos/nginx.svg`；禁止 `file:`、`data:`、其他协议和包含 `..` 的越界路径。LOGO 变化属于插件版本内容变化，必须递进版本，禁止覆盖已经导入的同版本 Manifest。

同一 `pluginId + version` 内容变化必须拒绝。升级必须发布新版本并展示 Capability、Permission、Runtime、Scope 和 Compatibility 差异。

内置插件启动安装必须满足两条规则：相同 `pluginId + version + packageSha256` 重复安装保持幂等；同一版本的 Manifest 或任一资源内容变化必须启动失败，禁止吞掉版本冲突、覆盖数据库记录或删除历史版本。修改已发布内置插件的 Manifest、Locale、Presentation、Workflow 等任一包内容时，必须先递增插件版本。

内置插件兼容升级只能迁移同租户、同 Plugin ID、来源为 `BUILTIN` 且语义版本低于当前目标版本的引用。升级目标必须是已成功导入的官方内置版本；禁止迁移用户插件，禁止把未来更高版本降级到当前代码版本。

内置设备插件位于 `backend/src/modules/plugins/builtin-plugins`。正式内置 Workflow DSL 仍只位于 `backend/src/modules/workflow-templates/builtin-workflows`；统一加载器可以读取正式 DSL 生成版本投影，但不得复制为第三套模板来源。

## 4. 生命周期

生命周期为：导入、校验、权限审批、禁用、启用、退休或隔离。

- 用户插件不得伪造 `BUILTIN` 来源。
- 权限变化必须使旧审批失效。
- 未启用、未审批、签名无效、版本冲突或资源校验失败的版本不得创建新 Binding。
- 已退休版本保留历史查询，但不得创建新业务绑定。

## 5. PluginBinding

PluginBinding 固定一个 PluginVersion，并保存普通变量、SecretRef、证书产物绑定、连接绑定和 ManagedContext。

- Managed Binding 必须包含 Host；设备插件通常还包含 DeviceAsset。
- Standalone Binding 禁止保存 ManagedContext。
- Secret 只能保存 `secret://` 引用，不得保存明文。
- Managed 与 Standalone 必须复用相同 PluginVersion、Workflow/Agent Recipe 和证书产物契约。

CapabilityAssignment 支持 Device、ManagedTarget、ApplicationAsset 三层，优先级为应用资产覆盖、受管目标覆盖、设备默认。设备管理插件和证书部署插件可以不同，宿主必须按能力解析最终 Binding。

## 6. 设备管理能力

设备插件至少声明：

- `device.connection.test`
- `device.discover`

按需声明：

- `device.identity.detect`
- `certificate.discover`
- `certificate.deploy`
- `certificate.rollback`

宿主负责网络出口、Gateway、TLS、Secret Grant、Artifact Grant、执行锁、恢复账本、表单渲染、发现投影和审计。插件不得直接访问数据库、Secret 存储或宿主任意文件。

## 7. 表单与展示

标准表单协议为 `gcac.plugin-form/v1`，必须支持文本、长文本、数字、密码引用、单选、复选、下拉、多选、开关、标签、文件引用和受限动态选项。

字段必须声明类型、默认值、必填、校验、条件显示、依赖、敏感属性、标准字段映射和 i18n Key。SecretRef 字段只能进入 SecretBinding。

设备详情由 Presentation Schema（展示结构）描述，宿主统一显示概览、Framework、Site、证书、绑定、日志和能力动作。禁止新增厂商专用 Vue 页面或 Tab 分支。

Presentation Schema 的 `valuePath` 必须引用统一设备详情 DTO 的公开字段；Framework、Site 和 Certificate 标签页必须读取标准发现投影，禁止引用只存在于厂商旧表或未定义的临时对象路径。插件资源测试必须验证 overview 字段路径可读且每个表格标签至少定义一列。

内置插件提供八种语言完整资源；用户插件至少提供默认语言，缺失语言由宿主安全回退。任何 HTML 必须按纯文本处理。

插件目录必须直接读取 Manifest 的 `logoUrl`，不得在前端按厂商名或 Plugin ID 维护硬编码 LOGO 映射。缺少或加载失败时由宿主显示统一回退标识。

## 8. 标准发现

设备发现输出必须使用 `gcac.device-discovery/v1`，包含 Device、Capability、Framework、Site、Certificate、CertificateBinding 和 Warning。

Certificate 应同时输出 `notBefore` 和 `notAfter`。厂商接口提供证书生效时间时，插件不得只投影到期时间；宿主必须把两个时间分别持久化并在前端转换为浏览器本地时间展示。

Certificate 应尽可能输出真实 `sha256Fingerprint`。如果厂商列表接口不返回指纹，插件应通过只读证书文件接口取得公钥证书内容并计算 X.509 SHA-256 指纹。宿主使用该指纹同时维护发现证书、CertificateVersion 和 CertificateBinding 的关联，禁止依赖名称或 Subject 猜测项目证书。

发现过程中逐项读取证书、站点或绑定详情时，必须为 foreach 每轮子步骤生成独立执行身份和幂等键，不能因步骤名相同把后续元素误判为重复请求。厂商内置对象、不可读文件或不支持格式不得中断整次只读发现；插件应使用 `foreach.continueOnError` 保留失败子步骤并继续后续元素，最终通过 Warning 暴露部分缺失。部署、变更和回滚流程禁止使用该容错模式。

所有集合字段必须始终输出数组。使用 JSONata 时必须显式处理零项和单项序列折叠，禁止依赖宿主把单对象自动转换为数组。

所有对象必须使用插件定义的稳定键。宿主负责 Schema 校验、幂等 ID、过期标记、冲突检测、关系投影和失败不污染。

稳定键不得直接拼接未经规范化的厂商对象名称。名称包含空格、中文、括号、通配符或其他协议允许字符以外的内容时，插件必须生成只包含英文字母、数字及 `._:/-` 的确定性编码键，并对 Site、CertificateBinding 等父子引用使用同一转换；原始名称只用于 `displayName`、`bindingName` 或 metadata 展示。禁止通过放宽宿主稳定键校验掩盖插件输出错误。

Framework 只表达设备真实承载且可独立识别的运行框架，不得用固定管理 API 或接入协议伪造 Framework。管理协议应进入 Device metadata 和基础信息；没有真实 Framework 时必须输出空数组，由宿主使用设备级 fallback service 承载 Site。

发现对象数量必须受宿主限制。插件不得通过输出无限数组绕过资源保护。

## 9. 证书产物

证书材料必须由统一 CertificateFormat 生成。插件只消费 ArtifactRef、SHA-256、大小、敏感标记和声明的输出槽位。

支持的通用输出包括叶子证书 PEM、私钥 PEM、有序中间链 PEM、PFX 和目标 SHA-256 指纹。明文私钥、PFX 密码和 Secret 不得进入普通计划快照、日志或数据库 JSON。

## 10. 执行、恢复与可观测性

Workflow DSL 插件使用 checkpoint、foreach、资源锁和恢复账本。Agent 插件继续使用 `gcac.agent-plan/v1` 和受控原子操作。

宿主按租户、插件版本和 Gateway 限制并发；按 Capability 独立熔断；记录开始、成功、失败、拒绝、在途、耗时和最近错误。熔断不得影响设备列表和其他 Capability。

恢复 Worker 只自动恢复幂等步骤。非幂等运行中步骤必须进入人工处理或显式补偿。

## 11. Standalone 归集

Scope 为 `BOTH` 的 Standalone Binding 可以归集为 Managed Device。

预览必须先取得只读标准发现输出，展示将创建或复用的 Host、DeviceAsset、Framework、Site、ManagedTarget、SecretRef、变量和产物绑定，并阻止地址、身份、站点和 Secret 冲突。

确认使用 PromotionRecord 作为 Saga 账本。完成后新计划使用 Managed Binding，历史执行仍保留 Standalone 标识。撤销必须恢复源 Binding，不删除历史执行。

## 12. 安全规则

- 禁止插件包携带 JavaScript、TypeScript、Shell、PowerShell、批处理、可执行文件或动态库。
- 所有网络、Secret、Artifact、设备写入和进程权限必须声明、审批并按步骤 Grant。
- Action 必须存在于宿主 Capability Registry 和插件 Manifest。
- Transform 使用受限表达式，不得访问宿主对象或执行代码。
- 日志、错误、审计和数据库执行快照必须脱敏。
- Built-in 插件不得绕过任何校验。

## 13. 宿主零厂商规则

核心 Registry、Resolver、Projector、执行编译器、设备表单和页面不得按厂商字符串选择实现。厂商名称只允许存在于插件包数据、测试 Fixture、兼容数据、迁移历史和文档。

新增厂商专用 Driver、Executor、Tester、Projector、Provider、Adapter 或设备页面必须由治理扫描拒绝。历史 Native Handler 允许列表被冻结，不得新增产品。

## 14. 验证清单

发布前至少验证：Schema、不可变版本、路径穿越、签名、权限审批、Secret/Artifact Grant、表单全字段、八语言或安全回退、标准发现、产物绑定、部署、验证、回滚、checkpoint、foreach、恢复、限流、熔断、指标、Managed/Standalone 等价性、归集和撤销。
