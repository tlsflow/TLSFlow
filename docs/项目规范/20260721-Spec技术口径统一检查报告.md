# Spec 技术口径统一检查报告

状态：完成

日期：2026-07-21

## 1. 检查目标

本次检查围绕 `018.1-能力驱动的证书部署适配器与兼容性目录` 和 `018.2-LinuxAgent产品线与能力适配架构`，统一 `specs/` 与 `docs/项目规范/` 中以下技术口径：

1. Agent 产品线与 Runtime 边界。
2. Windows 与 Linux 支持基线。
3. Provider、Adapter、Executor、Gateway 的职责边界。
4. Compatibility Profile、Capability 和兼容等级语义。
5. SSH、WinRM、CURL、签名脚本包和人工流程的降级边界。
6. 禁止使用 OS、发行版、产品版本或执行通道 `if/else`、`switch` 扩展兼容性。

## 2. 最终唯一口径

### 2.1 Agent 产品线

| 产品线 | 支持范围 | Runtime | 说明 |
| --- | --- | --- | --- |
| Windows Modern Agent | Windows Server 2016+ | Go | 现代 Windows 正式主产品线 |
| Windows Compatibility Agent | Windows Server 2008 R2 SP1 至 Windows Server 2012 R2 | C# / .NET Framework 4.8 | 独立构建、发布、升级和认证 |
| Linux Go Full Agent | 满足 Runtime Baseline 与 Architecture 的 Linux | Go，默认 `CGO_ENABLED=0` | 首批 `linux/amd64`、`linux/arm64` |
| Gateway Agent | 满足 Gateway Capability 的正式 Agent 环境 | 随所属正式产品线 | 只负责区域路由、探测和转发 |

以下产品线或主张已废弃：

- Windows PowerShell Full Agent。
- 覆盖全部平台的唯一 Go Runtime。
- Windows Server 2003/2008 非 R2 Legacy Agent。
- 旧 Linux Agent 或冻结过期 Go 工具链的 Linux 兼容产品线。

### 2.2 Windows 支持基线

| 系统范围 | Agent 支持 | 自动证书部署 |
| --- | --- | --- |
| Windows Server 2016+ | Windows Modern Agent | 支持，需满足 Capability 与 Profile |
| Windows Server 2008 R2 SP1 至 2012 R2 | Windows Compatibility Agent | 受控支持，需通过前置检查和认证 |
| Windows Server 2003/2003 R2 | `unsupported` | 禁止 |
| Windows Server 2008 非 R2 | `unsupported` | 禁止 |

WinRM、SMB、WMI、Gateway 或脚本包不能绕过 `unsupported`。低于基线的 Windows 只允许资产记录、迁移建议、显式人工流程或只监控。

### 2.3 Linux 支持基线

- 只维护 Linux Go Full Agent 一条正式 Linux 产品线。
- 初始 Kernel Baseline 为 Linux Kernel 3.2+，最终取 Go 工具链要求与 GCAC 实际 syscall 要求的较高者。
- 发行版名称不参与执行决策，只用于展示、认证环境和测试 fixture。
- Init System、Privilege、Filesystem、SELinux/AppArmor 和 Product Runtime 通过 Fact、Capability 与独立 Adapter 表达。
- 低于 Runtime Baseline 或 Architecture 不受支持时，使用 SSH、Gateway、签名脚本包、显式人工流程或只监控，不提供旧 Linux Agent。

### 2.4 架构边界

- Provider：只负责 IIS、NGINX、Apache、Tomcat 或自定义服务的产品领域语义。
- Adapter：负责 Certificate Store/Codec、Filesystem、Privilege、Service Controller、Security Module 和 Transport 的具体实现。
- Adapter Resolver：根据 Capability、Compatibility Profile、策略和优先级选择已注册实现。
- Executor：执行 Typed Operation，不理解产品业务语义。
- Gateway：只负责区域路由、探测和转发，不内嵌 SSH、WinRM、CURL 或产品部署逻辑。

新增兼容性只能增加 Fact Probe、Capability、Adapter 实现、Registry Entry、Compatibility Profile、Fixture 和测试证据。修改核心流程增加平台判断视为架构回归。

## 3. 已检查和修订范围

本次重点检查并修订了以下规范族：

- 产品与数据模型：`001`、`002`、`008`。
- Agent 与执行协议：`010`、`011`、`011.1`、`012`、`012.1`、`013`、`014`、`016`。
- Provider 与兼容性架构：`018`、`018.1`、`018.2`。
- 产品 Provider：`019`、`020`、`021`、`022`、`023`。
- 控制台展示：`028`。
- 项目规范：`docs/项目规范/20260721-Agent产品线与兼容性技术口径.md`。

主要修订结果：

1. 创建 `018.2`，补齐 Linux Agent 产品线、Runtime、平台 Adapter、产品 Handler、发布升级和认证矩阵规划。
2. 将 `012.1` 收缩为 Windows Server 2016+ Go Modern Agent 专项，不再覆盖 Windows Server 2012 R2。
3. 将 Windows Server 2003/2003 R2、Windows Server 2008 非 R2 和 IIS 6 固定为 `unsupported`。
4. 将 L2 统一定义为经认证的 Compatibility Agent，不再代表模糊的 Legacy Agent。
5. 将 NGINX、Apache、Tomcat、IIS 和自定义 Provider 统一为产品语义层，平台差异下沉到独立 Adapter。
6. 将控制台中的 Legacy Agent 新增入口改为历史迁移只读语义。

## 4. 历史内容处理规则

历史文档、历史任务完成记录和旧字段可以保留，但必须满足以下条件：

- 明确标注“历史”“已废弃”“迁移别名”或“被新 Spec 取代”。
- 不得作为当前支持承诺、实现入口或验收标准。
- 历史 `legacy` 字段只允许兼容读取，不允许创建新记录。
- 资产示例可以出现 Windows Server 2003 或旧发行版，但必须明确资产记录不等于 Agent 或自动部署支持。

`013-Legacy Agent与脚本包模式` 目录名作为历史编号保留。其有效实施范围仅包括签名脚本包、显式人工执行、结果回传和只监控，不再建设 Legacy Agent 产品线。

## 5. 后续扩展准入规则

任何新增平台、发行版、产品版本或执行通道必须提交：

1. Fact Probe 与证据字段。
2. 稳定 Capability Key 与参数约束。
3. 独立 Adapter 实现和 Registry Entry。
4. Compatibility Profile 与支持等级。
5. 契约测试、fixture、集成测试和真实环境认证证据。
6. 构建、安装、升级、回滚和安全评审结果。
7. 由 Profile 生成的兼容性目录更新。

以下提交不得合并：

- 在 Provider、Planner、Executor 或 Handler 中增加发行版/版本 `if/else`、`switch`。
- 复制 NGINX、Apache、Tomcat Handler 以适配不同发行版。
- 让 Gateway 同时承担路由和协议执行。
- 在文档、前端和代码中分别维护多套手工兼容性矩阵。
- 通过无代理通道绕过产品 `unsupported` 基线。

## 6. 检查结论

### 【核心判断】

✅ 值得做：兼容性矩阵是产品能力目录，不是版本判断表。当前架构只有在 Provider、平台 Adapter、执行通道和认证 Profile 分离后，才能持续扩展而不退化为特殊分支集合。

### 【关键洞察】

- 数据结构：兼容性应由 Fact、Capability、Adapter Registry、Compatibility Profile 和 Evidence 组成。
- 复杂度：发行版和版本差异被吸收到数据与注册表，核心 Resolver 保持稳定。
- 风险点：最大风险不是少支持一个旧系统，而是无代理、Gateway 或自定义命令绕过产品基线，制造不可审计的伪支持。

### 【最终结论】

规范层面的产品线、支持基线和职责边界已经统一。后续实现必须以 `20260721-Agent产品线与兼容性技术口径.md`、`018.1` 和 `018.2` 为准；历史文档只保留事实和迁移价值，不再具有当前规范效力。
