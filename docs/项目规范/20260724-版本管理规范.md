# GCAC 版本管理规范

## 1. 唯一版本源

GCAC 产品版本只允许由仓库根目录的 `version` 文件定义。文件内容必须是完整 SemVer，例如：

```text
0.1.0
```

前端构建、后端插件兼容校验和发布流程必须读取该文件，不得在业务代码中重复维护 GCAC 产品版本。

## 2. 版本更新

统一使用根目录脚本更新版本：

```bash
node scripts/versioning/update-version.mjs show
node scripts/versioning/update-version.mjs patch
node scripts/versioning/update-version.mjs minor
node scripts/versioning/update-version.mjs major
node scripts/versioning/update-version.mjs set 1.2.3
```

- `show`：显示当前版本，不修改文件。
- `patch`、`minor`、`major`：按 SemVer 规则递增对应版本段。
- `set`：设置指定的完整 SemVer，用于预发布版本或明确的发布版本。
- 非法 SemVer 必须直接拒绝，禁止静默修正。

## 3. 前后端使用方式

- Web 前端由 Vite 在构建时读取根 `version` 文件并注入 `__GCAC_VERSION__`。
- 前端业务代码统一从 `web/src/version.ts` 获取版本，不得直接读取文件或硬编码版本。
- 后端统一从 `backend/src/common/version.ts` 获取 `GCAC_VERSION`。
- 后端允许通过 `GCAC_VERSION` 环境变量覆盖文件值，仅用于产品文件未随运行包分发的部署场景；覆盖值仍必须是合法 SemVer。

## 4. 插件兼容规则

当前统一用户插件和 Agent Plan 插件的 Manifest（`gcac.plugin-manifest/v1`）使用：

```json
{
  "version": "1.0.0",
  "minGcacVersion": "0.1.0"
}
```

- `version` 表示插件自身版本。
- `minGcacVersion` 表示插件整体要求的最低 GCAC 宿主版本；兼容条件固定为 `GCAC_VERSION >= minGcacVersion`。
- 上传/导入、市场目录、启用、能力解析和执行边界必须复用后端统一 SemVer 比较逻辑；用户插件手动启用前必须再次检查。
- 为避免破坏历史插件，缺少 `minGcacVersion` 的旧 Manifest 按 `0.0.0` 归一化；新发布插件必须显式声明。
- 不兼容插件必须拒绝进入运行链路，并在错误详情中返回当前 GCAC 版本和最低要求版本。

历史 `gcac.agent-plugin/v1` 不属于当前统一 Manifest 发布链；该旧协议仍按 [`20260722-Agent插件开发规范.md`](20260722-Agent插件开发规范.md) 的严格字段规则处理，缺少 `minGcacVersion` 时不得进入旧协议运行链路。

插件能力还必须分别声明以下三类版本约束，不能把它们统称为“平台版本”：

| 版本维度 | 能力字段 | 约束内容 |
| --- | --- | --- |
| 宿主平台版本 | `compatibility.host.minVersion`、`requiredFeatures` | TLSFlow Host API、Schema、执行器版本和已登记宿主特性 |
| 目标产品版本 | `compatibility.targets[].productFamily`、`versionRange` | 目标产品族及其 SemVer 范围，例如 Nginx、NPM、IIS、Citrix |
| 执行环境版本 | `compatibility.execution[].location`、`minRuntimeVersion` | `AGENT`、`GATEWAY` 或 `CONTROL_PLANE` 运行时版本 |

`contractVersion` 只表示输入输出合同版本，不能替代宿主版本；`testedVersions` 只作为验证证据，不能解释为硬兼容范围。版本未知必须返回 `UNKNOWN`，不得默认兼容；低风险只读能力可以提示“版本未知，允许试探”，证书部署、回滚等高风险写能力必须阻止执行。兼容评估在插件目录、能力解析和实际执行前各执行一次，执行快照保存状态、输入版本、原因和时间。

插件版本不可变。新增能力并声明最低版本通常是非破坏性变更；提高已有能力的最低宿主、目标产品或执行环境版本属于破坏性变更，必须递增插件版本、不得原地修改已发布版本，并重新检查已有 Binding/Assignment。详细字段合同和生命周期门禁见 [`20260815-插件Manifest、Registry与Policy边界规范.md`](20260815-插件Manifest、Registry与Policy边界规范.md) 和 [`20260819-宿主插件能力接口与调用规范.md`](../插件开发/20260819-宿主插件能力接口与调用规范.md)。

## 5. 内置插件版本事实源

- 每个内置插件的唯一版本事实源是其包内 `manifest.json.version`；不得在 Catalog、Workflow、运行时代码或数据库中维护可反写该值的镜像版本。
- 后端启动和 `refresh-builtins` 扫描包后，统一 Registry、数据库 `PluginVersion` 和 Workflow Binding 都是不可变派生状态。
- 历史 P2 发布台账已删除，不属于当前版本管理链路。插件版本唯一来自包内 `manifest.json.version`，包摘要由 Loader/Registry 派生，Host API 授权由 Manifest/Policy/Execution Grant 边界负责。
- 同一 `pluginId@version` 摘要相同必须幂等注册；摘要不同的插件必须单独跳过并记录警告，不能阻塞其他插件或后端启动；较高 Manifest 版本创建新记录，旧记录保持可追溯。

## 6. 界面展示

当前 GCAC 版本必须显示在登录页面、主界面右上角用户菜单和设备页面。用户可见文案必须通过 `vue-i18n` 输出，样式必须使用设计系统主题变量。
