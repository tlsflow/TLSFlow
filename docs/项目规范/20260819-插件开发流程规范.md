# 插件开发流程规范

状态：现行版本

核对日期：`2026-08-23`

本文件定义 GCAC 插件从启动、测试、开发到验收的**操作流程**，是插件开发工作的唯一流程入口。它规定每个阶段必须做什么、产出物放在哪里、哪些动作被禁止，以及出现宿主能力缺口时的处理方式。

技术口径不重复定义，权威事实仍以以下规范为准：

- `docs/项目规范/20260802-统一设备与工作流插件开发规范.md`：插件模型、版本、绑定、执行边界和安全发布。
- `docs/项目规范/20260815-插件Manifest、Registry与Policy边界规范.md`：Manifest、Registry 与 Policy 边界。
- `docs/项目规范/20260722-Agent插件开发规范.md`：Agent Plan 插件目录组织、Manifest 与原子操作。
- `docs/项目规范/20260723-工作流模板管理及编写规范.md`：Workflow DSL 语法和模板来源。
- `docs/插件开发/20260819-宿主插件能力接口与调用规范.md`：宿主提供的接口和能力调用链，插件作者调用宿主能力的操作总览。
- `specs/004.1-插件包契约、权限与生命周期治理/`、`specs/004.5-插件进程隔离与宿主能力边界重构治理/`：跨域唯一事实。

代码存在不等于能力完成。没有真实协议、外部厂商、生产迁移或浏览器验收证据的事项必须标记 `IN_REVIEW` 或 `TODO`，不得在文档或交付说明中伪装为已完成。

## 1. 流程总览

```text
阶段0 启动：确认插件需求，创建插件文档目录
  -> 阶段1 平台测试：框架/站点发现/管理流程（可选）+ 证书更新流程（必选）-> 技术测试文档
  -> 阶段2 类型判定：内置插件 / 用户插件 -> 创建代码目录
  -> 阶段3 代码开发：只调用宿主插件系统接口和能力
  -> 阶段4 测试循环：手动测试 或 自动化测试流程（调试服务 + 直接调用插件）
  -> 阶段5 迭代归档：每轮问题现象/原因/解决方案写入「迭代说明」
  -> 验收：测试结果绑定插件版本与哈希，提交发布
```

阶段 4 与阶段 5 循环进行：每轮测试结束后，无论手动还是自动，问题解决后都必须先归档迭代说明，再进入下一轮。

### 发现责任总则

框架、站点、TLS 绑定和证书位置的发现必须只有一条来源链：

| 场景 | 事实采集 | 配置解析与标准化投影 | 证书插件职责 |
| --- | --- | --- | --- |
| Windows Full Agent | Agent 内置运行时发现 Nginx、Apache、Tomcat 等产品 | Agent 输出已确认事实，宿主只做通用投影 | 只负责证书部署、验证、回滚 |
| Linux Full Agent | Agent 从真实运行进程、服务 cgroup、程序运行参数和有效配置树生成权威 Web 事实 | 宿主只投影 Agent 已声明的 `frameworks/sites/listeners`；没有权威事实的旧 Agent 才允许兼容解析 | 只负责证书部署、验证、回滚 |
| 其他真正拥有发现能力的插件 | 插件自身声明的采集能力 | 宿主按其 Discovery Contract 投影 | 按该插件实际能力执行 |

因此，证书更新插件不得声明 `application.discover`、`certificate.discover`、`discoveryMappings`、`agentDiscoveryMappings`、`agent.fact.collect`、`runtimeEntrypoint` 或 Runner。`web.nginx` 独立发现/接入包已退役；`web.nginx`、`web.apache`、`app.tomcat` 仅作为框架事实类型和历史退役 ID 保留，不能作为运行期插件包注册。

## 2. 阶段 0：启动与插件文档目录创建

启动插件开发流程后，**第一步**必须在插件开发文档目录下创建该插件的文档目录：

```text
docs/插件开发/<pluginId>/
├── README.md              # 插件开发总览：目标、状态、关键决策、相关文档链接
├── 测试文档/              # 阶段 1 的技术测试文档
└── 迭代说明/              # 阶段 5 的每轮问题记录
```

- `<pluginId>` 使用插件稳定的 `pluginId`（如 `device.synology-dsm`），不得使用中文名、产品显示名或临时名称。
- 目录不存在时必须创建；已存在时复用并保持结构一致。
- 该目录是整个插件开发过程的事实存档点，与插件代码目录分开：代码目录放代码，`docs/插件开发/<pluginId>/` 放过程文档。
- 每份文档必须带日期前缀（`YYYYMMDD-...`），与仓库其他文档保持一致。

## 3. 阶段 1：平台测试（可选 + 必选）

按以下顺序测试插件平台的既有能力，并保存为技术测试文档：

| 测试项 | 是否必选 | 说明 |
| --- | --- | --- |
| 平台框架、站点发现及管理流程 | 按能力 | 只有插件实际声明发现能力时才测试；Windows/Linux 三类 Web 证书插件使用 Agent/宿主发现链，不重复测试插件发现 |
| 证书更新流程 | **必选** | 无论采用原子更新、SSH 流程还是 CURL 流程，都必须执行并记录 |

- 证书更新流程测试必须覆盖插件计划采用的执行通道：原子更新（Agent Atomic Plan）、SSH 流程、CURL 流程中至少插件实际使用的那一种；如插件同时支持多种，逐通道记录结果。
- 测试结果保存为技术测试文档，写入 `docs/插件开发/<pluginId>/测试文档/`，例如：

```text
docs/插件开发/<pluginId>/测试文档/
├── 20260819-平台框架与站点发现测试.md   # 可选
└── 20260819-证书更新流程测试.md          # 必选
```

技术测试文档至少包含：测试环境、被测对象与版本、测试步骤、期望结果、实际结果、通过/失败状态、失败时的证据（日志片段、接口返回）以及遗留问题。测试结果必须绑定 `pluginId`、插件版本、`packageHash`、`manifestHash` 和 `resourceHash`；版本或摘要变化后不得复用旧结果。

## 4. 阶段 2：插件类型判定与代码目录创建

根据用户要求确定插件类型，然后把插件代码文件夹创建到指定位置：

| 类型 | 代码位置 | 说明 |
| --- | --- | --- |
| 内置插件（BUILTIN） | `backend/src/modules/plugins/builtin-plugins/<pluginId>/` | 随代码发布并受 Git 跟踪；具体校验和生命周期见统一插件规范 |
| 用户插件（USER） | 用户指定的开发位置（本项目推荐 `data/plugins/<pluginId>/`） | 插件作者在自有/指定目录开发，打包后通过统一插件包导入接口 `POST /api/v1/plugin-packages/import` 发布为不可变 `PluginVersion` |

- 内置插件目录内建议结构：`manifest.json`、`runtime/`、`workflows/`、`forms/`、`action-contracts/`、`onboarding/`、`discovery/`、`fixtures/`、`tests/`；其中 `runtime/`、`discovery/`、`onboarding/` 只有在 Manifest 声明对应能力时才允许存在。
- 用户插件不得直接放进 `backend/src/modules/plugins/builtin-plugins/`，也不得与工作流 DSL 文件（`data/workflows`）混放；本项目推荐将待导入的用户插件包放在 `data/plugins/<pluginId>/`。目录扫描和生命周期规则以 [`20260802-统一设备与工作流插件开发规范.md`](../项目规范/20260802-统一设备与工作流插件开发规范.md) 为准，本流程只保留目录位置索引。`data/agent-plugins/` 仅是历史迁移记录，不作为当前用户插件的运行期目录。
- 类型判定结果和代码目录创建动作必须在插件文档目录的 `README.md` 中记录。

### 4.1 兼容性门禁操作

插件导入和发布前必须把兼容性声明当作可执行合同，而不是市场展示信息：

1. 外部市场包和用户插件目录包进入 `POST /api/v1/plugin-packages/import` 时，校验插件级 `minGcacVersion`；缺少该字段的历史统一插件按 `0.0.0` 归一化，新发布包必须显式声明。
2. 导入时对每个能力校验 `compatibility.host`、`compatibility.targets` 和 `compatibility.execution` 的字段结构；进入目录或拥有目标上下文后，再分别使用宿主平台版本/特性、目标产品族与版本范围、Agent/Gateway/Control Plane 运行时版本评估；`contractVersion` 不能替代平台版本，`testedVersions` 不能作为硬兼容范围。
3. 插件启用前必须重新执行插件级门禁；目标上下文变化或绕过导入接口写入版本记录时，不得沿用导入时的旧结果。
4. 受管目标能力解析时必须记录实际输入的产品族、产品版本、宿主版本/特性、执行位置和运行时版本。版本未知统一返回 `UNKNOWN`；低风险只读能力可允许试探，证书部署、回滚等高风险写能力直接阻断。
5. 实际执行前必须再次评估，并把能力键、评估状态、输入、原因、评估时间和规则摘要写入执行快照；执行开始后只使用冻结快照，不按当前最新版本重新解析。
6. 提高已有能力最低宿主、目标产品或执行环境版本时，必须递增插件版本并重新检查已有 Binding/Assignment；禁止修改已启用 PluginVersion 的兼容范围。新增能力的最低版本约束通常不影响既有能力。

字段定义、状态和统一评估器以 [`20260815-插件Manifest、Registry与Policy边界规范.md`](../项目规范/20260815-插件Manifest、Registry与Policy边界规范.md)、[`20260802-统一设备与工作流插件开发规范.md`](../项目规范/20260802-统一设备与工作流插件开发规范.md) 和 [`20260819-宿主插件能力接口与调用规范.md`](../插件开发/20260819-宿主插件能力接口与调用规范.md) 为准；本流程只规定操作顺序，不复制字段 Schema。

## 5. 阶段 3：插件代码开发与宿主边界

### 5.1 默认只调用宿主插件系统接口和能力

插件内部代码、工作流的编写，**默认只允许调用宿主插件系统提供的接口和能力**，包括：

- Manifest 与资源包合同（`gcac.plugin-manifest/v1`、资源索引、版本不可变）。
- 能力解析链：`CapabilityAssignment -> PluginBinding -> PluginVersion`。
- `WorkflowExecutionBinding` 作为普通工作流的正式执行来源。
- `DeploymentInputContractV1` 输入声明与投影接口。
- Workflow DSL 编排与 `plugin.action` 代码型能力。
- Plugin Runner v2 协议与 `hostApi.call` 登记方法（Host API 能力登记表见 `docs/插件开发/20260819-宿主插件能力接口与调用规范.md`）。
- 宿主 HTTP 接口索引（插件注册、版本、能力、Binding、工作流测试、输入投影）。

**禁止**直接修改宿主系统代码来实现插件功能，包括但不限于：在 `backend/src/modules/` 宿主模块中新增厂商/产品名分支、修改宿主 Schema/DTO/执行链、在宿主侧硬编码插件逻辑。

### 5.1.1 框架与站点发现的宿主边界

插件不能因为需要证书部署输入而复制框架或站点发现。Windows Full Agent 和 Linux Full Agent 都必须从实际进程、服务、运行参数和有效配置树解析出 Nginx、Apache、Tomcat 事实，统一通过 `FULL_WEB_DISCOVERY` 的 `frameworks/sites/listeners` 合同上报；`agent-capability-discovery.projector.ts` 只做标准化投影。`backend/src/modules/plugins/discovery/web-config-discovery.ts` 保留为旧 Agent 的兼容回退，不得覆盖或生成权威部署事实。

证书插件只消费已投影的 `frameworkType`、站点、TLS 绑定、`certificateLocation`、`configFingerprint`、`serviceName` 和 `programPath`。不得新增独立 `web.nginx` 发现包，也不得通过旧插件 ID、默认路径、端口或 TLS 握手补发现。

### 5.2 确需修改宿主代码时的流程

经评估确认必须修改宿主系统代码时，必须**暂停当前流程**：

1. 停止一切代码修改动作，向用户说明：为什么插件能力接口无法满足需求、要改宿主哪个模块、改动范围和风险。
2. 征得用户明确同意后，才能更新对应的宿主代码。
3. 修改完成后，必须同步更新：
   - 本插件开发流程规范（如流程、边界有变化）；
   - `docs/插件开发/20260819-宿主插件能力接口与调用规范.md` 中对应的宿主能力说明（接口、权限、限制、禁止项）；
   - 受影响的权威规范（`20260802-统一设备与工作流插件开发规范.md` 等）与 Spec。
4. 未经用户同意，不得以任何方式绕过该限制（包括临时补丁、注释开关、环境变量开关）。

### 5.2.1 Agent-side 插件的宿主安装边界

Agent-side 插件由宿主安装包分发，但插件代码不得自行假设临时解压目录可被运行时读取。Windows Go Full Agent 的 bootstrap 必须把 manifest 中声明的 Agent-side 可执行文件复制到 Agent 正式安装目录的 `plugins/` 子目录；Agent 运行时只从该目录加载。Gateway 安装不应携带 Full Agent 专用发现插件。

因此，出现 `AGENT_SIDE_PLUGIN_UNAVAILABLE` 时，应先检查宿主安装包是否包含插件、bootstrap 是否完成复制以及正式安装目录文件是否存在，不能把 Agent-side 固定事实转化为要求用户填写的部署输入。若需要修改 bootstrap，必须按第 5.2 节取得用户同意，并在插件迭代说明中记录宿主边界变更。

### 5.2.2 宿主兼容投影的修改边界

宿主为兼容历史数据补全通用投影时，允许在取得用户同意后修改宿主的通用输入回显、资产证书投影和详情脱敏 DTO，但不得加入插件名称分支、猜测路径或要求用户填写 Agent/插件已经发现的固定事实。此类修改必须同步更新宿主能力接口规范，并在对应插件的「迭代说明」中记录根因、改动位置和验证证据。

### 5.3 开发期硬要求

- 插件版本更新必须递进 Manifest 版本并同步全部 Workflow `metadata.version`；内置插件使用 `scripts/plugins/update-plugin-version.mjs`。
- 证书材料通过 Artifact Slot 注入，Secret 通过 Credential/Grant 引用；不得把 PEM、私钥、密码、Token 写入普通变量、DSL 命令、日志或审计明细。
- 插件代码只能通过 DSL 明确声明的 `plugin.action` 进入 Plugin Runner，不得把 Runner 入口当成整份工作流执行器。

### 5.4 Logo 资源开发边界

Logo 是插件包资源，不属于宿主静态资源。包内目录、Manifest `resources.logos`、摘要和读取接口以 [`Spec 004.1 Logo 资源归属与宿主读取合同`](../../specs/004.1-插件包契约、权限与生命周期治理/docs/20260822-插件Logo资源归属与宿主读取合同.md) 为唯一权威。

开发插件 Logo 时必须：

1. 将 `logos/logo.svg` 和 `logos/logo-square.svg` 放入当前插件目录。
2. 在 Manifest 的 `resources.logos.horizontal` 和 `resources.logos.square` 中声明两个包内路径。
3. 记录官方来源、许可证/使用说明、原始摘要和转换方式；没有可核验官方来源时不得伪造品牌 Logo。
4. 将 Logo 纳入资源完整性、`resourceHash`、包摘要和版本不可变测试。
5. Logo 内容或路径变化时递进 Manifest 与全部 Workflow 版本，不得修改历史 PluginVersion。
6. 通过宿主派生的 PluginVersion 资源 URL 验证市场、详情、应用向导和设备向导，不得使用 `/plugin-logos/`。

## 6. 阶段 4：测试循环（手动 / 自动化）

### 6.1 手动测试

按用户要求，由用户手动操作并反馈结果。插件开发方负责：

- 提供测试入口、输入说明和预期结果；
- 收集用户反馈的问题现象与证据；
- 修复后按阶段 5 归档迭代说明，再进入下一轮。

### 6.2 自动化测试流程

用户要求启动自动化流程时，按以下步骤循环执行：

1. **确保调试服务已启动**：使用 `./scripts/dev-backend.sh` 启动后端调试服务（必要时同时启动 `./scripts/dev-web.sh`）；服务未启动或启动失败时，先解决启动问题，不得在服务不可用时假装执行。
2. **确认插件可用**：按 [`20260802-统一设备与工作流插件开发规范.md`](../项目规范/20260802-统一设备与工作流插件开发规范.md) 完成对应生命周期动作，随后确认 Binding/Assignment 状态为 `ACTIVE`。
3. **定位应用资产**：按用户指定的应用资产名称，找到对应的应用资产及其执行绑定。
4. **直接调用插件**：调用该插件的证书更新流程（`certificate.deploy` 能力工作流），执行指定应用资产的证书更新。
5. **获取执行结果**：读取工作流执行结果、结构化输出与审计；写操作状态为 `UNKNOWN` 时不得自动重放写请求。
6. **解决报错并循环迭代**：根据执行结果定位问题；属于插件代码的问题，直接修复插件并进入下一轮；属于宿主能力缺口的问题，按第 5.2 节暂停并征求用户同意。
7. 循环直到证书更新流程完成并验收。

### 6.2.1 统一向导与部署输入专项验收

凡是插件声明 `resources.onboarding` 或 `deploymentDefaults`，证书更新流程测试还必须验证：

1. 选择站点后立即生成部署输入投影，并以插件声明默认值初始化应用级 Binding。
2. 表单只显示配方实际声明的 Slot；`fixed`、`asset`、`derived`、`system`、`step_output` 和 `runtime` 字段不得变成用户必填输入。
3. `default_overridable` 字段默认可执行、允许修改；证书格式匹配成功后，Artifact 输出映射自动回填，不要求重复选择叶子证书、私钥、证书链和指纹。
4. 站点切换、重复点击和请求竞态不会让旧投影覆盖新投影；投影失败必须结束 loading 并显示可定位的结构化错误。
5. 前端不得把 Vue Reactive Proxy 直接传给 `structuredClone`；复制输入前必须解除响应式包装。
6. `submit`、`execute` 和显式 Dry-run 读取同一份当前租户部署任务设置。Dry-run 关闭时不得出现隐式预检，显式 Dry-run 请求必须明确返回禁用原因。

### 6.2.2 兼容性专项验收

凡是能力声明版本约束，测试循环还必须覆盖：

1. 插件级 `minGcacVersion` 低于当前宿主时导入/启用拒绝，历史缺失字段按约定归一化。
2. 能力级宿主最低版本、必需特性、目标产品 `versionRange` 和执行位置最低运行时版本分别命中兼容与不兼容结果。
3. 宿主、目标产品或运行时版本未知时返回 `UNKNOWN`；只读能力的试探路径和证书部署等高风险写能力的阻断路径必须分别有证据。
4. 插件目录、能力解析、执行前三次评估使用相同规则；执行快照包含评估状态和版本输入，执行前目标版本变化时不能沿用旧的 `COMPATIBLE` 结果。
5. 提高已有能力最低版本的升级必须递增插件版本，并验证已有 Binding/Assignment 被重新检查；`testedVersions` 只能作为测试证据展示。

### 6.3 证书版本选择硬规则

自动化测试流程中，更新指定的证书版本**必须使用截止日期次新的证书，禁止使用截止日期最新的证书**：

- 对应用资产可用证书按截止日期（`notAfter`）排序，选择倒数第二新（次新）的证书版本执行更新；
- 最新截止日期的证书不得作为测试更新对象，防止把生产最新证书作为验证素材或误更新线上版本；
- 应用资产的证书版本集合、排序结果与最终选择必须在执行结果和迭代说明中记录，供复核。

## 7. 阶段 5：迭代说明归档

无论是用户手动迭代还是自动化测试流程，**每次测试后的问题解决**，必须把该轮问题记录保存到对应插件文档目录的「迭代说明」文件夹：

```text
docs/插件开发/<pluginId>/迭代说明/
└── 20260819-第01轮-<问题摘要>.md
```

文件命名：`YYYYMMDD-第NN轮-<问题摘要>.md`，轮次连续递增。每份记录必须包含：

| 字段 | 要求 |
| --- | --- |
| 问题现象 | 可复现的描述，附日志片段、接口返回或截图证据 |
| 问题原因 | 根因分析，明确是插件代码、插件资源、宿主能力还是外部厂商问题 |
| 解决方案 | 具体修改内容与修改位置 |
| 验证结果 | 修复后本轮/下轮测试的验证结论 |
| 涉及对象 | 插件版本、`pluginId`、应用资产、执行通道（原子/SSH/CURL） |

- 未归档的轮次视为未完成：问题解决后必须先写迭代说明，再进入下一轮测试。
- 迭代说明不得包含明文 Secret、私钥、PEM、Token 或密码。
- 归档的轮次记录应汇总进插件 `README.md` 的「迭代历史」小节。

## 8. 验收与发布

发布前按 `20260802-统一设备与工作流插件开发规范.md` 第 9 节验证清单执行，并额外确认：

1. 插件文档目录结构完整：`README.md`、`测试文档/`（证书更新流程测试必选）、`迭代说明/`（如有迭代）。
2. 框架/站点发现责任已经核对：Windows/Linux 均使用 Agent 运行时发现，宿主只投影权威事实并保留旧 Agent 兼容回退；证书插件没有发现声明或 Runner。
3. 证书更新流程测试覆盖插件实际使用的执行通道（原子/SSH/CURL），结果绑定插件版本与哈希。
4. 代码开发未越界修改宿主代码；确需修改的，用户同意记录与规范同步更新记录齐全。
5. 自动化测试（如执行）的最终轮次为成功，且选用的证书版本符合「截止日期次新」规则。
6. 接入向导、部署输入投影、Dry-run 设置和正式执行链路的最终状态均有明确验收证据。
7. 全部迭代说明已归档，无未记录的问题轮次。
8. 插件目录、能力解析和实际执行前的兼容性门禁均有测试证据，未知版本和高风险写能力阻断结果已写入执行快照。
