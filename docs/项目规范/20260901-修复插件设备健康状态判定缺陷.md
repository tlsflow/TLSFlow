# 插件设备健康状态判定缺陷修复

**修复日期**: 2026-09-01
**问题编号**: F5 资产离线仍显示健康
**影响范围**: 所有通过插件（PLUGIN）管理的网络设备

## 问题现象

用户报告 F5 BIG-IP 设备（102.37.137.196:8443）实际已离线，资产详情页仍显示"健康状态: 健康"。

## 根因分析

### 数据证据链

```
pg_device_assets:  last_discovered_at = null      ← 从未成功发现
                   last_error_code    = null
                   credential_id      = null      ← 未绑凭据
                   gateway_id         = null      ← 控制面直连探测

pg_hosts:          status             = 'UNKNOWN'

liveness_signals:  MANAGEMENT_TCP     = HEALTHY   ← 9 秒前观测成功
                   （唯一信号，无应用层验证）

实测连通性:
  nc 102.37.137.196 8443                    → succeeded  (TCP 通)
  curl https://.../mgmt/tm/sys/version      → timeout    (HTTP 不通)
```

TCP 握手成功、应用层超时 → 云侧 LB / 防火墙 / NAT 代答了 SYN，设备本身不可达。

### 缺陷 A：裸 TCP 握手可以把"未知"抬成"健康"

`backend/src/modules/devices/domain/managed-device-projection.ts:161`：

```typescript
if (livenessStatus === 'ONLINE' && healthStatus === 'UNKNOWN') return 'HEALTHY';
```

**逻辑**：管理 TCP 探测成功 → `livenessStatus = 'ONLINE'`；设备从未发现成功 → `healthStatus = 'UNKNOWN'` → 合流后输出 `'HEALTHY'`。

**错误**：TCP 握手只能证明"这个 IP:PORT 上有人接了 SYN"，不能证明设备应用层可用。云基础设施代答握手的情况极为常见（LB、防火墙、NAT）。

### 缺陷 B：传递了错误的状态参数

`PluginManagedDeviceProjectionAdapter.project()` 第 121 行和 `dashboard-read.repository.ts` 第 864 行：

```typescript
const sourceStatus = appliance.lastErrorCode ? 'ERROR'
  : appliance.lastDiscoveredAt ? 'DISCOVERED'
  : source.hostStatus;

const healthStatus = mapNetworkDeviceHealth(
  source.hostStatus,  // ← 错误：传了原始 pg_hosts.status，永远是 'UNKNOWN'
  ...
);
```

**错误**：发现流程只更新 `pg_device_assets.last_discovered_at`，从不回写 `pg_hosts.status`。应该传计算出的 `sourceStatus`（包含 `'DISCOVERED'` 状态），而不是原始 `host_status`。

### 缺陷 C：共用了不适配的陈旧阈值

`mapNetworkDeviceHealth` 原实现使用 `DEVICE_HEALTH_STALE_SECONDS`（默认 60 秒）判定发现结果是否陈旧。但：

- **TCP 探测**: 10 秒一次，周期调度（`main.ts:174`）
- **设备发现**: 手动触发，无周期调度

共用 60 秒窗口会导致所有网络设备在发现 1 分钟后立刻变"未知"，破坏现网可用性。

## 修复方案（A + B）

### A. 删除错误的提升规则

**文件**: `backend/src/modules/devices/domain/managed-device-projection.ts`

```diff
 function mergeNetworkHealthWithLiveness(
   healthStatus: ManagedDeviceHealth,
   livenessStatus: 'ONLINE' | 'OFFLINE' | 'UNKNOWN',
   hasLivenessSignal: boolean,
 ): ManagedDeviceHealth {
   if (livenessStatus === 'OFFLINE') return 'UNREACHABLE';
-  if (livenessStatus === 'ONLINE' && healthStatus === 'UNKNOWN') return 'HEALTHY';
   if (livenessStatus === 'UNKNOWN' && hasLivenessSignal && healthStatus === 'HEALTHY') return 'UNKNOWN';
   return healthStatus;
 }
```

**语义变更**：TCP 信号只允许**降级**（健康 → 不可达），不允许**升级**（未知 → 健康）。

### B. 传递正确的派生状态 + 独立发现陈旧窗口

**文件 1**: `backend/src/shared/observation-freshness.ts`

```diff
+export function readDiscoveryStaleSeconds(): number {
+  return readPositiveSeconds('DEVICE_DISCOVERY_STALE_SECONDS', 24 * 60 * 60);
+}
```

**文件 2**: `backend/src/modules/devices/domain/managed-device-projection.ts`


**文件 3**: `backend/src/modules/devices/domain/managed-device-projection.ts` 第 121 行

```diff

+  sourceStatus,  // 使用派生状态（'DISCOVERED' / 'ERROR' / 原始状态）
```

## 修复后的判定逻辑

| 发现状态 | TCP 探测 | 最终健康状态 | 说明 |
|---------|---------|------------|------|
| 从未发现 | 在线 | `UNKNOWN` | **本次修复目标**：裸 TCP 不能抬成健康 |
| 从未发现 | 离线 | `UNREACHABLE` | TCP 降级生效 |
| 24h 内成功发现 | 在线 | `HEALTHY` | 有强证据 + TCP 当前通 |
| 24h 内成功发现 | 离线 | `UNREACHABLE` | TCP 降级覆盖 |
| 发现 > 24h | 在线 | `UNKNOWN` | 证据过期，TCP 不能抬升 |
| 发现 > 24h | 离线 | `UNREACHABLE` | TCP 降级生效 |
| 有错误码 | 任意 | `UNREACHABLE` | 应用层失败优先 |

## 已知残留风险（需后续方案 C）

当前修复后仍存在以下边界情况：

**场景**：设备 20 小时前发现成功，现在实际离线，但云侧 LB 仍代答 TCP。

- **判定结果**: `HEALTHY`（发现在 24h 窗口内 + TCP 在线）
- **实际状态**: 不可达
- **根因**: TCP 握手仍然是弱证据，无法识破 LB 代答

**彻底解决方案（方案 C）**：周期性应用层探测

在 `main.ts` 新增调度器，每 N 分钟对插件设备执行 `device.connection.test` 能力（HTTP GET 真实 API），写入新的 `APPLICATION_LAYER` liveness 信号类型，替代 TCP 作为在线判定依据。

**当前设计的权衡**：

- 方案 A+B 消除了"从未发现却显示健康"的错误（本次 F5 问题）
- 保留 24h 发现窗口 + TCP 降级能力，对已成功发现过的设备提供基本持续监控
- LB 代答的残留 lie 需要方案 C 才能彻底解决，但那需要新增调度器和信号类型，改动面更大

## 破坏性影响分析

### ✅ 无破坏性（向后兼容）

1. **成功发现过的设备**：发现记录在 24h 内 + TCP 在线 → 仍显示 `HEALTHY`，行为不变
2. **TCP 离线降级**：已存在的降级规则继续生效，不受影响
3. **云服务**：明确标记为 `livenessMode='DISCOVERY'` 的设备跳过 TCP 探测，不受影响

### ⚠️ 预期变化（符合修复目标）

**从未成功发现的网络设备**：从错误的 `HEALTHY` 变为正确的 `UNKNOWN`。

- **判断依据**：`pg_device_assets.last_discovered_at IS NULL`
- **影响设备类型**：手动添加但从未点"发现"按钮的设备（如本次 F5）
- **业务影响**：这些设备本就不应该参与证书部署等自动化任务，显示 `UNKNOWN` 是诚实且安全的

## 环境变量配置

| 变量名 | 默认值 | 说明 |
|-------|-------|------|
| `DEVICE_DISCOVERY_STALE_SECONDS` | `86400`（24小时） | 插件设备发现结果的有效期。超过此时间未重新发现的设备健康状态降为 `UNKNOWN` |
| `DEVICE_HEALTH_STALE_SECONDS` | `60` | TCP 探测信号的有效期（不变，仅用于心跳等高频信号） |

**调优建议**：

- 如果发现流程有自动化调度（当前没有），可缩短至 1-4 小时
- 如果设备数量大、发现成本高，可延长至 7 天
- 不建议低于 1 小时（会导致手动发现后很快又变"未知"）
