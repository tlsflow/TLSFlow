# Agent 平台横向扩展与兼容性维护规范

> 状态：生效
> 版本：1.0
> 生效日期：2026-07-21
> 适用范围：所有 Agent 产品线、Provider、Adapter、Executor、Compatibility Profile、兼容性目录、安装升级脚本和认证活动

## 1. 文档目标

本文回答以下实际问题：

1. 新增一个操作系统或发行版时，到底需要修改哪些内容？
2. 什么情况下应当零代码扩展，什么情况下才允许新增 Adapter？
3. 什么情况下必须新建 Agent 产品线，而不是继续兼容现有 Agent？
4. 如何避免通过 `if/else`、`switch`、发行版专用目录或复制 Profile 扩展兼容性？
5. 如何维护 Agent 的运行基线、能力声明、适配器组合、真实认证和支持等级？
6. 如何证明新增兼容性没有破坏现有 IIS、Nginx、Apache、Tomcat、SSH 和 CURL 链路？

本文是 `docs/项目规范/20260721-Agent产品线与兼容性技术口径.md` 的执行规范：

- 技术口径定义必须遵守的产品线和架构原则。
- 本文定义新增平台、产品和兼容性时的具体步骤、文件范围、测试门禁和发布流程。
- `018.1-能力驱动的证书部署适配器与兼容性目录` 定义公共兼容性合同。
- `018.2-LinuxAgent产品线与能力适配架构` 定义 Linux Agent 的具体实现和认证要求。

当历史文档、代码注释或示例与本文冲突时，不得直接按历史内容实现；必须先按照项目规范修订技术口径。

## 2. 核心原则

### 2.1 兼容的是能力，不是操作系统名称

Agent 执行路径必须依赖机器实际提供的 Capability（能力声明），不能依赖发行版、操作系统展示名称或产品版本名称。

正确数据流：

```text
Platform Fact
    ↓
Capability Declaration
    ↓
Compatibility Profile Match
    ↓
Adapter Resolver
    ↓
Adapter Composition
    ↓
Typed Operation
    ↓
Execution + Verification + Recovery
```

禁止数据流：

```text
OS/发行版/版本名称
    ↓
if / else / switch
    ↓
选择命令、路径、产品 Handler 或回滚方式
```

### 2.2 新增普通发行版应当零代码

当新发行版满足现有 Agent Runtime Baseline（运行基线），且能声明现有 Capability 时，新增支持原则上只能增加：

- 真实环境 Fact fixture；
- 测试证据；
- Compatibility Profile 或既有 Profile 的证据；
- 认证报告和兼容性目录发布记录。

不得修改：

- Agent 主循环；
- Action Handler Registry 的既有分派逻辑；
- Product Adapter；
- Adapter Resolver；
- Provider 的 OS 判断；
- 前端硬编码兼容性矩阵。

### 2.3 产品与平台必须正交

产品语义和平台机制是两个独立维度。

产品维度示例：

- IIS；
- Nginx；
- Apache；
- Tomcat；
- 后续新增的 HAProxy、Caddy、Jetty 等。

平台维度示例：

- Windows Certificate Store；
- POSIX Filesystem；
- Windows SCM；
- systemd；
- SysV；
- OpenRC；
- root、sudo、doas；
- SELinux、AppArmor；
- 本地 Agent、SSH、CURL、Gateway。

不得创建 `UbuntuNginxHandler`、`RockyApacheHandler`、`WindowsTomcatProvider` 等把两个维度重新绑定的实现。

插件兼容性声明也必须保持两个维度独立：`compatibility.productFamilies` 使用 Host/Agent 的平台产品族标准值，例如 Windows 主机使用 `WINDOWS_SERVER`；`frameworkTypes` 才表达 `web.apache`、`web.nginx` 或 `app.tomcat` 等产品框架。不能用框架名替代产品族，也不能把平台后缀拼进产品族值。兼容性测试必须同时验证产品族匹配和框架类型匹配，避免插件在正确产品上被错误筛除。

### 2.4 失败关闭

发生以下情况时必须阻止执行：

- 缺少必要 Capability；
- Capability 证据未知、过期或置信度不足；
- 找不到必需 Adapter；
- 同类 Adapter 存在多个同级候选；
- Profile 为 `unsupported`；
- Action Schema Version 不支持；
- 没有唯一 Product Handler；
- 必需的备份、验证或恢复能力不存在。

禁止通过默认 Adapter、猜测命令、自动选择第一个候选或返回伪成功继续执行。

### 2.5 Never break userspace

对已经发布且仍在支持范围内的 Agent 平台能力，兼容性扩展不得改变现有外部行为，包括：

- 已发布 Action 的结果、错误和恢复语义；
- 请求和结果字段；
- 错误码和错误分类；
- 幂等和重试语义；
- 备份、验证、回滚和恢复语义；
- SSH/CURL 工作流行为；
- 已发布 Profile 的稳定 ID 和版本语义。

已发布平台能力需要淘汰时，必须通过版本化合同和明确的发布说明完成。GCAC 当前插件重构属于未发布项目的最终合同切换：旧插件 Action、旧协议 Alias 和旧 Runtime 直接删除或拒绝，不建立旧对象到新对象的升级绑定，也不建立运行期兼容。

## 3. 统一兼容性模型

平台兼容性由 Runtime Baseline、Platform Fact、Capability Declaration、Adapter Composition、Compatibility Profile 和 Certification Record 六个概念共同决定，不允许用单一 OS 名称替代。

### 3.1 Agent Runtime Baseline

Runtime Baseline 回答：

> Agent 二进制能否在目标环境安装、启动、通信、升级和回滚？

至少包含：

- Agent 产品线；
- OS Family；
- 最低操作系统、Kernel 或 Runtime；
- CPU Architecture；
- 动态库或静态链接要求；
- TLS 和加密基线；
- 服务安装方式；
- 权限要求；
- 明确不支持范围。

当前正式产品线：

| 产品线 | 运行范围 | Runtime |
| --- | --- | --- |
| Windows Compatibility Agent | Windows Server 2008 R2 SP1、2012、2012 R2 | Go 1.20.x |
| Windows Modern Agent | Windows Server 2016 及以上 | Go |
| Linux Go Full Agent | 满足当前 Linux Runtime Baseline 的 Linux；首批 amd64/arm64 | Go，默认 `CGO_ENABLED=0` |
| Gateway Agent | 由对应 Gateway 产品线基线决定 | 不改变目标产品语义 |

Runtime Baseline 是安装和运行边界，可以检查 OS Family、系统版本、Kernel 和架构；但这些信息不得用于产品执行路径分派。

### 3.2 Platform Fact

Fact 是 Agent 对目标环境的原始观察，必须保留事实来源、采集时间和失败状态。

示例：

```json
{
  "kernel": "6.1.0",
  "architecture": "amd64",
  "initSystem": "systemd",
  "privilege": "root",
  "securityModule": "selinux",
  "securityMode": "enforcing",
  "filesystem": "posix",
  "products": {
    "nginx": { "installed": true }
  }
}
```

Fact 规则：

- 采集失败必须保留 `unknown` 或错误证据，不能转换为 `false`。
- 发行版名称可以作为资产事实和认证标签。
- 产品版本可以作为发现结果和认证标签。
- Fact Collector 必须静态注册，重复注册失败。
- 新增 Collector 不得修改统一采集主循环。

### 3.3 Capability Declaration

Capability 是对 Fact 的稳定、版本化解释，回答：

> 当前环境是否具备某项可执行能力？

示例：

```text
agent.full.online
linux.systemd.v1
linux.privilege.root.v1
linux.security.selinux.v1
linux.filesystem.posix-atomic.v1
nginx.cert.install
iis.binding.update
```

Capability 必须包含：

- 稳定 Capability Key；
- 值；
- 状态；
- 置信度；
- 证据；
- 采集或计算时间；
- 必要时的过期时间。

Capability 命名必须描述能力，不得描述发行版：

```text
正确：linux.systemd.v1
错误：linux.ubuntu.v1

正确：linux.security.selinux.v1
错误：linux.rhel-security.v1
```

### 3.4 Adapter Composition

Adapter Composition 回答：

> 当能力满足时，使用哪些独立适配器完成操作？

公共目录只允许七类 AdapterKind：

1. `product`
2. `certificate_store`
3. `artifact_codec`
4. `service_controller`
5. `transport`
6. `verifier`
7. `rollback`

示例：

```json
{
  "product": "product.nginx",
  "certificate_store": "certificate-store.posix-filesystem",
  "artifact_codec": "artifact-codec.pem",
  "service_controller": "service-controller.systemd",
  "transport": "transport.agent-local",
  "verifier": "verifier.tls-remote",
  "rollback": "rollback.posix-certificate-files"
}
```

Privilege、Filesystem 和 Security Module 可以作为 Agent 内部平台 Adapter 与 Capability 存在；未经公共合同评审不得随意新增 AdapterKind。

### 3.5 Compatibility Profile

Compatibility Profile 是当前 v1 兼容性目录的发布单元，回答：

> 什么能力组合可以使用什么 Adapter Composition，以什么支持等级对外发布？

当前 Profile 字段职责：

| Profile 字段 | 当前职责 |
| --- | --- |
| `match` | Capability Requirement，即能力匹配条件 |
| `composition` | Adapter Composition，即执行组合 |
| `status` | 当前发布支持等级 |
| `limitations` | 适用限制和未覆盖范围 |
| `evidence` | 合同测试、fixture、真实环境和安全评审证据 |

发行版名称不得成为运行时 `match` 的核心条件。只有 Runtime Baseline 确实依赖的 OS Family 或最低版本可以进入安装边界；发行版和产品版本应主要存在于 evidence、fixture 和认证报告中。

### 3.6 Certification Record

Certification Record（认证记录）回答：

> 哪个固定环境实际完成了哪些测试？

认证记录至少包含：

- OS 名称和精确版本；
- Kernel 或 Windows Build；
- CPU Architecture；
- Agent 版本和构建哈希；
- init system 或 Windows Service Model；
- 权限模式；
- SELinux/AppArmor 等安全模式；
- 产品和精确版本；
- 证书格式；
- 执行通道；
- Adapter Resolution 结果；
- 成功、失败和恢复场景；
- 日志、审计、截图或自动化报告引用；
- 执行时间、责任人和证据过期时间。

发行版和产品版本可以出现在认证记录中，因为它们用于证明测试环境，不用于运行时分派。

### 3.7 当前 v1 与未来拆分边界

当前仓库尚未提供独立的 Runtime Baseline Schema、Execution Recipe Schema 和 Certification Record Schema。因此，在正式 Spec 和 Schema 落地前：

- Runtime Baseline 继续由项目规范、Agent 安装器、构建元数据和 Profile 限制共同表达。
- Adapter Composition 继续存放于 `Compatibility Profile.composition`。
- Certification Record 继续通过 `Profile.evidence` 和 Spec 认证报告表达。
- 禁止擅自创建不受 Schema、Catalog Loader 和 CI 管理的第三套目录。

机器可读对象拆分由 `specs/018.3-兼容性数据模型与认证治理` 负责，并必须完整实现：

- Schema；
- Loader；
- Resolver 输入；
- API；
- 文档生成；
- v1 Profile 只作为清退审计对象，运行期直接拒绝；
- 漂移检查。

不得只创建 JSON 文件而不接入目录和验证链路。

## 4. 横向扩展决策树

任何“新增平台支持”需求必须先走以下决策树。

### 4.1 第一步：现有 Agent 能否运行

检查：

- 是否属于已有 OS Family；
- 是否满足最低 OS、Kernel 或 Runtime；
- 是否属于已构建 CPU Architecture；
- TLS、服务安装、权限和文件系统是否满足要求；
- 安装、启动、心跳、升级和回滚是否可工作。

如果不能运行，进入“新 Agent 产品线评审”，不得先写产品兼容分支。

### 4.2 第二步：能否声明现有 Capability

如果目标环境可由现有 Capability 完整描述，例如：

```text
systemd + root + SELinux + POSIX atomic filesystem
```

则进入零代码认证流程。

如果出现全新平台机制，例如 runit，则进入新平台 Adapter 流程。

### 4.3 第三步：现有 Adapter 能否唯一组合

Resolver 必须满足：

- 所有 required AdapterKind 都有唯一候选；
- Capability Requirement 满足；
- 无 forbidden 冲突；
- Action Schema Version 支持；
- 必需验证和回滚 Adapter 存在。

如果能唯一组合，不得新增重复 Adapter。

### 4.4 第四步：是否只是新的认证环境

如果执行组合不变，仅新增 Rocky Linux、AlmaLinux、Ubuntu、Debian、SUSE、Alpine 的某个版本，应当只新增或更新：

- fixture；
- Profile evidence；
- 真实认证记录；
- 支持等级；
- 自动生成目录。

### 4.5 第五步：是否需要新 Agent 产品线

只有同时满足以下一项或多项时，才允许提议新 Agent 产品线：

- 当前 Agent 二进制无法在目标系统运行；
- Runtime 或系统 API 与现有产品线根本不兼容；
- 保持单一产品线会迫使大量核心代码出现平台特殊情况；
- 安全和 TLS 基线无法在现有产品线中保持；
- 升级、服务安装或恢复模型完全不同，无法由独立平台 Adapter 吸收。

新产品线必须经过架构评审，明确：

- 生命周期和维护期限；
- 支持范围；
- 不支持范围；
- 与现有产品线共享的控制面协议；
- 构建、签名、升级、回滚和认证成本；
- 为什么不能用一个独立 Adapter 解决。

## 5. 四类标准扩展场景

### 5.1 场景 A：新增普通 Linux 发行版

示例：Rocky Linux 9、AlmaLinux 9、Ubuntu 26.04。

如果满足现有 Linux Runtime Baseline，并提供现有 Capability：

```text
linux.systemd.v1
linux.privilege.root.v1 或 linux.privilege.sudo-noninteractive.v1
linux.filesystem.posix-atomic.v1
linux.security.selinux.v1 / apparmor.v1 / none.v1
```

标准变更范围：

1. 新增真实环境 Fact fixture。
2. 验证 Capability Snapshot。
3. 使用 Catalog Resolver 解析现有 Profile。
4. 运行产品闭环和失败恢复测试。
5. 增加 evidence 或认证报告。
6. 根据证据提升支持等级。
7. 重新生成兼容性目录。

正常情况下代码改动数量应为零。

禁止：

```go
if distro == "rocky" { ... }
if distro == "ubuntu" { ... }
```

禁止创建：

```text
linux-go-full-agent-rocky/
linux-go-full-agent-ubuntu/
rocky-nginx-handler.go
ubuntu-systemd-adapter.go
```

### 5.2 场景 B：新增平台机制

示例：新增 runit Service Controller。

标准流程：

1. 增加原始 Fact，例如 `initSystem=runit`。
2. 定义版本化 Capability，例如 `linux.runit.v1`。
3. 实现 `service-controller.runit`。
4. 注册 Adapter，不修改统一 Resolver。
5. 创建 Adapter Manifest，声明 consumes、produces、requirements 和冲突。
6. 增加重复注册、未知操作、失败关闭和确定性测试。
7. 增加能力 fixture。
8. 使用现有 Product Adapter 组合验证。
9. 完成真实环境认证。

Product Adapter 不得出现 runit 判断。

正确路径：

```text
Fact(init=runit)
    ↓
Capability(linux.runit.v1)
    ↓
Service Controller Registry
    ↓
service-controller.runit
```

### 5.3 场景 C：新增产品

示例：新增 Caddy 证书部署。

标准流程：

1. 定义产品 Action 输入、结果和错误语义。
2. 定义产品 Capability，例如 `caddy.cert.install`。
3. 实现唯一 `product.caddy` Product Adapter。
4. 复用 Certificate Store、Artifact Codec、Service Controller、Transport、Verifier 和 Rollback。
5. 注册 Product Handler 和 Adapter Manifest。
6. 增加发现、dry-run、备份、安装、验证、回滚和恢复测试。
7. 创建 experimental Profile。
8. 在代表平台组合认证。

禁止分别创建：

```text
UbuntuCaddyAdapter
RockyCaddyAdapter
WindowsCaddyAdapter
```

如果 Caddy 在 Windows 和 Linux 的产品语义一致，应当复用 `product.caddy`，仅组合不同的平台 Adapter。

### 5.4 场景 D：新增 Agent 产品线

示例：目标系统无法运行现有 Go 或 .NET Runtime。

标准流程：

1. 提交技术不可行证据，证明现有 Agent 无法运行或无法保持安全基线。
2. 证明独立 Adapter 无法解决。
3. 明确新产品线支持范围和终止条件。
4. 共享 Action Contract、Capability Snapshot、Result、Error Code、Recovery Ledger 和审计语义。
5. 独立实现构建、签名、安装、升级和回滚。
6. 创建 Runtime Baseline、Profile 和真实认证计划。
7. 完成架构、安全和运维成本评审。

不得为了少量命令差异创建新 Agent 产品线。

## 6. 各层职责和禁止事项

### 6.1 Agent Core

职责：

- 注册；
- 心跳；
- Capability 上报；
- 任务轮询；
- Direct Control；
- Action 生命周期；
- 结果暂存与重放；
- 超时、取消和恢复协调；
- 日志与审计。

禁止：

- 识别 IIS、Nginx、Apache、Tomcat 等产品；
- 按发行版选择命令；
- 按产品版本选择 Handler；
- 内置默认 Adapter。

### 6.2 Fact Collector

职责：

- 采集可验证事实；
- 输出证据、时间和错误；
- 保留 unknown。

禁止：

- 直接选择 Adapter；
- 根据发行版名称推断所有能力；
- 将采集失败写为 false。

### 6.3 Capability Mapper

职责：

- 把 Fact 转换为稳定 Capability；
- 维护版本和证据；
- 计算置信度。

禁止：

- 输出发行版专用 Capability；
- 无证据声明能力；
- 自动提升支持等级。

### 6.4 Product Adapter

职责：

- 产品领域发现；
- 产品配置语义；
- 产品操作顺序；
- 生成 Typed Operation；
- 定义产品错误和恢复边界。

禁止：

- 识别发行版；
- 直接调用 systemd、SCM、sudo、SSH 或 CURL；
- 根据 OS 生成命令；
- 重复实现平台文件原子替换。

### 6.5 Platform Adapter

职责：

- 文件系统；
- 服务控制；
- 权限提升；
- 安全模块；
- 系统证书存储；
- 平台命令执行。

禁止：

- 理解产品业务；
- 返回伪成功；
- 静默回退到未声明命令。

### 6.6 Transport / Executor

职责：

- 本地执行；
- SSH、CURL、Gateway 等传输；
- SecretRef 解析边界；
- 超时和返回值采集。

禁止：

- 重新解释产品语义；
- 在 Executor 中维护产品兼容矩阵；
- 把远程平台名称转换为硬编码命令。

### 6.7 Compatibility Catalog

职责：

- 加载 Manifest 和 Profile；
- 校验 Schema；
- 解析唯一 Adapter Composition；
- 输出支持等级、限制和证据；
- 生成 API、前端数据和文档。

禁止：

- 维护第二套人工矩阵；
- 用数组顺序决定适配器；
- 自动选择多个同级候选之一；
- 在前端重新推断兼容性。

## 7. 文件和目录规范

### 7.1 当前正式目录

```text
compatibility/
├── runtime-baselines/
├── execution-recipes/
├── certifications/
│   ├── linux/
│   └── windows/
├── adapters/
│   ├── product/
│   ├── certificate-store/
│   ├── artifact-codec/
│   ├── service-controller/
│   ├── transport/
│   ├── verifier/
│   └── rollback/
├── fixtures/
│   ├── contracts/
│   ├── linux/
│   └── windows/
├── profiles/
│   ├── linux/
│   └── windows/
└── schemas/
```

规则：

- Adapter Manifest 只能进入对应 AdapterKind 目录。
- Runtime Baseline、Execution Recipe 和 Certification Record 必须通过稳定 ID 引用，不得复制到 Profile。
- 已发布 Certification Record 不可修改或删除；复测必须新增记录。
- Profile 按 OS Family 组织，不按单个产品版本创建目录树。
- fixture 是事实和测试输入，不是运行时分派表。
- 不得新增第二套兼容性矩阵目录。
- 不得新增未接入 Schema 和 Catalog Loader 的兼容性 JSON 目录。

### 7.2 Agent 代码目录

Agent 至少保持以下边界：

```text
internal/core/                 控制面和任务生命周期
internal/handlers/             产品 Handler
internal/platform/             平台 Adapter
internal/compatibility/        公共合同和解析接线
```

成熟实现可以先在同包专用文件中完成零行为迁移，但不得长期把控制面、产品和平台实现重新堆回 `main.go`。

### 7.3 文档与认证证据

- 项目级强制规则放在 `docs/项目规范/`。
- Spec 专属认证计划和报告放在对应 `specs/<spec>/docs/`。
- 自动生成兼容性文档放在 `docs/兼容性/`。
- 运行期用户导入数据不得放入项目规范或 Spec 目录。

## 8. 命名与版本规范

### 8.1 Capability Key

格式：

```text
{domain}.{capability}[.{variant}].v{major}
```

示例：

```text
linux.systemd.v1
linux.filesystem.posix-atomic.v1
linux.privilege.sudo-noninteractive.v1
```

破坏性语义变化必须提升 major，不能原地改变旧 Capability 含义。

### 8.2 Adapter ID

格式：

```text
{adapter-kind}.{stable-name}
```

示例：

```text
product.nginx
service-controller.systemd
certificate-store.posix-filesystem
```

Adapter Manifest 的 `version` 独立演进；稳定 Adapter ID 不应包含发行版和普通产品版本。

### 8.3 Profile ID

Profile ID 应描述能力组合或正式发布范围，不应枚举所有发行版名称。

推荐：

```text
linux-systemd-nginx
linux-openrc-nginx
windows-modern-iis
windows-compatibility-iis
```

不推荐：

```text
ubuntu-24-nginx
rocky-9-nginx
debian-12-nginx
```

如果多个发行版使用相同能力组合，应复用 Profile，通过 evidence 区分认证环境。

### 8.4 Action 和 Schema Version

- 新行为通过 Action Schema Version 演进。
- 旧 Action 只进入删除/作废审计台账；运行期不得通过 Alias 映射或字符串猜测执行。
- 未知 major 必须失败。
- 不得在 Handler 内根据 payload 猜版本。

## 9. 支持等级与证据门禁

支持等级固定为：

```text
experimental
compatible
supported
certified
legacy
unsupported
```

### 9.1 experimental

至少满足：

- Schema 有效；
- Adapter 已注册；
- 单元和合同测试通过；
- 有 fixture 或构建证据；
- 未完成真实环境闭环。

### 9.2 compatible

至少满足：

- 能力组合和 Adapter Resolution 完整；
- 代表 fixture 通过；
- Operation Plan、失败关闭和恢复合同通过；
- 真实环境覆盖有限或目标环境未直接认证。

### 9.3 supported

至少满足：

- 代表真实环境完成安装、发现、部署、验证和回滚；
- 主要失败场景通过；
- 限制和运维文档完整；
- 证据未过期。

### 9.4 certified

至少满足：

- 固定 OS、架构、产品版本、证书格式和执行通道；
- 完整成功路径；
- 配置失败、刷新失败、TLS 失败、权限失败；
- 超时、取消、重试、崩溃和中断恢复；
- 安装、升级、降级边界和自动回滚；
- 安全模块 enforcing 场景；
- 安全评审通过；
- 证据未过期。

### 9.5 legacy

- 仅受限能力、Gateway、脚本包或人工辅助；
- 必须显式审批；
- 不得宣传为全自动正式支持。

### 9.6 unsupported

- 不生成 Agent 自动安装和部署计划；
- 不允许普通审批绕过；
- 可以保留资产、监控和迁移建议。

Windows Server 2003、2003 R2 和 2008 非 R2 固定为 `unsupported`。

### 9.7 证据过期与降级

- failed 或 expired evidence 不得继续支撑 certified/supported。
- Catalog 必须保留 declaredStatus 和 effectiveStatus。
- 降级必须有稳定原因码。
- 恢复支持等级必须增加新证据，不能修改历史证据伪造有效期。

## 10. 标准实施流程

### 10.1 需求登记

兼容性需求必须明确：

- 目标 OS 和版本；
- Agent 产品线；
- CPU Architecture；
- 产品和版本；
- 证书格式；
- init/service model；
- 权限模式；
- 安全模块；
- 执行通道；
- 期望支持等级。

### 10.2 基线判断

回答：

1. 现有 Agent 能否运行？
2. 是否满足 Runtime Baseline？
3. 能否声明现有 Capability？
4. 能否唯一解析现有 Adapter？
5. 是否只是新增认证环境？

### 10.3 最小变更选择

按以下优先级选择：

1. 只新增认证证据。
2. 只新增 fixture 和 Profile evidence。
3. 新增 Capability Mapper。
4. 新增一个独立平台 Adapter。
5. 新增一个 Product Adapter。
6. 最后才评估新 Agent 产品线。

不得跳过前面的简单方案直接建立新产品线或复制产品实现。

### 10.4 实现

实现时必须：

- 静态注册 Handler、Collector 和 Adapter；
- 重复注册失败；
- 未知类型失败；
- 相同输入解析结果确定；
- 不增加发行版或产品版本分派；
- 不改变旧 Alias 和协议；
- 写入恢复账本；
- 对必要操作执行验证和回滚。

### 10.5 验证

从小到大运行：

1. 新 Collector/Adapter/Handler 单元测试。
2. Registry 和 Resolver 合同测试。
3. 产品成功、失败和恢复测试。
4. Agent 全量测试。
5. Agent 构建。
6. 包装、安装、升级和回滚测试。
7. 兼容性架构守卫。
8. Compatibility Catalog 测试。
9. 文档生成和漂移检查。
10. 真实环境认证。

### 10.6 发布

发布前必须：

- 更新 Manifest/Profile/evidence；
- 生成兼容性目录；
- 确认支持等级；
- 记录 Agent revision、SHA-256 和签名；
- 明确 `vcs.modified` 状态；
- 发布限制和不支持范围；
- 设置证据过期时间；
- 完成回滚方案。

## 11. 测试矩阵

### 11.1 Agent Runtime

- 安装前置检查；
- 不支持 OS/Kernel/Architecture 拒绝；
- 服务安装和启动；
- 注册、心跳、任务轮询；
- Direct Control；
- 离线结果重放；
- 升级；
- 坏版本自动回滚；
- major 降级边界；
- 断电恢复；
- 签名和篡改拒绝。

### 11.2 Capability

- Fact 正常采集；
- 采集失败保留 unknown；
- 超时；
- 部分失败；
- 重复注册；
- 确定性顺序；
- 证据和置信度；
- 过期处理。

### 11.3 Adapter

- 正常解析；
- 缺失；
- 冲突；
- 歧义；
- 重复注册；
- 未知操作；
- Action Schema Version 不支持；
- 相同输入在不同注册顺序下结果一致。

### 11.4 产品闭环

每个产品至少验证：

```text
discover
→ dry-run
→ backup
→ install
→ validate
→ reload/restart
→ verify
→ complete
```

失败场景至少验证：

- payload 无效；
- 证书或私钥无效；
- 证书与私钥不匹配；
- 权限不足；
- 磁盘空间不足；
- 原子替换失败；
- 安全上下文恢复失败；
- 配置校验失败；
- 服务重载或重启失败；
- TLS 指纹或主机名验证失败；
- context cancel；
- deadline exceeded；
- Agent 中断后的启动恢复；
- 恢复本身失败。

### 11.5 真实环境代表组合

Linux 首批至少覆盖：

- systemd + AppArmor + amd64；
- systemd + SELinux enforcing + arm64；
- OpenRC + root；
- SysV + sudo non-interactive；
- 真实 Nginx；
- 真实 Apache；
- 真实 Tomcat/JDK；
- PEM、PKCS12、JKS。

Windows 首批至少覆盖：

- Windows Server 2008 R2 SP1 + IIS 7.5 + Compatibility Agent；
- Windows Server 2012 / 2012 R2 + Compatibility Agent；
- Windows Server 2016+ + Modern Agent；
- 安装、升级、部署失败、回滚、重试和恢复。

## 12. CI 和架构守卫

CI 必须阻止以下新增内容：

- OS/发行版/产品版本 `if/else` 或 `switch` 分派；
- Agent 主循环中的产品分派；
- Provider 中按 OS 生成命令；
- Resolver 中按 Agent 产品线硬编码选择 Adapter；
- 发行版专用 Agent 工程；
- 发行版专用 Product Handler；
- 未登记 AdapterKind；
- 未受 Schema 管理的兼容性 JSON；
- 没有 evidence 的非 unsupported Profile；
- 前端硬编码兼容性矩阵；
- 自动选择歧义 Adapter；
- 修改历史认证证据覆盖失败记录。

架构守卫允许登记历史债务，但必须满足：

- 每个债务有稳定指纹；
- 每个债务有迁移目标；
- 新增同类副本仍然失败；
- 不得通过扩充允许列表绕过新代码评审；
- 债务数量只能下降，不能无解释上升。

## 13. 代码评审检查清单

评审任何平台扩展时必须回答：

### 数据结构

- 核心新增数据是 Fact、Capability、Manifest、Profile 还是 evidence？
- 是否创建了重复的兼容性来源？
- 是否把认证环境错误地当成运行时条件？

### 特殊情况

- 是否新增 OS、发行版或产品版本条件分支？
- 是否能通过 Capability 和 Registry 消除？
- 是否复制了已有 Profile 或 Product Handler？

### 复杂度

- 新增普通发行版为什么需要代码？
- 新增平台机制是否只增加一个独立 Adapter？
- 是否修改了不应感知产品的平台 Core？

### 破坏性

- 未发布插件重构中的旧 Action Alias 是否已经清退？
- 错误码、结果和恢复语义是否保持？
- 是否影响 SSH/CURL、Gateway 或其他产品？
- 是否更新并构建受影响 Agent？

### 实用性

- 是否有真实目标环境？
- 是否有明确支持等级？
- 是否有证据和过期时间？
- 方案复杂度是否与实际平台差异匹配？

## 15. 三种最终交付结果

每项平台扩展最终只能归入以下结果之一。

### 15.1 零代码认证扩展

适用条件：

- Agent 可以运行；
- 已有 Capability 足够；
- 已有 Adapter 可唯一组合。

交付：fixture、evidence、认证报告、Profile 状态和生成目录。

### 15.2 新平台能力扩展

适用条件：

- Agent 可以运行；
- 出现新的独立平台机制；
- 产品语义不变。

交付：Fact、Capability、单一平台 Adapter、Manifest、测试、Profile 和认证。

### 15.3 新产品或新 Agent 产品线

适用条件：

- 新产品语义无法由现有 Product Adapter 表达；或
- 现有 Agent 无法运行且独立 Adapter 无法解决。

交付：版本化合同、Handler/Adapter、构建发布链路、Profile、认证和迁移策略。

## 16. 当前项目的直接执行结论

### 16.1 新增大多数 Linux 发行版

默认采用零代码认证扩展：

- 不新增 Linux Agent 产品线；
- 不新增发行版条件判断；
- 不复制 Nginx、Apache、Tomcat Handler；
- 复用 systemd/SysV/OpenRC、Privilege、Filesystem 和 Security Module Adapter；
- 通过真实环境证据提升支持等级。

### 16.2 新增 Windows Server 版本

- Windows Server 2008 R2 SP1、2012、2012 R2 使用 Compatibility Agent。
- Windows Server 2016 及以上使用 Modern Agent。
- Windows Server 2003、2003 R2、2008 非 R2 固定 unsupported。
- 不得在 Modern Agent 中加入旧 Windows 版本分派。

### 16.3 新增产品

- 每个产品只维护一个稳定 Product Adapter 语义。
- 平台差异通过 Adapter Composition 解决。
- SSH/CURL/Gateway 是 Transport 或 Workflow 执行通道，不形成第二套产品实现。

### 16.4 下一阶段架构演进

Runtime Baseline、Execution Recipe、Certification Record 和引用式 Compatibility Profile 的机器可读治理由现行 `specs/004.3-内置产品插件、兼容目录与旧Provider退役治理` 推进。该 Spec 负责最终数据模型、旧对象清退和最新目录生成；运行期不得读取 v1 Profile 或建立 Alias/转换层，Agent Core 继续只实现通用事实和安全原语。
