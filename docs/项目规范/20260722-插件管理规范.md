# GCAC 插件管理规范

## 1. 插件定义

GCAC 插件当前指一个可被工作流系统加载的 DSL 文件模板，不是独立的 npm 包，也不是另一套数据库实体。

插件文件只有两个正式来源：

- 内置插件：`backend/src/modules/workflow-templates/builtin-workflows`，随系统代码发布并受 Git 跟踪。
- 用户插件：`data/workflows`，由运行期或管理员导入和维护。

## 2. 插件身份

插件身份由 DSL 的 `metadata.name` 决定，必须满足以下要求：

- 使用稳定、唯一、全小写的英文标识和短横线命名。
- 发布后不能因为显示名称、Logo、平台或执行方式变化而修改。
- `metadata.displayName` 只用于界面展示，不作为关联主键。

## 3. 插件元数据

推荐的插件元数据如下：

| 字段 | 必填 | 说明 |
| --- | --- | --- |
| `name` | 是 | 稳定插件 ID |
| `displayName` | 否 | 面向用户的名称 |
| `description` | 否 | 插件能力和适用场景说明 |
| `version` | 新插件必填 | SemVer 插件版本，例如 `1.1.0` |
| `logoUrl` | 否 | HTTP(S) URL 或本地 Web 路径 |
| `platforms` | 推荐 | 目标平台或设备标识，例如 `linux`、`windows`、`synology-dsm` |
| `updateMethods` | 推荐 | 更新通道：`ssh`、`curl`，混合模板可同时声明 |
| `maintainer` | 推荐 | 维护团队或责任人 |
| `homepage` | 否 | 文档、发布记录或维护入口 |
| `category` | 否 | 市场分类 |
| `tags` | 否 | 搜索和能力标签 |

示例：

```json
{
  "metadata": {
    "name": "apache-8444-cert-switch",
    "displayName": "SSH更新Apache站点证书",
    "description": "通过 SSH 更新 Apache 证书文件并验证 HTTPS 服务。",
    "version": "1.1.2",
    "logoUrl": "/plugin-logos/apache-wordmark.svg",
    "platforms": ["linux"],
    "updateMethods": ["ssh"],
    "maintainer": "GCAC",
    "category": "certificate",
    "tags": ["apache", "linux", "ssl"]
  }
}
```

## 4. 版本规则

- 新插件从 `1.0.0` 开始；预发布版本必须使用合法 SemVer，例如 `1.0.0-beta.1`。
- 修复错误或不改变输入输出契约的调整递进 patch。
- 增加兼容能力、平台或可选步骤递进 minor。
- 改变变量契约、执行语义、必需凭据或回滚行为递进 major。
- 修改 DSL 内容、Logo、版本说明、平台、更新方式或标签，都必须递进版本。
- 原版本文件不可覆盖后继续使用旧版本号。
- 数据库 `WorkflowTemplateVersion.version` 是工作流编辑历史的整数版本，与插件的 SemVer 不同。

## 5. 平台与执行方式

`platforms` 和 `updateMethods` 是声明字段，不是权限放行字段：

- `platforms` 描述插件经过验证的目标平台，不应使用 `all` 隐藏未验证范围。
- `updateMethods` 必须与实际 DSL step 一致；SSH/SFTP/SCP 声明 `ssh`，HTTP/CURL 声明 `curl`，混合流程同时声明。
- 后端仍需在执行前检查资产能力、凭据类型、连接参数和目标平台，不得仅凭插件元数据执行。

## 6. 更新与发布

- 内置插件通过代码评审、Schema 校验、执行计划预览、回滚检查和平台试跑后随版本发布。
- 用户插件更新保存到 `data/workflows`，建议在外部版本库保留历史文件和变更说明。
- 插件更新不会自动修改已经创建的工作流。
- 用户必须显式执行“套用模板”，系统才会为已有工作流创建新的 draft version。
- 从插件新建工作流后，工作流保留插件的稳定 `metadata.name`，插件市场据此显示“正在使用”。

## 7. 安全要求

- 禁止在插件 DSL 中写入明文密码、Token、私钥或生产凭据。
- Logo 和 homepage 只用于展示，不能参与执行、签名或权限判定。
- 本地 Logo 只能使用浏览器可访问的 Web 路径，禁止 `file://`、`data:` 和包含 `..` 的越界路径。
- 插件失败时必须保留结构化校验错误，不能伪装成可用插件。
- 使用第三方品牌 Logo 时必须遵守品牌方的商标与使用指南。Synology Logo 的商标归 Synology Inc. 所有，不表示 Synology 对 GCAC 或该插件提供赞助、认可或背书。

## 8. 后续扩展边界

当前使用 `metadata.name` 关联插件与新建工作流，足够满足单一稳定 ID 的场景。

如果未来允许插件别名、分支发布或一个插件生成多个工作流，应新增数据库字段：

- `sourcePluginId`
- `sourcePluginVersion`
- `sourcePluginHash`

届时不能继续依赖工作流名称猜测插件来源。
