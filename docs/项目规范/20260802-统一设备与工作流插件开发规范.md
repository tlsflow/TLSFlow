## 2. 插件模型

Manifest 使用 `gcac.plugin-manifest/v1`，必须独立声明：

- `executionLocation`：`CONTROL_PLANE`、`AGENT`、`AGENT_SIDE_PLUGIN` 或 `PLUGIN_RUNNER`；代码型能力统一在同 Docker 的独立 Plugin Runner 进程中运行。
- `source`：`BUILTIN` 或 `USER`。
- `scope`：`MANAGED`、`STANDALONE` 或 `BOTH`。
- `trust`：`OFFICIAL_SIGNED`、`USER_SIGNED` 或 `UNSIGNED`。
- `support`：`OFFICIAL`、`COMMUNITY` 或 `SELF_MANAGED`。
- capabilities、permissions、compatibility、resources。

插件身份只能由 `CapabilityAssignment -> PluginBinding -> PluginVersion` 解析。禁止根据设备所有者、Agent 是否存在、厂商名称、产品名称、Framework Type、DeviceFamily 或 DriverKind 选择插件实现。

### 2.1 版本不可变

- 同一 `pluginId + version` 的 Manifest、资源或包哈希变化必须拒绝。
- 修改已导入版本必须递增插件版本。
- 内置插件重复安装必须幂等；内容冲突必须失败关闭。
- 退休版本可以查询历史，但不能创建新 Binding。
- 内置 Workflow DSL 只允许位于 `backend/src/modules/workflow-templates/builtin-workflows`；用户导入只允许位于 `data/workflows`。

### 2.2 版本事实、启动降级和运维边界

GCAC 必须区分以下三种版本，任何接口、日志、脚本和文档都不得把它们当成同一个字段：

| 版本 | 来源 | 作用 |
| --- | --- | --- |
| Manifest 插件版本 | 包内 `manifest.json.version`，使用 SemVer | 内置插件版本唯一事实源，标识不可变发布包 |
| Workflow DSL 版本 | DSL `metadata.version`，使用 SemVer | 标识插件内置 Workflow 内容自身的语义版本，独立于插件版本 |
| 数据库 Workflow 版本 | `WorkflowTemplateVersion.version`，使用递增整数 | 标识数据库中同一工作流的编辑/发布历史 |

- 同一 `pluginId + Manifest version` 不得覆盖；Manifest、资源或包哈希发生变化时，必须创建新的插件版本。
- 同一插件资源的 DSL `metadata.version` 不得因运行时导入而隐式递增，也不得由插件版本脚本改写。包内容变化必须先递进 Manifest 插件版本；Workflow 内容变化是否递进其自身 SemVer 由工作流维护者决定。
- 内置插件版本更新必须使用 `scripts/plugins/update-plugin-version.mjs`，脚本校验 SemVer、Manifest 与全部资源映射、版本不可变规则后只更新 Manifest 顶层版本，并同步 Catalog 摘要。Catalog 固定为 `scripts/architecture/p2-plugin-release-manifest.json`，只记录发布策略、最终包 SHA-256、Host API 授权和所有权；不得手工修改运行时数据库或直接改 Catalog 来“修复”版本。
- 插件版本查询必须返回全部当前租户可见版本、状态、哈希、Workflow 绑定和运行引用统计；最高版本只能表示排序结果，不能被推断为当前运行版本。
- 插件版本切换必须由管理员显式发起，并在同一数据库事务中更新所有运行引用：`unified_plugin_bindings`、`plugin_capability_assignments`、`pg_hosts.management_channels`、`pg_service_assets.metadata` 和 `pg_device_assets.plugin_version_id`。切换失败必须整体回滚。
- 版本切换不得修改历史 `PluginVersion`、插件包或 DSL 内容，不得自动改写用户派生 Workflow；用户工作流升级必须通过显式套用产生新的不可变版本。
- 内置插件导入、权限审批、启用和 Workflow 发布按插件逐项处理。包扫描、Manifest/摘要校验或同一 `pluginId@version` 摘要冲突必须失败关闭启动或热刷新；已注册包的 Workflow 发布等后处理问题可以记录结构化 `warning`，至少包含 `phase`、`pluginId`、`version`、`errorCode` 和错误信息。数据库连接、应用构造和路由注册错误仍必须阻塞启动。历史引用直接删除或作废并记录审计，运行时不做兼容转换。

### 2.3 版本注册表和运行期热刷新

- 内置包仓库版本事实只允许包内 `manifest.json.version`；统一 Registry 在启动和热刷新时扫描包，不能建立第二份版本 Ledger。发布 Catalog 只保存发布策略、摘要、Host API 授权和所有权。数据库中的 `unified_plugin_versions`、`unified_plugin_resources` 和 Plugin Workflow Binding 是从包扫描派生的不可变运行记录；Catalog、数据库和 Binding 都不得反向改写 Manifest。
- 插件市场目录必须使用当前租户可见版本集合，即租户版本与系统内置版本的并集，并按 SemVer 展示最高可用版本。不得只查询租户历史副本，否则会遮蔽新的系统内置版本。
- `POST /api/v1/plugin-catalog/refresh-builtins` 只用于通过统一 Registry 扫描并导入不可变插件包、派生发布资源，不读取或升级旧运行引用；最新运行引用只能由当前 Manifest 显式创建。
- “刷新市场”必须先调用内置插件导入接口，再重新查询插件目录；更新内置插件文件后必须按不可变 PluginVersion 发布流程注册。
- 导入只注册并启用新的不可变版本，不自动把旧 Binding、Capability Assignment、Host、ServiceAsset 或 DeviceAsset 映射到新版本；旧引用直接删除或作废，新引用只能由当前 Manifest/PluginVersion/Capability 显式创建，不提供运行期旧版本回退。
- 当前运行版本必须由实际运行引用推断；插件市场显示的最高版本表示“最新可用版本”，不能替代版本管理接口中的当前运行版本。

## 3. 四种设备和目标模式

| 模式 | 合法对象 | 执行来源 | 禁止事项 |
| --- | --- | --- | --- |
| 无 Agent DeviceAsset | DeviceAsset、标准发现投影、无代理连接 | 设备/目标事实或 Workflow | 不虚构 Agent，不创建无依据的 PluginBinding |
| ManagedTarget + Plugin | ApplicationAsset、ManagedTarget、活动 Plugin Assignment | `CapabilityAssignment + PluginBinding` | 不同时保留冲突 WorkflowExecutionBinding |
| ManagedTarget + Workflow Override | ManagedTarget、活动 WorkflowExecutionBinding | 用户明确选择的 Workflow | 必须停用冲突的应用级 ACTIVE Plugin Assignment |
| Standalone + Workflow | ApplicationAsset、WorkflowExecutionBinding、无活动 Target | Workflow | 新目标不得创建 Standalone PluginBinding 或 CapabilityAssignment |

新的 Standalone 归集必须使用 `ApplicationAsset + WorkflowExecutionBinding`。当前 `plugin-promotion.service.ts` 仍按旧 Standalone PluginBinding 自动创建 Managed Binding，属于迁移缺口，不得作为新实现模板。

## 4. PluginBinding、Assignment 和输入

- Managed Binding 必须有 `managedContext.hostId`，可选 `managedTargetId`。
- ManagedContext 不保存 Agent ID、DeviceAsset ID、厂商类型或执行位置；这些由标准目标上下文实时解析。
- Standalone Workflow 不保存 ManagedContext。
- 普通变量、连接、凭据和 Artifact 使用统一 `InputBindingsV1`。
- Secret 只保存稳定 `credentialId` 或 `secret://` 引用，不保存明文。
- 证书材料只能通过 Artifact Slot 注入，不能写入普通变量、DSL 命令、日志或计划 JSON。
- 最终输入优先级为：单次执行覆盖 → 应用资产 Binding → Agent 发现资产字段 → 插件默认值。
- `source.kind=asset` 表示从 `DeploymentAssetContextV1` 结构化字段取值；资产字段存在时，插件默认值不得覆盖它。
- `bindingPolicy=default_overridable` 只表示用户可显式覆盖默认值，不能把默认值当成已发现事实。

### 4.1 插件部署输入与通用表单

- 插件的普通变量、连接、凭据和 Artifact 必须通过 `DeploymentInputContractV1` 声明；宿主只按契约投影和渲染，不得按变量名、厂商、产品、资产类型或工作流名称增加业务分支。
- 面向用户可编辑的部署输入必须提供 `descriptionKey`，并在 `ui` 中提供 `labelKey`、`group`、`order` 和 `helpKey`。这些字段是表单契约的一部分，不得依赖宿主回退显示变量名。
- 新建应用资产时，宿主通过草稿应用资产上下文生成部署输入投影；插件不得要求先持久化应用资产才能填写自己的输入。
- `allowInsecureTls` 是普通的 `boolean` Binding 输入，不是设备 `tlsVerify` 的别名，也不是宿主根据设备配置自动生成的默认值。需要 TLS 例外的插件必须显式声明：

```json
{
  "allowInsecureTls": {
    "type": "boolean",
    "required": true,
    "configurationMode": "required",
    "source": { "kind": "binding" },
    "lifecycle": "pre_execution",
    "bindingPolicy": "required_binding",
    "descriptionKey": "deploymentInputs.allowInsecureTls.description",
    "ui": {
      "labelKey": "deploymentInputs.allowInsecureTls.label",
      "group": "security",
      "order": 10,
      "helpKey": "deploymentInputs.allowInsecureTls.help"
    }
  }
}
```

### 4.2 应用资产接入配方与新建设备入口

应用资产接入配方是插件资源，唯一资源入口为 Manifest 的 `resources.onboarding.applicationAsset`，通常指向 `onboarding/application-asset.json`。配方固定使用 `gcac.application-onboarding/v1`；宿主只读取已启用的固定 `PluginVersion`，并把 `pluginVersionId + recipeHash` 固定到接入会话。前端、API 请求和运行数据库都不得传入资源路径或临时配方内容。

当配方的 `deviceSelection` 为 `EXISTING_OR_NEW` 时，插件可用 `newDeviceOnboarding` 声明统一设备向导的预选入口：

```json
{ "kind": "AGENT_INSTALL", "platformKey": "linux" }
```

或：

```json
{ "kind": "PLUGIN_MANAGED", "pluginId": "device.citrix.netscaler-adc" }
```

- `AGENT_INSTALL.platformKey` 必须使用设备平台注册表中的稳定键。统一设备向导在打开时解析该键；无法解析时必须失败关闭，不得退回空白平台选择。向导只生成对应平台的 Agent 安装流程；在 Agent 实际注册、健康检查和发现事实可用前，不得把它伪装成可选设备。
- `PLUGIN_MANAGED.pluginId` 必须是已启用设备插件的稳定标识。向导必须加载该插件当前可用版本的 `forms.device`，由设备插件完成凭据收集、连接测试和设备创建。
- `EXISTING_ONLY` 与 `NONE` 配方禁止声明 `newDeviceOnboarding`。为兼容历史版本，未声明该字段的 `EXISTING_OR_NEW` 配方只允许选择已有设备，前端不得显示一个会打开空白设备向导的“新增设备”选项。
- `PLUGIN_MANAGED` 的设备表单引用必须是 Manifest `resources.forms` 中声明的真实资源路径，例如 `forms/device.json`；禁止写逻辑别名、内嵌表单或宿主专属字段。
- 宿主只转发声明，不得按 IIS、Apache、NGINX、Tomcat、Citrix、Synology 或其他厂商/产品名称分支。新增平台需要改变入口时，修改插件配方并递进 Manifest 版本。

设备插件成功创建设备后，宿主关闭设备向导、恢复原接入会话并刷新兼容设备列表。Agent 安装流程只在用户完成安装并关闭向导后恢复列表；设备是否出现仍由实际注册和平台能力校验决定，不得写入虚假会话状态。

配方、表单、Manifest onboarding 资源或该字段任一变化都属于插件包内容变化，必须通过 `scripts/plugins/update-plugin-version.mjs` 递进 Manifest 版本并更新发布 Catalog 摘要，禁止修改运行数据库来绕过版本规则。

- `allowInsecureTls` 只表达用户对当前部署跳过 TLS 证书校验的明确意图，不产生网络执行授权；审批、输入快照、审计和 `ExecutionGrant` 仍由宿主统一处理。

## 5. Agent 证书位置和标准发现

Agent 插件必须通过资源声明发现映射，使用标准 `gcac.device-discovery/v2` 和 `gcac.agent-discovery-mapping/v1`。宿主不按 NGINX、Apache、Tomcat、IIS 或其他产品名称分派。

### 5.1 证书位置

- 依赖当前服务配置的证书路径、KeyStore、服务名或程序路径时，变量必须引用 `source.kind=asset` 的正式 `target.certificateLocation.*` 字段。
- 精确发现得到的路径、端口、服务和指纹优先于插件默认值。
- 历史默认路径不得作为运行期兼容兜底；目标事实缺失时必须阻断计划或要求人工补齐，不得猜测产品路径。
- 发现必须同时处理 `notBefore`、`notAfter` 和尽可能真实的 `sha256Fingerprint`。
- `configFingerprint` 必须进入证书位置和输入快照；Agent Atomic 计划可通过 `preflight.assert.expectedSha256` 在执行前重新读取并比对，指纹不一致必须失败关闭。
- 可选材料或可选刷新方式必须使用结构化 `whenVariablePresent` 条件；条件为空时，计划编译器和 Agent 宿主都必须跳过该操作，不得把空路径送入权限校验或文件系统。
- 手工目标的 TLS 验证必须使用 `certificate.verify/v1` 结构传递 `connectHost`、`serverName` 和 `port`，不得退化为命令字符串或自由文本。
- Agent 只返回进程、服务、端口、文件、权限和摘要等原始本机事实。Windows NGINX、Apache、Tomcat 的配置解析和框架识别由对应控制面插件完成；Agent Core 不解析 `server`、`VirtualHost`、`Connector` 等产品语法。

### 5.2 稳定键和容错

- 所有对象和父子引用使用插件声明的稳定键。
- 含中文、空格或协议特殊字符的名称必须生成确定性编码键，原始值只用于展示。
- 集合字段始终输出数组，零项和单项不能折叠成对象。
- 只读发现可以使用 `foreach.continueOnError` 保留部分失败；部署、变更和回滚禁止使用该容错。
- 只读发现 warning 必须使用稳定 `code`，并保留来源 Capability 和受影响路径；warning 不能包含私钥、KeyStore 密码或其他 Secret。
- 每个 foreach 子项必须有独立执行身份和幂等键。

## 6. Workflow DSL 与 Trusted JS 插件

- Agent Plan 和代码型插件不能转换成用户工作流。插件提供的标准 Capability 或声明式 Workflow 才能作为用户工作流复制来源；`credential.acquire` 不是用户工作流复制来源。
- 插件内部工作流标记为 `plugin_internal`、只读、归插件版本所有。
- 用户复制出的工作流仍标记为 `user`、归用户所有，并在 WorkflowVersion 上保存可选 `pluginSource` 来源证据。
- 发布时使用规范化 DSL 内容计算 SHA-256；同一插件资源哈希不变则复用已发布版本，插件任一资源变化都必须递进 Manifest 插件版本，Workflow `metadata.version` 仍由工作流内容独立维护。
- 正式 DSL 仍只能来源于内置模板目录或用户导入目录，禁止新增第三套样例目录。
- 需要厂商 SDK、签名请求、异步轮询、检查点恢复或复杂发现/部署/回滚编排时，应使用带代码入口的官方 PluginVersion，通过独立 Plugin Runner 和受控 Host API 执行，而不是把厂商逻辑固化在宿主分支中。

### 6.1 `credential.acquire` 插件能力

`credential.acquire` 与 `certificate.deploy`、`certificate.rollback` 平级，是插件为特定资产提供的浏览器临时凭据获取能力。能力合同固定使用：

```json
{
  "key": "credential.acquire",
  "contractVersion": "1.0",
  "actionContractId": "credential.acquire.v1",
  "riskLevel": "HIGH",
  "executionLocations": ["CONTROL_PLANE"]
}
```

插件必须同时声明：

- 独立的 `WorkflowVersion`，不得与 deploy/rollback 工作流共享；其 DSL `metadata.version` 独立维护；
- 登录入口、允许 Origin、浏览器运行时限制等输入合同；
- `CredentialOutputContract`，明确参数名、敏感类型、必填性和 delivery；
- 工作流所需的受限 Browser Session Broker 能力。

用户完成网页登录后，只有手动点击“获取凭据”才允许执行该工作流。工作流不得根据页面内容猜测 Token、Cookie 或 Header，不得接收客户端提交的秘密，不得序列化 Playwright `Browser`、`BrowserContext` 或 `Page` 对象。执行器只能使用短租期 `BrowserSessionHandle` 访问创建会话时的同一个 BrowserContext。

`credential.acquire` 的未声明敏感输出必须丢弃，不得进入 Secret、普通变量、日志、审计或 API 响应。验证通过后，只有输出合同允许的字段才能写入临时 `BROWSER_SESSION` 凭据。

`credential.acquire` 只在 `GCAC_DEPLOYMENT_ARCHITECTURE=standard` 时可执行。标准架构固定使用独立 Browser Runtime 专用容器，并在容器内为每个会话启动独立 Chromium/Xvfb/VNC 进程组；不得动态创建会话 OCI 容器，也不得让 GCAC Backend 或 Browser Runtime 挂载 Docker Socket。小型架构可以读取插件合同和历史记录，但不得装配或执行 Browser Runtime。

## 7. Runtime 和执行位置

执行位置只表达在哪里执行，不能决定使用哪个插件。宿主只按固定 `canonicalPluginId`、`pluginVersionId` 和 Capability 调用对应 Plugin Runner 或 Agent v2 合同，不再保留旧 Runtime 分派器。

宿主负责：

- 网络出口、Gateway、TLS 和连接；
- Secret Grant、Artifact Grant、执行锁和恢复账本；
- Schema 校验、表单、发现投影、审计、限流、熔断和指标；
- 计划快照、结果同步、验证和回滚。

- 声明式插件和 Agent Plan 插件不得执行任意代码；代码型插件只能通过同一 Docker 内独立 Plugin Runner 进程执行，并且必须通过签名、Policy Authority、Grant、Host API 和代码执行授权门禁。
- Plugin Runner 不是 OS 沙箱；生产仍必须依赖最小权限、资源限制、路径/服务白名单、审计和节点隔离策略。
- 所有 Runtime 的插件都不得直接访问数据库、Secret 存储、宿主任意文件系统路径或未声明的宿主内部服务。

## 8. 安全、发布和成熟度

- 声明式插件和 Agent Plan 插件不得进入代码执行态；代码型插件必须单独获得代码执行授权后才能装配和执行。
- 官方代码插件允许携带受控代码和 SDK 依赖，但不得携带宿主原生扩展、任意二进制执行文件或未登记的动态库。代码只能由独立 Plugin Runner 进程加载。
- 代码插件只允许 `OFFICIAL_SIGNED` 或明确受控签名级别进入装配候选；未签名、用户自签名或来源不明的插件不得执行。即使已装配，执行前仍必须通过代码执行授权门禁。
- 高风险权限、网络访问、设备写入、Secret 和 Artifact 必须声明并审批。
- 未启用、未审批、签名无效、版本冲突、资源校验失败或未知 Action 必须失败关闭。
- 用户插件发布者可信链和密码学验签当前尚未完成，状态为 `TODO`；不能以包加载成功代替验签。
- 真实部署、真实回滚、Gateway、产品版本和执行位置必须分别记录成熟度，不能合并成一个“支持”标签。
- Workflow DSL 中的 `allowInsecure: true` 只能在明确审批、审计、测试隔离和发布门禁下使用，不得作为普通默认值；对应的用户配置必须通过 `allowInsecureTls` Binding 输入表达。

## 9. 验证清单

发布前必须验证：

1. Manifest、资源路径、不可变版本和包哈希。
2. Runtime、Scope、Capability、Permission、签名等级和兼容性。
3. 四种设备/目标模式及来源冲突。
4. `source.kind=asset`、证书位置、精确发现和稳定键。
5. Secret/Artifact Grant、输入快照和 `configFingerprint` 状态。
6. Workflow DSL Schema、内容哈希、Provenance、checkpoint、foreach、assert 和 rollback。
7. `credential.acquire` 能力合同、独立 Workflow 资源与绑定、插件版本驱动的 DSL `metadata.version`、Browser Session Broker、同上下文验证和 `CredentialOutputContract`。
8. Plugin Runner Host API 门禁、SDK 依赖白名单、独立进程代码入口、Capability Token、Policy Authority、审计字段和恢复账本。
9. 真实部署/回滚、Gateway、外部厂商和多实例协调的证据状态。
10. 八语言资源或安全回退、前端 i18n、审计和脱敏。
11. Manifest 插件版本、Workflow DSL 版本和数据库 Workflow 整数版本未被混用。
12. 版本冲突不会阻塞后端启动；版本查询、显式切换和事务回滚均有自动化证据。
13. 应用接入配方必须覆盖 `AGENT_INSTALL` 与 `PLUGIN_MANAGED` 预选、未知字段拒绝、禁用设备选择模式拒绝、设备向导回跳和兼容设备刷新；真实厂商/Agent 验收仍按平台单独记录。
