## 2. 插件模型

Manifest 使用 `gcac.plugin-manifest/v1`，必须独立声明：

- `executionLocation`：`CONTROL_PLANE`、`AGENT`、`AGENT_SIDE_PLUGIN` 或 `PLUGIN_RUNNER`；`PLUGIN_RUNNER` 只表示 DSL `plugin.action` 的代码执行位置，不表示整份 Workflow 的执行器。
- `source`：`BUILTIN` 或 `USER`。
- `scope`：`MANAGED`、`STANDALONE` 或 `BOTH`。
- `trust`：`OFFICIAL_SIGNED`、`USER_SIGNED` 或 `UNSIGNED`。
- `support`：`OFFICIAL`、`COMMUNITY` 或 `SELF_MANAGED`。
- capabilities、permissions、compatibility、resources。

插件身份只能由 `CapabilityAssignment -> PluginBinding -> PluginVersion` 解析。禁止根据设备所有者、Agent 是否存在、厂商名称、产品名称、Framework Type、DeviceFamily 或 DriverKind 选择插件实现。

### 2.1 版本不可变

- 同一 `pluginId + version` 的 Manifest、资源或包哈希变化必须拒绝。
- 修改已导入版本必须递增插件版本。
- 内置插件重复安装必须幂等；内容冲突必须失败关闭。
- 退休版本可以查询历史，但不能创建新 Binding。
- 内置 Workflow DSL 只允许位于 `backend/src/modules/workflow-templates/builtin-workflows`；用户导入只允许位于 `data/workflows`。

### 2.2 版本事实、启动降级和运维边界

GCAC 必须区分以下三种版本，任何接口、日志、脚本和文档都不得把它们当成同一个字段：

| 版本 | 来源 | 作用 |
| --- | --- | --- |
| Manifest 插件版本 | 包内 `manifest.json.version`，使用 SemVer | 内置插件版本唯一事实源，标识不可变发布包 |
| Workflow DSL 版本 | DSL `metadata.version`，使用 SemVer | 必须与 Manifest 插件版本一致，标识本次插件包内 Workflow 快照 |
| 数据库 Workflow 版本 | `WorkflowTemplateVersion.version`，使用递增整数 | 标识数据库中同一工作流的编辑/发布历史 |

- 同一 `pluginId + Manifest version` 不得覆盖；Manifest、资源或包哈希发生变化时，必须创建新的插件版本。
- 同一插件资源的 DSL `metadata.version` 必须与 Manifest 插件版本一致。包内容变化必须先递进 Manifest 插件版本，并由版本脚本同步 Workflow 版本；插件包发布器和内置版本门禁拒绝不一致的版本组合。
- 内置插件版本更新必须使用 `scripts/plugins/update-plugin-version.mjs`，脚本校验 SemVer、Manifest 与全部资源映射、版本不可变规则后只更新 Manifest 顶层版本。Loader/Registry 会从实际包派生摘要；历史 P2 发布台账不再同步，也不得作为运行时或开发门禁。
- 插件版本查询必须返回全部当前租户可见版本、状态、哈希、Workflow 绑定和运行引用统计；最高版本只能表示排序结果，不能被推断为当前运行版本。
- 插件版本切换必须由管理员显式发起，并在同一数据库事务中更新所有运行引用：`unified_plugin_bindings`、`plugin_capability_assignments`、`pg_hosts.management_channels`、`pg_service_assets.metadata` 和 `pg_device_assets.plugin_version_id`。切换失败必须整体回滚。
- 版本切换不得修改历史 `PluginVersion`、插件包或 DSL 内容，不得自动改写用户派生 Workflow；用户工作流升级必须通过显式套用产生新的不可变版本。
- 内置插件扫描、Manifest/Policy/摘要校验、导入、权限审批、启用和 Workflow 发布都按插件逐项处理；用户插件通过 USER 导入链写入当前租户后保持 `DISABLED + NOT_REQUIRED`，只允许管理员手动启用。单个插件失败时只跳过或禁用该插件并记录结构化 `warning`，至少包含 `phase`、`pluginId`、`version`、`errorCode` 和错误信息；其他插件和后端继续启动。数据库连接、应用构造和路由注册错误仍必须阻塞启动。历史引用直接删除或作废并记录审计，运行时不做兼容转换。
- `gcac.plugin-manifest/v1` 的 USER 插件权限仍必须在 Manifest 中声明并通过导入校验，但不创建或等待权限审批记录；BUILTIN 插件和 `gcac.agent-plugin/v1` 插件继续执行各自的权限审批规则。

### 2.3 版本注册表和运行期热刷新

- 内置包仓库版本事实只允许包内 `manifest.json.version`；统一 Registry 在启动和热刷新时扫描包，不能建立第二份版本 Ledger。数据库中的 `unified_plugin_versions`、`unified_plugin_resources` 和 Plugin Workflow Binding 是从包扫描派生的不可变运行记录；历史发布台账、数据库和 Binding 都不得反向改写 Manifest。
- 插件市场目录必须使用当前租户可见版本集合，即租户版本与系统内置版本的并集，并按 SemVer 展示最高可用版本。不得只查询租户历史副本，否则会遮蔽新的系统内置版本。
- `POST /api/v1/plugin-catalog/refresh-builtins` 会通过统一 Registry 扫描并导入内置不可变插件包，同时按当前租户扫描 `data/plugins/<pluginId>/` 并通过 USER 导入链发布用户插件；用户包不进入内置 Registry，不读取或升级旧运行引用，且导入后保持 `DISABLED + NOT_REQUIRED`，等待管理员手动启用。
- “刷新市场”必须先完成内置包扫描和用户包导入，再重新查询插件目录；更新任一插件文件后必须递进 Manifest 版本并按不可变 PluginVersion 发布流程注册。
- 导入只注册新的不可变版本；是否启用由插件来源对应的生命周期规则决定，不自动把旧 Binding、Capability Assignment、Host、ServiceAsset 或 DeviceAsset 映射到新版本；旧引用直接删除或作废，新引用只能由当前 Manifest/PluginVersion/Capability 显式创建，不提供运行期旧版本回退。
- 当前运行版本必须由实际运行引用推断；插件市场显示的最高版本表示“最新可用版本”，不能替代版本管理接口中的当前运行版本。

### 2.4 测试归属与执行边界

插件测试按行为责任分层，不按“内置/用户”标签把所有用例放进同一目录：

| 测试层 | 归属与目录 | 主要内容 |
| --- | --- | --- |
| 插件包测试 | `backend/src/modules/plugins/builtin-plugins/<pluginId>/tests/`；Fixture 与插件包同目录 | Manifest、资源、Runtime、产品协议、原子计划和插件特有故障 |
| 宿主公共测试 | `backend/src/modules/plugins/application/`、`runner/`、`protocol/` 及宿主模块测试目录 | 导入、Registry、Policy、权限、租户隔离、Host API、Runner 生命周期和执行控制面 |
| 跨边界测试 | `compatibility/fixtures/<family>/` 或显式 P2 测试批次 | 多插件共享的协议、故障矩阵、真实 Runner 子进程和版本摘要绑定 |
| 用户插件测试 | 用户插件自己的源码仓库或发布工程 | 插件作者维护的产品行为测试；宿主不执行其中的任意测试代码 |

现有与 Runtime 相邻的 `runtime/index.test.mjs` 可以保留；新增插件测试优先使用包内 `tests/`。宿主测试不得因为某个内置插件存在而伪装成插件自身测试，插件测试也不得反向验证宿主所有公共能力。

按需测试必须遵守以下触发规则：

- 只改一个插件包时，运行该插件包测试、通用 Manifest/资源版本门禁和受影响 Runner 集成测试。
- 修改 Schema、导入、权限、Registry、Host API、Runner 协议或共享执行链时，运行宿主公共契约/安全测试，并补跑受影响插件批次。
- 发布或共享基础设施变更必须运行完整 P1/P2；不能以局部插件测试代替全量门禁。
- 用户插件导入只执行宿主提供的 Manifest、资源、哈希、Workflow、权限、Grant、Action 和失败关闭契约；代码型插件必须在隔离进程和固定向量中执行。

所有插件测试结果必须绑定 `pluginId`、版本、`packageHash`、`manifestHash` 和 `resourceHash`。摘要或版本变化后，旧测试结果不得继续作为发布证据。

## 3. 四种设备和目标模式

| 模式 | 合法对象 | 执行来源 | 禁止事项 |
| --- | --- | --- | --- |
| 无 Agent DeviceAsset | DeviceAsset、标准发现投影、无代理连接 | `WorkflowExecutionBinding`；必要时由 DSL `plugin.action` 调用设备 Action | 不虚构 Agent，不创建无依据的执行来源 |
| ManagedTarget | ApplicationAsset、ManagedTarget 上下文 | `WorkflowExecutionBinding`；Action 绑定只在 DSL 明确声明时存在 | 不建立包级 Runner Workflow 或第二条执行主链 |
| Standalone | ApplicationAsset、Standalone 目标上下文 | `WorkflowExecutionBinding`；必要时由 DSL `plugin.action` 调用 Action | 新目标不得创建独立 PluginBinding 作为工作流来源 |

所有目标的工作流执行来源统一为 `WorkflowExecutionBinding`，ManagedTarget 只提供目标上下文。当前 `plugin-promotion.service.ts` 仍按旧 Standalone PluginBinding 自动创建 Managed Binding，属于迁移缺口，不得作为新实现模板；跨域绑定和 Action 固定规则以 004.5、006.2 和 008.2 为准。

## 4. PluginBinding、Assignment 和输入

- Managed Binding 必须有 `managedContext.hostId`，可选 `managedTargetId`。
- ManagedContext 不保存 Agent ID、DeviceAsset ID、厂商类型或执行位置；这些由标准目标上下文实时解析。
- Standalone Workflow 不保存 ManagedContext。
- 普通变量、连接、凭据和 Artifact 使用统一 `InputBindingsV1`。
- Secret 只保存稳定 `credentialId` 或 `secret://` 引用，不保存明文。
- 证书材料只能通过 Artifact Slot 注入，不能写入普通变量、DSL 命令、日志或计划 JSON。
- 最终输入优先级为：单次执行覆盖 → 应用资产 Binding → Agent 发现资产字段 → 插件默认值。
- `source.kind=asset` 表示从 `DeploymentAssetContextV1` 结构化字段取值；资产字段存在时，插件默认值不得覆盖它。
- `bindingPolicy=default_overridable` 只表示用户可显式覆盖默认值，不能把默认值当成已发现事实。

### 4.1 插件部署输入与通用表单

- 插件的普通变量、连接、凭据和 Artifact 必须通过 `DeploymentInputContractV1` 声明；宿主只按契约投影和渲染，不得按变量名、厂商、产品、资产类型或工作流名称增加业务分支。
- 面向用户可编辑的部署输入必须提供 `descriptionKey`，并在 `ui` 中提供 `labelKey`、`group`、`order` 和 `helpKey`。这些字段是表单契约的一部分，不得依赖宿主回退显示变量名。
- 新建应用资产时，宿主通过草稿应用资产上下文生成部署输入投影；插件不得要求先持久化应用资产才能填写自己的输入。
- 用户在统一向导选择站点后，宿主必须立即使用该站点和当前应用资产草稿生成部署输入投影；首次投影使用插件配方声明的 `deploymentDefaults` 初始化 Binding，保存站点前必须再次使用同一输入解析链校验并回填最终 Binding。
- 接入配方声明 `deploymentDefaults` 时，通用表单只显示配方中实际声明的变量、连接、凭据和 Artifact Slot。字段是否可编辑仍由 `configurationMode`、`bindingPolicy` 和 `source` 决定，不能因为插件默认值存在而显示整份输入合同。
- 证书格式选择器匹配到 `format + configName` 后，宿主必须依据当前 Artifact Contract 自动生成输出映射。只要映射无歧义，叶子证书、私钥、证书链和指纹不得再次要求用户逐项选择；用户只能覆盖被合同声明为 `default_overridable` 的映射。
- `allowInsecureTls` 是普通的 `boolean` Binding 输入，不是设备 `tlsVerify` 的别名，也不会在没有插件契约声明时被宿主猜测生成。需要 TLS 例外的插件必须显式声明：

```json
{
  "allowInsecureTls": {
    "type": "boolean",
    "required": true,
    "configurationMode": "required",
    "source": { "kind": "binding" },
    "lifecycle": "pre_execution",
    "bindingPolicy": "required_binding",
    "descriptionKey": "deploymentInputs.allowInsecureTls.description",
    "ui": {
      "labelKey": "deploymentInputs.allowInsecureTls.label",
      "group": "security",
      "order": 10,
      "helpKey": "deploymentInputs.allowInsecureTls.help"
    }
  }
}
```

### 4.2 应用资产接入配方与新建设备入口

应用资产接入配方是插件资源，唯一资源入口为 Manifest 的 `resources.onboarding.applicationAsset`，通常指向 `onboarding/application-asset.json`。配方固定使用 `gcac.application-onboarding/v1`；宿主只读取已启用的固定 `PluginVersion`，并把 `pluginVersionId + recipeHash` 固定到接入会话。前端、API 请求和运行数据库都不得传入资源路径或临时配方内容。

当配方的 `deviceSelection` 为 `EXISTING_OR_NEW` 时，插件可用 `newDeviceOnboarding` 声明统一设备向导的预选入口：

```json
{ "kind": "AGENT_INSTALL", "platformKey": "linux" }
```

或：

```json
{ "kind": "PLUGIN_MANAGED", "pluginId": "device.citrix.netscaler-adc" }
```

- `AGENT_INSTALL.platformKey` 必须使用设备平台注册表中的稳定键。统一设备向导在打开时解析该键；无法解析时必须失败关闭，不得退回空白平台选择。向导只生成对应平台的 Agent 安装流程；在 Agent 实际注册、健康检查和发现事实可用前，不得把它伪装成可选设备。
- `PLUGIN_MANAGED.pluginId` 必须是已启用设备插件的稳定标识。向导必须加载该插件当前可用版本的 `forms.device`，由设备插件完成凭据收集、连接测试和设备创建。
- `EXISTING_ONLY` 与 `NONE` 配方禁止声明 `newDeviceOnboarding`。为兼容历史版本，未声明该字段的 `EXISTING_OR_NEW` 配方只允许选择已有设备，前端不得显示一个会打开空白设备向导的“新增设备”选项。
- `PLUGIN_MANAGED` 的设备表单引用必须是 Manifest `resources.forms` 中声明的真实资源路径，例如 `forms/device.json`；禁止写逻辑别名、内嵌表单或宿主专属字段。
- 目标投影必须为每个可部署目标提供稳定的 `managedTargetId` 和 `configFingerprint`。Agent Host 的 `configFingerprint` 必须来自真实配置事实；插件管理的网络设备没有 Agent 配置文件时，由宿主基于站点、目标、框架、端点和发现元数据生成 `gcac.discovered-target-identity/v1` SHA-256 摘要，插件不得填充随机值、时间戳或直接拼接目标 ID。
- 站点发现返回的所有满足目标类型、能力和健康条件的目标都必须进入向导候选列表；缺少真实目标关系时才标记不可选，不能因为网络设备没有文件式配置指纹而把整台设备的站点清空。
- 宿主只转发声明，不得按 IIS、Apache、NGINX、Tomcat、Citrix、Synology 或其他厂商/产品名称分支。新增平台需要改变入口时，修改插件配方并递进 Manifest 版本。
- 需要在应用资产创建完成时写入应用级部署默认值的插件，可以在配方声明 `deploymentDefaults`。`capabilityKey`、`variables`、`connections` 和 `credentials` 的具体字段和值由插件自行定义；宿主只按统一输入合同校验并保存，不得按产品名称解释字段。
- `deploymentDefaults.certificateFormat` 使用宿主标准格式码和 `configName`，例如 `{ "format": "PEM", "configName": "宿主默认 PEM Bundle" }`。宿主负责把它解析为当前租户可用的证书格式配置 ID，并根据插件 Artifact 合同生成产物映射；插件不得把环境相关的 `certificateFormatId` 固定写入配方。
- `deploymentDefaults` 当前只适用于 `MANAGED_TARGET` 应用资产接入；没有声明该字段的历史插件继续沿用人工绑定路径。默认值只写入应用级 Plugin Binding，不替代审批、输入快照、审计和 `ExecutionGrant`。

设备插件成功创建设备后，宿主关闭设备向导、恢复原接入会话并刷新兼容设备列表。Agent 安装流程只在用户完成安装并关闭向导后恢复列表；设备是否出现仍由实际注册和平台能力校验决定，不得写入虚假会话状态。

配方、表单、Manifest onboarding 资源或该字段任一变化都属于插件包内容变化，必须通过 `scripts/plugins/update-plugin-version.mjs` 递进 Manifest 版本；摘要由 Loader/Registry 重新计算，禁止修改运行数据库来绕过版本规则。

- `allowInsecureTls` 只表达用户或插件接入配方对当前部署跳过 TLS 证书校验的明确意图，不产生网络执行授权。插件可以通过 `deploymentDefaults.variables.allowInsecureTls` 显式把该值预填到应用级 Binding；宿主不得根据设备配置、插件名称或 TLS 探测结果自行猜测该值。审批、输入快照、审计和 `ExecutionGrant` 仍由宿主统一处理。
- Managed 设备接入表单若使用标准字段 `tls.verifyPeer`，且设备连接 Workflow 显式声明 required 的 `allowInsecureTls` Binding，宿主可以按统一规则写入其反值；这只是同一用户开关的输入投影，不是厂商分支、默认猜测或执行授权。

## 5. Agent 证书位置和标准发现

Agent 插件必须通过资源声明发现映射，使用标准 `gcac.device-discovery/v2` 和 `gcac.agent-discovery-mapping/v1`。宿主不按 NGINX、Apache、Tomcat、IIS 或其他产品名称分派。

### 5.1 证书位置

- 依赖当前服务配置的证书路径、KeyStore、服务名或程序路径时，变量必须引用 `source.kind=asset` 的正式 `target.certificateLocation.*` 字段。
- 精确发现得到的路径、端口、服务和指纹优先于插件默认值。
- 历史默认路径不得作为运行期兼容兜底；目标事实缺失时必须阻断计划或要求人工补齐，不得猜测产品路径。
- 发现必须同时处理 `notBefore`、`notAfter` 和尽可能真实的 `sha256Fingerprint`。
- `configFingerprint` 必须进入证书位置和输入快照；Agent Atomic 计划可通过 `preflight.assert.expectedSha256` 在执行前重新读取并比对，指纹不一致必须失败关闭。
- 可选材料或可选刷新方式必须使用结构化 `whenVariablePresent` 条件；条件为空时，计划编译器和 Agent 宿主都必须跳过该操作，不得把空路径送入权限校验或文件系统。
- 手工目标的 TLS 验证必须使用 `certificate.verify/v1` 结构传递 `connectHost`、`serverName` 和 `port`，不得退化为命令字符串或自由文本。
- Agent 只返回进程、服务、端口、文件、权限和摘要等原始本机事实。Windows NGINX、Apache、Tomcat 的配置解析和框架识别由对应控制面插件完成；Agent Core 不解析 `server`、`VirtualHost`、`Connector` 等产品语法。
- Windows Go Agent 的完整 Web 发现必须保留并正确传递已声明的 `refreshWebInventory` 控制字段；完整扫描应能产生框架、站点、配置文件和证书文件事实。控制面不得在严格解码前删除该字段，也不得用空库存掩盖扫描未执行或 Agent-side 插件不可用。
- Agent-side Web 插件生成服务名、程序路径和配置指纹时，必须优先使用真实进程镜像路径，再回退到进程命令行、SCM 服务可执行路径和服务 `ImagePath`；所有回退结果都必须标记来源，缺失时保持缺失，不得猜测默认配置路径。
- 历史 Target 的部署输入投影必须读取同一 Framework 的 `rawFacts` 补全缺失运行事实，并保持 Target 已确认字段优先。插件和 Agent 不得通过路径猜测服务名、程序路径或配置指纹。

### 5.2 稳定键和容错

- 所有对象和父子引用使用插件声明的稳定键。
- 含中文、空格或协议特殊字符的名称必须生成确定性编码键，原始值只用于展示。
- 集合字段始终输出数组，零项和单项不能折叠成对象。
- 只读发现可以使用 `foreach.continueOnError` 保留部分失败；部署、变更和回滚禁止使用该容错。
- 只读发现 warning 必须使用稳定 `code`，并保留来源 Capability 和受影响路径；warning 不能包含私钥、KeyStore 密码或其他 Secret。
- 每个 foreach 子项必须有独立执行身份和幂等键。
- 发现稳定键变化时，宿主必须在同一投影事务中处理同一来源的历史非托管绑定：设置失效时间并释放唯一索引；已经由用户接管的 `MANAGED` 绑定不得被自动删除或覆盖。历史脏数据不能导致整批新发现事实回滚。

## 6. Workflow DSL 与插件 Action

- Agent Plan 和代码型插件不能单独伪装成用户工作流。用户工作流只能直接提交当前 DSL；插件内部 Workflow 只作为 `plugin_internal` 固定版本供能力绑定，不提供复制派生入口。代码型能力只能作为 DSL 中明确声明的 `plugin.action` 步骤；`credential.acquire` 不是用户工作流复制来源。
- 插件内部工作流标记为 `plugin_internal`、只读、归插件版本所有。
- 历史 `plugin_derived` 和 `legacy` 记录只进入发布前清理审计，不参与运行期查询、转换或新版本绑定；用户工作流直接提交后标记为 `user` 并归用户所有。
- 发布时使用规范化 DSL 内容计算 SHA-256；同一插件资源哈希不变则复用已发布版本，插件任一资源变化都必须递进 Manifest 插件版本，并同步全部 Workflow `metadata.version`。
- 正式 DSL 仍只能来源于内置模板目录或用户导入目录，禁止新增第三套样例目录。
- 需要厂商 SDK、签名请求或私有协议等 DSL 无法表达的单个能力时，应使用带代码入口的官方 PluginVersion，通过 DSL 的 `plugin.action` 调用独立 Plugin Runner 和受控 Host API；异步轮询、检查点、部署/验证/回滚顺序仍必须写入普通 DSL，而不是交给 Runner 编排。

### 6.1 `credential.acquire` 插件能力

`credential.acquire` 与 `certificate.deploy`、`certificate.rollback` 平级，是插件为特定资产提供的浏览器临时凭据获取能力。能力合同固定使用：

```json
{
  "key": "credential.acquire",
  "contractVersion": "1.0",
  "actionContractId": "credential.acquire.v1",
  "riskLevel": "HIGH",
  "executionLocations": ["CONTROL_PLANE"]
}
```

插件必须同时声明：

- 独立的 `WorkflowVersion`，不得与 deploy/rollback 工作流共享；其 DSL `metadata.version` 仍须与当前 PluginVersion 一致；
- 登录入口、允许 Origin、浏览器运行时限制等输入合同；
- `CredentialOutputContract`，明确参数名、敏感类型、必填性和 delivery；
- 工作流所需的受限 Browser Session Broker 能力。

用户完成网页登录后，只有手动点击“获取凭据”才允许执行该工作流。工作流不得根据页面内容猜测 Token、Cookie 或 Header，不得接收客户端提交的秘密，不得序列化 Playwright `Browser`、`BrowserContext` 或 `Page` 对象。执行器只能使用短租期 `BrowserSessionHandle` 访问创建会话时的同一个 BrowserContext。

`credential.acquire` 的未声明敏感输出必须丢弃，不得进入 Secret、普通变量、日志、审计或 API 响应。验证通过后，只有输出合同允许的字段才能写入临时 `BROWSER_SESSION` 凭据。

`credential.acquire` 只在 `GCAC_DEPLOYMENT_ARCHITECTURE=standard` 时可执行。标准架构固定使用独立 Browser Runtime 专用容器，并在容器内为每个会话启动独立 Chromium/Xvfb/VNC 进程组；不得动态创建会话 OCI 容器，也不得让 GCAC Backend 或 Browser Runtime 挂载 Docker Socket。小型架构可以读取插件合同和历史记录，但不得装配或执行 Browser Runtime。

## 7. Runtime 和执行位置

执行位置只表达在哪里执行，不能决定使用哪个插件。宿主先固定普通 DSL WorkflowVersion；只有 DSL 明确包含 `plugin.action` 时，才按固定 `canonicalPluginId`、`pluginVersionId`、Capability 和 Action Binding 调用对应 Plugin Runner 或 Agent v2 合同，不再保留旧 Runtime 分派器。

宿主负责：

- 网络出口、Gateway、TLS 和连接；
- Secret Grant、Artifact Grant、执行锁和恢复账本；
- Schema 校验、表单、发现投影、审计、限流、熔断和指标；
- 计划快照、结果同步、验证和回滚。

- 声明式插件和 Agent Plan 插件不得执行任意代码；代码型插件只能在 DSL `plugin.action` 步骤中通过同一 Docker 内独立 Plugin Runner 进程执行，并且必须通过签名、Policy Authority、Grant、Host API 和代码执行授权门禁。
- Plugin Runner 不是 OS 沙箱；生产仍必须依赖最小权限、资源限制、路径/服务白名单、审计和节点隔离策略。
- 所有 Runtime 的插件都不得直接访问数据库、Secret 存储、宿主任意文件系统路径或未声明的宿主内部服务。

## 8. 安全、发布和成熟度

- 声明式插件和 Agent Plan 插件不得进入代码执行态；代码型插件必须单独获得代码执行授权后才能装配和执行。
- 官方代码插件允许携带受控代码和 SDK 依赖，但不得携带宿主原生扩展、任意二进制执行文件或未登记的动态库。代码只能由独立 Plugin Runner 进程加载。
- 代码插件只允许 `OFFICIAL_SIGNED` 或明确受控签名级别进入装配候选；未签名、用户自签名或来源不明的插件不得执行。即使已装配，执行前仍必须通过代码执行授权门禁。
- 高风险权限、网络访问、设备写入、Secret 和 Artifact 必须声明；BUILTIN 插件和 `gcac.agent-plugin/v1` 插件还必须完成权限审批，USER 插件不设置该审批门槛。
- 未启用、适用的权限审批未完成、签名无效、版本冲突、资源校验失败或未知 Action 必须失败关闭。
- 用户插件发布者可信链和密码学验签当前尚未完成，状态为 `TODO`；不能以包加载成功代替验签。
- 真实部署、真实回滚、Gateway、产品版本和执行位置必须分别记录成熟度，不能合并成一个“支持”标签。
- Workflow DSL 中的 `allowInsecure: true` 只能在明确审批、审计、测试隔离和发布门禁下使用，不得作为普通默认值；对应的用户配置必须通过 `allowInsecureTls` Binding 输入表达。

## 9. 验证清单

发布前必须验证：

1. Manifest、资源路径、不可变版本和包哈希。
2. Runtime、Scope、Capability、Permission、签名等级和兼容性。
3. 四种设备/目标模式及来源冲突。
4. `source.kind=asset`、证书位置、精确发现和稳定键。
5. Secret/Artifact Grant、输入快照和 `configFingerprint` 状态。
6. Workflow DSL Schema、内容哈希、Provenance、checkpoint、foreach、assert 和 rollback。
7. `credential.acquire` 能力合同、独立 Workflow 资源与绑定、Manifest 插件版本和 DSL `metadata.version` 的边界、Browser Session Broker、同上下文验证和 `CredentialOutputContract`。
8. DSL `plugin.action` 的输入/输出 Schema、Action Binding、Plugin Runner Host API 门禁、SDK 依赖白名单、独立进程代码入口、Capability Token、Policy Authority、审计字段和恢复账本。
9. 真实部署/回滚、Gateway、外部厂商和多实例协调的证据状态。
10. 八语言资源或安全回退、前端 i18n、审计和脱敏。
11. Manifest 插件版本、Workflow DSL 版本和数据库 Workflow 整数版本未被混用。
12. 同一 `pluginId@Manifest.version` 的内容冲突必须阻塞启动或热刷新；已注册版本的 Workflow 派生发布失败只隔离对应插件并记录告警，不阻塞后端，版本查询、显式切换和事务回滚均有自动化证据。
13. 应用接入配方必须覆盖 `AGENT_INSTALL` 与 `PLUGIN_MANAGED` 预选、未知字段拒绝、禁用设备选择模式拒绝、设备向导回跳和兼容设备刷新；真实厂商/Agent 验收仍按平台单独记录。
14. 声明 `deploymentDefaults` 的插件必须验证站点选择后的投影回填、只显示已声明 Slot、Artifact 输出自动映射、默认可覆盖字段的修改以及最终保存前重新解析。
15. 插件包测试、宿主公共测试和跨边界测试按责任归属存放，用户插件测试未被宿主任意执行。
16. 按需测试结果已绑定插件版本及 `packageHash`、`manifestHash`、`resourceHash`；共享宿主改动已补跑 P1/P2。
