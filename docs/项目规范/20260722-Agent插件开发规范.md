# Agent 插件开发规范

## 1. 文档目的

本文档规定 GCAC Agent Plan 与 Agent-side Plugin 的运行协议、原子操作、安全边界、设计、开发、校验、测试、发布、升级和废弃要求，是本领域的主规范。跨域 Plugin Runner、Host API、Action IPC 与 DSL `plugin.action` 边界以 `specs/004.5-插件进程隔离与宿主能力边界重构治理/` 为唯一权威；统一插件包、Manifest、Registry 与发布来源以 `docs/项目规范/20260802-统一设备与工作流插件开发规范.md` 为准。

本文中的 `backend/src/modules/plugins/builtin-agent-plugins/` 和 `data/agent-plugins/` 仅保留为历史目录记录，不是当前运行期扫描或插件市场来源。当前内置资源统一由 `backend/src/modules/plugins/builtin-plugins/` 的 Manifest/Registry 发布链管理；用户插件通过统一插件包导入接口进入不可变 `PluginVersion`。

Agent 插件用于组合受控原子操作，在 Windows 或 Linux Agent 上完成非标准 HTTPS 服务的证书部署。插件不是任意脚本包，不是远程终端，也不是新的产品 Handler。任何实现不得以“兼容特殊场景”为理由绕过权限、签名、版本、审计和回滚规则。

本规范与以下文档共同构成 Agent 插件的正式契约：

- `specs/004.5-插件进程隔离与宿主能力边界重构治理/`：控制面 Plugin Runner、Host API 和 DSL `plugin.action` 的跨域边界；Agent 插件不得把 Runner 或 Agent Core 变成工作流编排器。
- `docs/项目规范/20260723-工作流模板管理及编写规范.md`：工作流 DSL 规范。Agent 插件不是工作流 DSL 的 step 类型。
- `docs/项目规范/20260707-国际化规范.md`：前端用户文案规范。
- `docs/项目规范/20260707-主题变量规范.md`：前端样式和设计令牌规范。

### 1.1 统一部署输入契约修订（2026-07-30）

Agent 插件的部署输入声明统一使用 `DeploymentInputContractV1`，Schema 唯一实现位于 `backend/src/modules/deployment-inputs/schema/deployment-input-contract.schema.ts`。Agent Plugin 与 Workflow DSL 共享同一份变量 Source、配置模式、生命周期、覆盖策略、Connection、Credential Slot 和 Artifact Slot 定义；两者只在输入解析完成后的 Runtime Adapter 分流。

新增任何厂商 Agent 插件时，只允许新增或修改插件自己的 Contract、Binding 和 Recipe 资源；宿主资产服务、部署计划、执行器和前端表单不得为该插件新增变量传递、变量名猜测或产品分派代码。插件运行时直接消费统一 Resolver 生成的 `ResolvedDeploymentInputV1`；如果现有 Slot 接口无法表达需求，应扩展版本化通用协议，而不是在宿主增加厂商特例。

正式 Source 仅允许 `asset`、`binding`、`default`、`derived`、`system`、`step_output`。普通变量类型不得包含 `credential` 和 `certificate`；凭据必须使用 Credential Slot，证书材料必须使用 Artifact Slot。`execution_context`、`secretBindings` 和独立 `artifactInputs` 属于 Spec 033.6 的硬切迁移对象，不得用于新增或发布新版本插件。

统一 Resolver 的取值优先级固定为：单次执行覆盖 → 应用资产 Binding → Agent 发现的资产字段 → 插件默认值。`source.kind=asset` 表示变量从 `DeploymentAssetContextV1` 的结构化字段读取；当该字段不存在且变量声明了 `default` 时，才允许回退默认值。`bindingPolicy=default_overridable` 只表示默认值可被显式 Binding 覆盖，不得解释为默认值可以覆盖已经存在的资产发现值。

Agent 管理的 NGINX、Apache HTTP Server 和 Apache Tomcat 站点，如果部署目标依赖当前服务配置中的证书路径、KeyStore、服务名或程序路径，插件变量必须使用 `source.kind=asset` 绑定正式 `target.certificateLocation.*` 字段。目标事实缺失时必须阻断计划并要求人工补齐；不得把历史默认路径作为运行期兜底，也不得把 `/etc/nginx/tls/server.crt`、`/etc/httpd/tls/server.crt` 等示例路径当作已发现站点的部署事实。

## 2. 核心原则

### 2.0 默认禁用

所有内置和用户插件首次发现、导入或升级到新版本时，默认不得参与任何业务选择。缺少租户级目录启用记录等价于 `disabled`。手动启用和权限审批是两个独立条件：Agent 插件必须同时满足包状态、权限审批和目录启用；DSL 模板插件必须同时满足文件校验和目录启用。

### 2.1 控制面 Agent Plugin 只描述，Agent-side Plugin 独立执行

控制面 Agent Plugin 负责声明和编译：

- 适用平台和 Agent Capability。
- 用户可配置变量。
- SecretRef 引用槽位。
- 所需证书 Artifact。
- 文件、程序、服务和网络权限。
- 原子操作及其执行阶段。
- 失败后的回滚操作。

`executionMode=agent_plan` 插件不得包含自定义二进制、动态库、解释器、内嵌脚本或下载后执行逻辑；它只能把产品语义编译为 Agent v2 类型化计划。若必须调用本机专有 API，能力归对应的 Agent-side Plugin。Agent-side Plugin 必须是独立进程，通过 Agent Core 窄接口请求事实采集和授权原语，不得访问宿主数据库、绕过 Agent Core 或取得任意命令执行能力。代码型控制面插件统一由同一 Docker 内的独立 Plugin Runner 进程执行；Plugin Runner 与 Agent-side Plugin 是两个不同的进程边界，不能混写为 Agent Core 的内置代码。

### 2.2 默认拒绝

出现以下任一情况时必须拒绝导入、启用、挂载、编译或执行：

- Manifest 字段缺失、类型错误或引用不存在。
- 插件平台、架构或 Capability 与 Agent 不兼容。
- 高风险权限未经审批。
- 变量展开后的实际目标超出权限声明。
- 插件版本、包哈希或签名不匹配。
- 执行计划过期、被篡改或目标 Agent 不匹配。
- 插件包含副作用操作但没有回滚。
- 插件请求 Shell 或未注册的原子操作。

禁止用默认值、兼容分支或 Mock 执行掩盖上述错误。

### 2.3 未发布项目的版本切换

- GCAC 尚未发布，不承诺历史用户、历史应用资产、历史挂载或历史执行兼容；当前工作区旧 Action、旧挂载和旧 Agent 合同只能作为清退对象。
- 未发布阶段允许协调修改当前 Manifest、PluginVersion 和执行合同，但必须同步更新 Schema、Fixture、测试、任务和验收记录；禁止保留运行期 alias/fallback 作为“兼容”。
- 进入生产前，插件版本、包哈希和签名材料必须不可变；上线后新增能力必须发布新插件版本或新原子操作 Schema 版本。
- Agent 必须明确上报支持的动作及 Schema 版本，控制面不得根据操作系统名称猜测能力。

### 2.4 统一插件目录与 Binding

控制面 Agent Plugin 必须投影到统一 PluginVersion 目录，执行位置固定为 `agent_plan`；其他代码型控制面能力使用 `isolated_process`，只能由 DSL 的 `plugin.action` 步骤调用同一 Docker 内独立 Plugin Runner 进程执行单个 Action。需要本机专有 API 的 Agent-side Plugin 使用独立进程身份，不得伪装成 Agent Core 或完整 Workflow。统一目录投影保留 Canonical Plugin ID、版本、平台 Profile、Framework、架构、权限和最低 GCAC 版本。

Agent Manifest 的 `metadata.logoUrl` 用于声明插件市场 LOGO，并在统一目录投影时写入统一 Manifest 顶层 `logoUrl`。该值必须是 HTTP(S) URL 或浏览器可访问的本地 Web 路径；修改 LOGO 必须发布新版本。

应用资产使用统一 PluginBinding 固定 PluginVersion、变量、SecretRef 和证书产物绑定；Agent mount、`gcac.agent-plan/v2`、签名、Capability Token、Policy Authority、Nonce 校验和恢复协议作为 Agent 执行边界，不得改成 Workflow DSL。

完整统一插件模型见 `docs/项目规范/20260802-统一设备与工作流插件开发规范.md`。

## 3. 目录和文件组织

### 3.1 内置插件

系统内置 Agent Plan 资源随统一插件包位于：

```text
backend/src/modules/plugins/builtin-plugins/
```

内置资源随代码发布并受 Git 跟踪。内置插件必须与用户上传插件使用同一套 Manifest 校验、权限审批、资产绑定、计划编译和 Agent 执行链路，不得创建旁路。

### 3.2 用户插件

用户插件通过统一插件包导入接口发布为不可变 `PluginVersion`。历史 Agent 插件包曾使用以下目录保存；该目录不再作为运行期加载或市场扫描来源：

```text
data/agent-plugins/
```

目录规则：

- `data/agent-plugins` 仅作为历史迁移记录，不是当前用户插件的运行期文件目录。
- `data/workflows` 继续只用于用户工作流 DSL，不保存 Agent 插件。
- 用户插件不得与工作流 DSL 文件混放；统一导入接口负责版本、资源摘要、签名和租户边界。
- 业务代码只能依赖统一 PluginVersion/Resource 记录，不得直接拼接宿主绝对路径。
- 插件包内容、Manifest、签名和包哈希必须按版本隔离保存，已发布版本不得被覆盖。

推荐目录结构：

```text
data/agent-plugins/
└── <pluginId>/
    └── <version>/
        ├── manifest.json
        ├── package.bin
        └── package-metadata.json
```

工作流 DSL 文件只能从 `data/workflows/` 导入；Agent Plan 与代码型插件只能通过统一插件包发布链进入 PluginVersion。两套协议禁止跨目录扫描，也禁止按文件内容猜测协议类型。

### 3.3 禁止的目录

不得把 Agent 插件放入以下目录：

- `backend/src/modules/workflow-templates/builtin-workflows`
- `data/workflows`
- `docs/工作流样例`
- `docs/workflows`

Agent Plan、Agent-side Plugin 和工作流 DSL 是三个边界清晰的执行协议。用户工作流 DSL 只能保存到 `data/workflows/`，插件只能通过统一 PluginVersion 导入接口发布；禁止按文件内容猜测协议类型。两者的部署输入声明仍必须共同引用 `DeploymentInputContractV1` 和同一个输入 Schema。

## 4. Manifest 基础结构

Agent 插件 Manifest 使用：

```json
{
  "apiVersion": "gcac.agent-plugin/v1",
  "kind": "AgentDeploymentPlugin",
  "pluginId": "example.product.certificate",
  "name": "example-product-certificate-deployment",
  "publisher": "Example Publisher",
  "version": "1.0.0",
  "minGcacVersion": "0.1.0",
  "metadata": {},
  "compatibility": {},
  "inputContract": {
    "apiVersion": "gcac.deployment-input/v1",
    "variables": {},
    "connections": {},
    "credentials": {},
    "artifacts": {}
  },
  "permissions": [],
  "operations": [],
  "rollback": []
}
```

### 4.1 `apiVersion`

- 第一版固定为 `gcac.agent-plugin/v1`。
- 不得用插件版本替代协议版本。
- 协议字段发生不兼容变化时必须发布新的 `apiVersion`。

### 4.2 `kind`

固定为 `AgentDeploymentPlugin`。

### 4.3 `pluginId`

- 必须全局稳定且不可随显示名称变化。
- 推荐使用反向域名或组织前缀，例如 `com.example.rabbitmq.pem`。
- 发布后不得复用同一 `pluginId` 表示完全不同的产品或部署语义。

### 4.4 `name`

- 使用稳定的英文短横线命名。
- 用于日志、目录和排障，不作为用户唯一识别依据。
- 用户界面优先显示 `metadata.displayName`。

### 4.5 `version`

必须使用语义化版本：

```text
MAJOR.MINOR.PATCH
```

- `MAJOR`：变量、Artifact、权限或行为存在不兼容变化。
- `MINOR`：在不改变既有合同语义的前提下增加变量、平台或操作能力；这不是历史版本兼容承诺。
- `PATCH`：不改变外部契约的缺陷修复。

相同 `pluginId + version` 的 Manifest 和包内容必须保持不可变。

### 4.6 `minGcacVersion`

- 使用完整 SemVer 声明插件可运行所需的最低 GCAC 版本，例如 `0.1.0`。
- 插件导入、启用、挂载和执行前均必须满足 `当前 GCAC 版本 >= minGcacVersion`。
- 当前工作区的每个插件必须显式填写该字段，不得依赖宿主猜测兼容性。
- 缺少该字段的 Manifest 必须拒绝导入或执行；不得按 `0.0.0` 或其他默认值为旧插件提供运行期兼容。
- 该字段只表达 GCAC 宿主兼容下限，不能替代插件自身的 `version` 或协议 `apiVersion`。

## 5. Metadata 规范

`metadata` 可包含：

- `displayName`：面向用户的名称。
- `description`：说明适用场景和部署结果。
- `category`：产品或使用场景分类。
- `tags`：用于目录检索。
- `maintainer`：维护者或组织。
- `homepage`：项目主页或内部文档入口。

Metadata 不得包含：

- 明文密码、Token、私钥或证书内容。
- 宿主实际路径、IP 地址或客户名称。
- 用于驱动执行分支的隐藏配置。

执行逻辑必须来自正式字段，不能通过标签或描述文本推断。

## 6. 兼容性声明

示例：

```json
{
  "compatibility": {
    "platforms": ["WINDOWS", "LINUX"],
    "frameworks": ["web.nginx", "web.iis", "runtime.custom"],
    "architectures": ["amd64", "arm64"],
    "requiredCapabilities": ["agent.plan.validate", "agent.plan.execute", "agent.execution.receipt"],
    "operationSchemaVersions": {
      "file.atomic_replace": ["1.0"],
      "service.control": ["1.0"]
    }
  }
}
```

规则：

1. `platforms` 必填，只允许 `WINDOWS` 和 `LINUX`。
2. `frameworks` 可选，值使用开放的标准命名空间标识，例如 `web.nginx`、`web.iis`、`app.tomcat`；禁止使用宿主维护的大写厂商枚举。声明后，应用资产选择器按标准 Framework Type 过滤。

Agent Capability 详情需要生成 Framework、Site 或 ManagedTarget 时，插件包必须在统一 Manifest 的 `resources.agentDiscoveryMappings` 中引用 `gcac.agent-discovery-mapping/v1` JSON 资源。资源声明 Capability Key、`web_sites` 或 `connectors` 通用形状、Framework Type、Target Type 与部署 Capability。宿主不提供厂商 fallback，也不接受多个启用插件占用同一 Capability Key。
3. `architectures` 可选；声明后必须与 Agent 上报值匹配。
4. `requiredCapabilities` 必须包含插件实际依赖的能力。
5. `operationSchemaVersions` 应覆盖插件使用的全部原子操作。
6. 不得在控制面或插件代码中增加 `if Windows`、`if Linux`、产品名称或版本号硬编码分派。
7. 同一产品跨 Windows/Linux 时必须保持一个逻辑插件，并在包内声明平台 Profile；不得按操作系统复制插件，也不得在一个操作中塞入两套脚本。

## 7. 变量定义规范

### 7.1 支持类型

第一版支持：

- `string`
- `number`
- `boolean`
- `enum`
- `object`
- `file`

Credential 和 Certificate 不得作为普通变量类型，分别使用 Credential Slot 和 Artifact Slot。

### 7.2 变量定义

示例：

```json
{
  "inputContract": {
    "apiVersion": "gcac.deployment-input/v1",
    "variables": {
    "certificatePath": {
      "type": "file",
      "required": true,
      "default": "/etc/example/tls/server.crt",
      "configurationMode": "advanced",
      "source": { "kind": "default" },
      "lifecycle": "pre_execution",
      "bindingPolicy": "default_overridable"
    },
    "servicePort": {
      "type": "number",
      "required": true,
      "minimum": 1,
      "maximum": 65535,
      "default": 443,
      "configurationMode": "advanced",
      "source": { "kind": "default" },
      "lifecycle": "pre_execution",
      "bindingPolicy": "default_overridable"
    }
    },
    "connections": {},
    "credentials": {},
    "artifacts": {}
  }
}
```

### 7.3 命名规则

- 使用英文标识符，以字母或下划线开头。
- 后续可包含字母、数字、下划线、短横线和点号。
- 名称表达业务含义，不使用 `value1`、`param2` 等无意义名称。
- 不得依赖变量名猜测资产字段或产品类型。

### 7.4 校验规则

- 必填变量必须设置 `required=true`。
- 数字应声明 `minimum` 和 `maximum`。
- 枚举必须提供非空 `enum`。
- 字符串和文件路径可使用 `pattern` 做基础格式约束。
- 默认值必须符合变量类型及校验条件。
- 未声明变量必须被拒绝，不允许静默保留。

### 7.5 编辑范围

- `fixed`：只能来自 `asset`、`derived`、`system` 或 `step_output`，禁止 Binding 覆盖。
- `default_overridable`：允许按 Execution、Application、Target、Device、Default 顺序覆盖。
- `required_binding`：必须在计划创建前由有效 Binding 提供。

执行阶段覆盖不得修改应用资产中保存的原始配置。

## 8. SecretRef 规范

### 8.1 基本规则

- 凭据必须声明 Credential Slot，Binding 只保存 `{ "credentialId": "cred_xxx" }`。
- 创建计划时固定 `credentialVersionId` 和精确 SecretRef 快照，不保存密码、Token 或裸 SecretRef。
- 前端编辑页面只能展示引用和元数据，不得回显明文。

### 8.2 禁止事项

- 禁止把密码放入 `variableBindings`。
- 禁止把 Secret 写入 Manifest、日志、审计详情、错误信息或文档示例。
- 禁止让 Agent 插件读取任意环境变量或系统凭据目录。
- 禁止通过命令参数、文件名或 URL 查询参数泄漏 Secret。

### 8.3 运行时处理

如果某个原子操作未来需要使用 Secret，必须先为该原子操作建立明确的 Secret 输入 Schema 和脱敏规则。不得把 SecretRef 直接当作明文传给程序。

## 9. Certificate Artifact 规范

### 9.1 输入类型

证书材料必须通过统一 Contract 的 Artifact Slot 声明。`kind` 只使用 `certificate` 或 `file`，具体材料语义由 `artifactContract.outputs[].role` 表达。

示例：

```json
{
  "artifacts": {
    "certificate": {
      "kind": "certificate",
      "required": true,
      "configurationMode": "required",
      "lifecycle": "pre_execution",
      "artifactContract": { "outputs": { "certificate": { "role": "public_certificate", "required": true } } }
    },
    "privateKey": {
      "kind": "certificate",
      "required": true,
      "configurationMode": "required",
      "lifecycle": "pre_execution",
      "artifactContract": { "outputs": { "privateKey": { "role": "private_key", "required": true, "sensitive": true } } }
    }
  }
}
```

### 9.2 资产绑定

应用资产必须为每个必填 Artifact 配置：

- `certificateFormatId`
- `outputBindings`

示例：

```json
{
  "inputBindings": {
    "apiVersion": "gcac.input-bindings/v1",
    "variables": {},
    "connections": {},
    "credentials": {},
    "artifacts": {
      "certificate": {
        "certificateFormatId": "format-pem",
        "outputBindings": { "certificate": "leafPem" }
      },
      "privateKey": {
        "certificateFormatId": "format-pem",
        "outputBindings": { "privateKey": "privateKeyPem" }
      }
    }
  }
}
```

### 9.3 规则

- 插件不得假设证书格式或文件名。
- 插件不得读取控制面本地文件路径。
- 控制面必须在生成签名计划前验证输出键真实存在。
- 私钥 Artifact 不得写入日志或错误详情。
- Artifact 内容进入计划时必须受计划签名和过期时间保护。

## 10. 权限声明规范

### 10.1 权限结构

每条权限包含：

- `name`
- `description`
- `risk`
- `scope`
- `values`

支持的 `scope`：

- `filesystem`
- `process`
- `service`
- `network`
- `secret`
- `shell`
- `certificate_store`
- `iis`

支持的风险等级：

- `low`
- `medium`
- `high`

### 10.2 最小权限原则

示例：

```json
{
  "permissions": [
    {
      "name": "rabbitmq-tls-files",
      "description": "读写 RabbitMQ TLS 文件",
      "risk": "medium",
      "scope": "filesystem",
      "values": ["/etc/rabbitmq/tls/*"]
    },
    {
      "name": "rabbitmq-service",
      "description": "重启 RabbitMQ 服务",
      "risk": "medium",
      "scope": "service",
      "values": ["rabbitmq-server"]
    }
  ]
}
```

规则：

1. 优先声明确定路径、程序和服务名称。
2. `*` 全局通配必须标记为 `high`，并说明无法收窄的原因。
3. 变量展开后必须再次检查实际值是否匹配权限范围。
4. 权限声明只允许覆盖插件真实使用的目标。
5. 删除操作必须与写入操作使用同一文件权限边界。
6. 新版本扩大权限时必须重新审批，不能继承旧版本审批结果。
7. `file` 类型变量表示用户明确绑定的文件目标；计划编译器必须把其解析后的非空绝对路径作为精确值加入已审批的 `filesystem` 权限快照，禁止自动扩大为父目录或全局通配符。
8. 动态精确路径只能在插件已声明并获批 `filesystem` Scope 时生成；插件未声明该 Scope 时必须拒绝编译。
9. `command.execute.input.program` 和 `service.control.input.serviceName` 如果引用变量，计划编译器必须把展开后的程序路径和服务名作为精确值加入对应的 `process`、`service` 权限快照；插件不得用 `*` 代替动态发现结果。
10. `preflight.assert` 的 `path` 和 `program` 必须在控制面编译阶段执行与 Agent 相同的权限检查，禁止把明显越界问题拖到 Agent 执行阶段。

### 10.3 Shell 权限

第一版不允许 Shell。Manifest 出现以下内容必须被拒绝：

- `shell.enabled=true`
- `/bin/sh -c`
- `cmd.exe /c`
- `powershell -Command`
- 把多个命令拼接成单个字符串。

即使声明 `scope=shell`，也不代表第一版可以启用 Shell。该 Scope 仅用于显式表达和拒绝未来不兼容插件。

## 11. 原子操作规范

本章同时定义 Agent 插件的运行协议边界。Agent 插件使用 `gcac.agent-plugin/v1` Manifest，只能声明受控原子操作，不注册 IIS、NGINX、RabbitMQ、Java 等产品 Handler。所有 Agent 插件默认不启用；导入、签名校验或权限审批完成不等于可参与资产选择，必须同时满足插件安装状态、权限审批和租户目录启用状态。缺少目录启用记录按禁用处理。

### 11.1 支持的操作

当前双平台 Agent 的内置 Operation Registry 支持：

| 操作 | 用途 |
| --- | --- |
| `preflight.assert` | 检查路径、程序或前置条件 |
| `file.backup` | 建立可回滚备份 |
| `file.atomic_replace` | 在同一目录中写临时文件并原子替换 |
| `file.restore` | 根据备份操作 ID 恢复文件 |
| `file.set_permissions` | 设置文件权限或属主 |
| `command.execute_allowlisted` | 执行固定可执行文件、参数模板和环境白名单内的程序 |
| `service.control` | 控制允许的系统服务 |
| `windows.certificate.inspect_pfx` | 检查 PFX、证书私钥和指纹 |
| `windows.certificate_store.import_pfx` | 幂等导入 Windows Certificate Store |
| `windows.certificate_private_key.grant` | 由 `web.iis` Agent-side Plugin 通过窄接口向 IIS 应用池身份授予私钥读取权限；不得注册到 Agent Core 通用 Registry |
| `certificate.material.validate` | 校验证书材料、格式和指纹 |

IIS Binding、Windows AppPool ACL、Nginx reload、Apache 配置解析和其他产品语义不属于通用 Agent Operation。需要 Windows 专有 API 时由 `web.iis` 的 Agent-side Plugin 通过 Agent Core 窄接口执行；普通文件、服务和证书材料动作仍使用上述通用原语。

Manifest 的 `operationType` 和权限 `scope` 使用小写点号标识，不由控制面维护产品白名单。插件可以声明新的扩展标识，但这不等于 Agent 自动获得实现：启用和执行前必须由目标 Agent 上报对应 Operation 与 Schema 版本，未注册的 Operation 必须在 Agent 端失败关闭。产品标识、Operation 实现和所需权限属于插件与 Agent Registry 的协商数据，禁止重新写回宿主 TypeScript Union、数组或 `switch`。

### 11.2 通用字段

每个操作必须包含：

```json
{
  "id": "install-certificate",
  "name": "安装证书",
  "stage": "install",
  "operationType": "file.atomic_replace",
  "schemaVersion": "1.0",
  "timeoutSeconds": 60,
  "dependsOn": ["backup-certificate"],
  "input": {}
}
```

### 11.3 操作 ID

- 在 `operations` 或 `rollback` 各自范围内唯一。
- 发布后保持稳定，便于账本、审计和排障识别。
- 使用动作含义命名，例如 `backup-certificate`，不用数组序号。

### 11.4 依赖关系

- `dependsOn` 只能引用同一操作集合中的已存在 ID。
- 禁止循环依赖。
- 阶段顺序仍是第一约束，依赖不得让后续阶段反向依赖前序阶段。

### 11.5 `command.execute_allowlisted`

正确示例：

```json
{
  "operationType": "command.execute_allowlisted",
  "input": {
    "program": "/usr/bin/keytool",
    "args": ["-list", "-keystore", "${variables.keystorePath}"]
  }
}
```

错误示例：

```json
{
  "operationType": "command.execute_allowlisted",
  "input": {
    "program": "/bin/sh",
    "args": ["-c", "keytool -list && systemctl restart app"]
  }
}
```

规则：

- `program` 必须匹配本地策略中固定的绝对路径或可执行文件摘要。
- `args` 必须是字符串数组。
- 参数必须匹配插件声明的固定模板；环境变量、工作目录、超时、输出大小和子进程策略必须显式绑定。
- 禁止 Shell、管道、重定向、命令替换和多命令拼接。
- 程序和展开后的参数必须进入审计，但敏感参数必须脱敏。

### 11.6 `file.atomic_replace`

- 有覆盖风险时必须先执行 `file.backup`。
- 目标路径必须在 `filesystem` 权限内。
- 临时文件必须在目标文件同一目录创建，确保原子替换语义。
- 私钥默认使用最小权限。
- 不允许把内容写到权限声明外的临时目录后跨文件系统移动。
- Linux Agent 以低权限服务账号运行时，文件动作只能使用通用本地策略和已批准的文件权限边界；禁止在 Agent Core 内加入 Nginx 专用 helper 或产品特定 sudoers 通道。
- PREFLIGHT 必须验证与正式执行相同的直接访问或受控 helper 路径，并在结果中返回 `privilegeMode`；禁止只验证插件 `filesystem` Scope 后声称目标可读写。
- 产品配置检查和 reload 语义由对应控制面插件声明，Agent 只执行经过策略绑定的通用动作，不识别 NGINX 或其他产品。
- Linux Agent 升级必须把 Agent 二进制和 `gcac-nginx-helper` 作为同一事务更新；启动验证失败或断电恢复时必须同时回滚，禁止只替换二进制形成协议版本不一致。

### 11.7 平台或 Gateway TLS 验证

- Agent Plugin Recipe 禁止声明 `tls.verify`，业务 Agent 不得发起部署后的 TLS 网络验证。
- TLS 验证必须建模为独立 Execution `VERIFY` 步骤，由平台后端主动执行；明确指定 Gateway 时，由控制面主动派发 `gateway.probe` 且通道必须为 `probe.tls`。
- 验证输入只允许使用宿主能力对象 `certificateVerification`，其 `capabilityKey` 固定为 `certificate.verify`、`schemaVersion` 固定为 `1.0`，并包含 `connectHost`、`serverName`、`port`、`expectedDomains` 和 `expectedFingerprintSha256`。禁止继续使用平铺 `verifyConnectHost`、`verifyServerName`、`verifyPort`。
- `connectHost` 必须来自受管 Host 的 `primaryIp`，`serverName` 必须来自应用资产的 `sniName`，未配置时使用应用资产 `address`；`port` 必须来自应用资产端口。
- 所有 Agent Atomic 和 Workflow DSL 证书部署均由宿主追加独立 `VERIFY`，插件只负责部署。宿主默认使用平台后端执行；明确指定 Gateway Agent 时使用 `probe.tls`。
- 正式成功判定只比较宿主 TLS 握手返回的远端叶子证书 SHA-256、域名和目标证书，不要求插件提供本地 `certPath` 指纹，也不在结果同步阶段补发第二次网络探测。
- 缺少任一字段必须失败关闭并要求重新生成部署计划；禁止回退 `verifyHost`、`verifyUrl`、DNS 解析结果或 Agent 自身猜测。
- 仅“端口可连接”不能作为证书部署成功；平台或 Gateway 必须完成 TLS 握手、域名校验并返回远端证书 SHA-256 指纹。
- 旧部署计划和旧 Plugin Binding 不做运行时兼容，必须按最新受管目标快照重新生成。
- 唯一允许的部署后验证结果路径是 `resultDetail.verify.remoteCertificateSha256`；Gateway 返回结果也必须使用该结构，禁止顶层 `remoteCertificateSha256`、`remoteFingerprintSha256` 或本地 Binding Thumbprint 充当成功证据。
- Agent 产品 Handler、Provider 和 Recipe 只能返回安装、配置测试、reload/restart、备份与回滚证据；禁止暴露 `VERIFY`/`verify` 操作、`tls.local_verify`、`tls.remote_probe`、`iis_binding_verify`、`nginx_verify_delegated` 等并行协议。
- 部署前证书、私钥、证书链和 keystore 的纯材料解析使用 `certificate.material.validate`，它不能联网、不能读取部署后端点，也不能替代 `certificate.verify`。
- 宿主结果同步层只校验 VERIFY 执行器已经返回的标准结果，禁止解析 Workflow extracted 字段冒充验证结果，禁止恢复旧 Agent 失败，禁止补发 TLS 请求。
- 插件发布前必须全仓检查 `tls.verify`、`tls_probe`、`tls.local_verify`、`tls.remote_probe`、`verifyHost`、`verifyPort`、`verifyServerName` 和顶层 `remoteCertificateSha256`；除本节禁止清单、不可变历史迁移和通用 HTTP 客户端 TLS 安全配置外，不得命中。

### 11.8 Windows IIS 原子操作

- `windows.certificate.*` 必须声明 `certificate_store` 权限，第一版只允许 `LocalMachine/My`。
- `windows.iis.*` 必须声明 `iis` 权限，站点和应用池名称在变量展开后再次校验。
- `windows.iis.binding.capture` 必须早于 Binding 更新执行，并把原证书 Thumbprint 写入恢复账本。
- `windows.iis.binding.restore_certificate` 必须引用捕获操作 ID，禁止插件直接提供任意旧 Thumbprint。
- PFX 密码只能来自受控 Artifact 或 SecretRef，不得写入普通日志。

## 12. 阶段规范

正常操作阶段顺序固定为：

```text
prepare → backup → install → refresh → verify
```

回滚操作使用：

```text
rollback
```

规则：

1. `prepare` 只能检查，不得修改系统状态。
2. `backup` 建立回滚材料，不得提前覆盖目标。
3. `install` 写入证书、私钥、KeyStore 或配置。
4. `refresh` 重启或重新加载服务。
5. `verify` 验证最终 TLS 服务和目标证书。
6. 核心阶段禁止 `continueOnError=true`。
7. 不得通过调整数组顺序绕过阶段约束。

## 13. 回滚规范

### 13.1 必须声明回滚的操作

`install` 或 `refresh` 阶段存在任何操作时必须声明 `rollback`。该规则按阶段语义判断，不维护会阻止插件扩展的产品 Operation 白名单。以下内置操作是典型副作用示例：

- `file.atomic_replace`
- `file.set_permissions`
- `command.execute_allowlisted`
- `service.control`

### 13.2 文件回滚

文件回滚应引用对应备份操作：

```json
{
  "id": "restore-certificate",
  "name": "恢复原证书",
  "stage": "rollback",
  "operationType": "file.restore",
  "schemaVersion": "1.0",
  "input": {
    "backupOperationId": "backup-certificate"
  }
}
```

### 13.3 执行规则

- 失败后按回滚数组逆序执行。
- 回滚操作必须幂等。
- 回滚失败返回 `AGENT_ROLLBACK_FAILED` 并进入 `MANUAL_INTERVENTION`。
- `MANUAL_INTERVENTION` 状态下禁止自动无限重试。
- 备份账本必须记录目标路径、原始存在状态、权限和必要的属主信息。
- 回滚操作需要前序副作用成功后才有意义时，必须使用 `input.whenOperationCompleted`；前序操作未完成时 Agent 返回成功的跳过结果。

## 14. 资产绑定规范

应用资产插件策略示例：

```json
{
  "type": "AGENT",
  "agent": {
    "mode": "PLUGIN",
    "agentId": "agent-001",
    "certificateFormatId": "format-pem",
    "plugin": {
      "pluginPackageId": "plugin-package-001",
      "pluginVersionId": "plugin-version-001",
      "inputBindings": {
        "apiVersion": "gcac.input-bindings/v1",
        "variables": {},
        "connections": {},
        "credentials": {},
        "artifacts": {}
      }
    }
  }
}
```

规则：

- 必须选择目标 Agent 上状态为 `MOUNTED` 的插件。
- 必须固定 `pluginPackageId` 和 `pluginVersionId`。
- 保存前必须调用绑定预览接口。
- 插件模式不要求 SiteAsset 和 ManagedTarget。
- 原生模式仍要求 SiteAsset 和 ManagedTarget，不得因为插件功能放宽历史校验。
- 更换 Agent、插件版本、变量、SecretRef 或 Artifact 映射后必须重新预览。

### 14.1 Agent 站点证书位置

控制面插件负责解释 Agent 返回的原始本机事实并识别 NGINX、Apache 或 Tomcat；Agent Core 不解析任何产品配置。ManagedTarget 元数据中的正式结构为 `gcac.certificate-location/v1`，由宿主投影到 `DeploymentAssetContextV1.target.certificateLocation` 和 `deployment.targets[].certificateLocation`。如必须调用本机专有配置 API，由对应产品插件的 Agent-side Plugin 通过 Agent Core 窄接口完成，结果仍必须转换为原始事实或标准计划输入。

正式结构至少支持：

- `storageKind=PEM_FILES`：`certificatePath`、`privateKeyPath`，可选 `certificateChainPath`。
- `storageKind=KEYSTORE`：`keystorePath`，可选 `keystoreType` 和 `alias`。
- `storageKind=WINDOWS_CERTIFICATE_STORE`：`storeThumbprint`。
- 通用审计字段：`sourceConfigPath`、`serviceName`、`programPath`、`reloadCommand`、`configFingerprintSha256`、`confidence`、`observedAt`。

规则：

- 新 Agent 发现结果应写入版本化 `certificateLocation`；`certPath`、`keyPath`、`keystorePath` 和 `storeThumbprint` 等旧字段只允许出现在清退扫描和负向 Fixture 中。
- 旧 Agent 未返回正式结构时，宿主必须拒绝需要正式结构的执行并记录环境/协议阻断；不得从旧字段构造运行期兼容位置，也不得猜测框架默认路径。
- 发现结果只包含位置和审计元数据，禁止包含私钥内容、KeyStore 密码或任何 Secret 明文。
- Windows Full Agent 的 NGINX、Apache、Tomcat 只读发现必须保留产品 detail 中的 `warnings`，并在直连 Discovery 响应和标准投影中输出结构化 `code`、`path` 与来源 Capability；单个配置或证书材料失败不得丢弃其他产品事实。
- Windows 路径必须按本机文件系统语义保留，不能把程序路径、配置路径、证书路径、私钥路径、链路径和 KeyStore 路径合并成一个泛化字段。Tomcat KeyStore 只允许上报公开证书摘要、类型、别名和位置，不得上报密码或私钥内容。
- `confidence=EXACT` 且 resolved input 使用了不同的插件默认路径时，部署计划必须以 `DEPLOYMENT_INPUT_DEFAULT_OVERRIDES_DISCOVERED_LOCATION` 拒绝创建；显式应用资产 Binding 或执行覆盖仍允许生效，并必须保留 provenance（来源追踪）。
- NGINX、Apache 的 `certificatePath`、`privateKeyPath`、可选链路径、程序路径和服务事实，以及 Tomcat KeyStore 的 `keystorePath`、`keystoreType`、`keyAlias`、Java 程序路径和服务名，均应直接绑定 `target.certificateLocation` 对应字段。
- Agent Atomic 手工目标可以通过 `whenVariablePresent` 表达 PEM/KeyStore 和程序/服务刷新二选一；空条件必须在计划编译和 Agent 执行两侧一致跳过。
- 手工目标的验证输入必须结构化为 `certificate.verify/v1`，包含连接地址、端口和 SNI；禁止用 `shell` 或命令字符串承载 TLS 验证。

## 15. 资产直选与旧挂载清退规范

新建和编辑应用资产时，必须直接选择已启用的插件包版本。选择器必须至少按应用资产的操作系统平台和框架类型过滤；Agent 的架构和 Capability 在绑定预览及执行计划编译时再次校验。不得要求用户先进入 Agent 详情或插件目录建立挂载关系。

`mountId` 是当前工作区遗留字段。项目尚未发布，不保留旧资产运行期兼容；新资产不得生成 `mountId`，旧挂载入口必须在生产接线前清退。挂载相关 API 和数据表只能作为清退范围记录，不得继续作为执行主路径。

### 15.1 插件选择和执行前检查

- 插件已启用。
- 高风险权限已审批。
- Agent 平台和架构兼容。
- Agent 已注册并支持 `agent.fact.collect`、`agent.plan.validate`、`agent.plan.execute`、`agent.execution.receipt`。
- Agent 支持插件声明的原子操作 Schema 版本。

### 15.2 当前挂载审计快照

清退前的当前挂载审计必须保存：

- Agent ID。
- 插件包和版本 ID。
- 包哈希。
- 能力和版本校验快照。
- 权限快照和审批结果。
- 挂载状态和时间。

无论是否存在历史挂载，都不得在每次执行时静默切换到插件最新版本。

### 15.3 禁用和删除

- 禁用插件时应阻止新资产选择和新执行计划编译，并禁用其历史有效挂载。
- 仍被当前工作区资产引用的挂载不得静默删除，必须先完成引用清退。
- 删除前必须提供引用检查或明确错误。
- 当前审计记录中的插件版本和权限快照不得因清退操作丢失；这不构成历史执行恢复承诺。

## 16. 执行计划规范

控制面编译的执行计划使用 `gcac.agent-plan/v2`，至少包含：

- `planId`
- `tenantId`
- `agentId`
- `executionRunId`
- `executionStepId`
- 插件包 ID、版本 ID、包哈希和 Manifest 哈希
- `issuedAt`
- `expiresAt`
- `idempotencyKey`
- 权限快照
- 变量摘要
- 正常操作和回滚操作
- `AgentCapabilityTokenV1`、Policy Authority 决策、Nonce 和签名引用

执行计划必须在实际 Execution Step 创建后编译，禁止使用伪造或占位 Run/Step ID 提前签名。

### 16.1 PREFLIGHT 非破坏性预演

- Agent `PREFLIGHT` 计划必须包含正式 `APPLY` 的全部 Agent 原子操作；TLS 验证不属于 Agent Plan，必须作为后续独立 `VERIFY` 步骤展示和执行。
- Agent 必须逐操作返回 `operationResults`，并保留原操作 ID、类型和阶段；控制面将其转换为逐项 `dryRunChecks`。
- `file.backup` 只检查路径、文件是否存在、可读属性和预计备份对象，不创建备份。
- `file.atomic_replace` 只检查权限、目标路径、父目录和 Artifact 内容，不创建目录、不写临时文件、不替换目标文件。
- `file.set_permissions` 只展示计划权限，不执行 chmod、chown 或 ACL 修改。
- `command.execute_allowlisted` 默认只验证固定程序、参数模板和权限，不执行命令；需要在预演中真实执行的只读检查必须建模为独立受控预检操作。
- `service.control` 只读取服务当前状态并展示正式动作，不执行 start、stop、restart 或 reload。
- 平台或 Gateway 的 DRY-RUN TLS 验证是只读真实探测；当前端点暂不可达时返回 warning，并明确展示执行位置、连接地址、SNI 和端口。
- PREFLIGHT 结果必须明确包含 `preview=true` 和 `mutating=false`，任何产生业务状态修改的实现都属于严重缺陷。

### 16.2 主动派发、进度和超时

- 现代 Agent、设备代理和工作流转发操作必须由控制面主动连接目标 Agent 发起，禁止把任务先放入 `queued` 再把 Agent 拉取作为静默兜底。
- 主动直连任务入库时必须直接占有 `direct:{taskId}` lease，并进入 `acked` 状态；`pullTasks` 不是生产执行路径，不能作为历史兼容兜底。
- Agent 拉取任务接口必须在生产接线前清退；统一部署、能力重扫和 Gateway 转发执行链不得调用该接口驱动执行。
- 控制面可以在已经主动启动的短期 action 会话中查询 Agent 状态；这属于控制面主动获取执行更新，不是 Agent 轮询控制面任务队列。
- Agent 必须在 action 状态中持续暴露当前 operation ID、类型、序号、已完成数量、总数量和已完成操作结果；控制面必须把该进度写入 Execution Step detail stream。
- 单次直连 HTTP 请求必须有有限超时，整个 action 等待时间必须大于 Agent 计划上限但保持有限；任何连接、状态查询或执行超时都必须形成失败终态，禁止无限 `RUNNING`。
- Linux Agent Atomic PREFLIGHT 默认单操作上限为 20 秒，插件声明可以缩短或延长，但最高 60 秒；整个 PREFLIGHT 计划上限为 90 秒。
- PREFLIGHT 超时必须返回 `AGENT_PLAN_PREFLIGHT_TIMEOUT`，错误信息必须包含最后执行的 operation ID 和类型；超时后不得继续派发后续修改性动作。

签名规范：

- 控制面必须先通过 JSON 序列化和反序列化得到实际传输对象，再对不含 `authorization` 的计划计算签名；禁止让 `undefined` 等不可传输值参与签名。
- 对象键必须按 Unicode code unit 升序排列；数组保持原顺序；数字、布尔值、字符串和 `null` 使用标准 JSON 表示。
- 字符串 canonical 化不得额外转义 `<`、`>`、`&`；控制面和 Agent 必须使用同一 UTF-8 字节序列计算 HMAC-SHA256。
- Agent 必须先对接收到的原始计划对象验签，再转换为内部执行结构；不得因忽略暂不消费的扩展字段而改变待验签内容。
- 生产和开发均必须显式注入测试或生产 KeySet；缺少 KeySet、未知 key、撤销 key 或策略根状态异常时必须失败关闭，禁止任何默认密钥。

## 17. 幂等和账本规范

- 同一执行步骤和同一插件输入必须生成稳定幂等键。
- Agent 必须持久化计划状态、已完成操作、操作结果、备份和回滚结果。
- 已成功计划再次到达时返回缓存结果，不重复覆盖文件或重启服务。
- 进程中断后允许根据账本继续执行尚未完成的操作。
- 幂等键相同但计划内容不同必须拒绝，不能复用旧账本。

## 18. 审计和日志规范

### 18.1 遗留 Action 清退

项目尚未发布，不建立历史部署计划的运行期迁移别名。遗留 Action 只能进入清退台账或负向 Fixture；运行期遇到旧 Action、旧 Snapshot、旧 Binding 或缺失正式输入时必须在 Agent Task 入队前拒绝，不得转换为旧合同或静默 fallback。

生产执行只能使用当前有效的 Capability Assignment、PluginBinding、固定 PluginVersion 和 `ResolvedDeploymentInputV1`；旧命令、路径及 Secret 不得进入新计划，也不得出现在拒绝响应或审计明文中。

必须能够追踪：

- 谁上传、审批、启用、禁用插件。
- 谁把哪个插件版本挂载到哪个 Agent。
- 哪个应用资产绑定了哪个挂载和版本。
- 哪个 Execution Run/Step 生成并派发了计划。
- Agent 实际执行了哪些原子操作。
- 是否发生失败、回滚或人工干预。

日志禁止包含：

- 私钥内容。
- 密码、Token 和 Secret 明文。
- 完整 PFX、JKS、PKCS#12 或 PEM Bundle。
- 未脱敏的敏感命令参数。

## 19. 开发流程

### 19.1 新增插件

1. 确认场景不能由现有原生 Handler 或工作流 DSL 更简单地解决。
2. 列出目标文件、程序、服务、网络和 Secret 权限。
3. 定义最小变量和 Artifact 输入。
4. 使用现有原子操作编排正常阶段和回滚。
5. 运行 Manifest Schema 校验。
6. 运行兼容性、权限和安全测试。
7. 在测试 Agent 上执行部署、验证、失败回滚和重复执行。
8. 完成权限评审和发布记录。

### 19.2 新增原子操作

只有现有原子操作无法表达真实且重复出现的需求时，才允许新增原子操作。新增时必须同时完成：

- DTO 和 Schema。
- Windows/Linux 支持矩阵。
- Agent Registry 注册。
- 权限模型。
- 输入和输出 Schema。
- 幂等和回滚语义。
- 签名计划兼容性。
- 单元测试、安全测试和文档。
- Agent 构建产物更新。

不得为了单个产品增加一个只服务该产品的“原子操作”。这种需求应优先重新设计为通用文件、服务、命令或验证能力。

## 20. 测试准入规范

### 20.1 Manifest 测试

- 正常 Manifest 校验成功。
- 缺失字段和非法类型失败。
- 未声明变量和 Artifact 引用失败。
- 重复操作 ID 和循环依赖失败。
- 阶段逆序失败。
- 有副作用但无回滚失败。
- Shell 请求失败。

### 20.2 权限测试

- 允许路径成功。
- 相似前缀路径越界失败。
- `..` 路径穿越失败。
- 未声明程序、服务和网络目标失败。
- 变量展开后越界失败。
- 高风险权限未审批时启用失败。

### 20.3 签名计划测试

- 正确签名成功。
- 任一字段篡改后失败。
- 过期计划失败。
- 目标 Agent 不匹配失败。
- 包哈希或 Manifest 哈希不匹配失败。
- 重复计划命中幂等账本。

### 20.4 原子执行测试

- 文件备份和原子替换。
- 原文件不存在时的安装和回滚删除。
- 权限及属主恢复。
- 程序参数数组执行。
- Shell 绕过拒绝。
- 服务刷新失败触发回滚。
- TLS 指纹验证成功和失败。
- 回滚失败进入 `MANUAL_INTERVENTION`。

### 20.5 双平台要求

修改 Windows Agent 源码后必须立即执行：

```powershell
gofmt -w .
go test ./...
go build -o gcac-agent.exe .
```

修改 Linux Agent 源码后必须立即执行：

```bash
gofmt -w <本次修改的 Go 文件>
go test ./...
bash ./build.sh
```

不得把“请用户自行编译”作为交付步骤。

## 21. 发布准入

插件只有同时满足以下条件才允许发布或启用：

- Manifest Schema 校验通过。
- 包哈希稳定。
- 签名状态符合环境策略。
- 权限清单完成评审。
- 高风险权限完成审批。
- Windows/Linux 兼容性声明有测试证据。
- 正常部署、TLS 验证、重复执行和失败回滚通过。
- 文档说明变量、Artifact、权限和故障处理。
- 没有明文 Secret、Shell 或未注册操作。

## 22. 升级规范

- 资产默认继续使用固定版本。
- 升级前比较变量、Artifact、权限和操作差异。
- 权限扩大必须重新审批。
- 删除必填变量、修改变量类型或改变 Artifact 语义属于 `MAJOR` 版本变化。
- 升级必须重新执行绑定预览和兼容性检查。
- 禁止直接修改历史插件包、历史 Manifest 或历史执行计划。

## 23. 废弃规范

- 废弃插件应先标记不可用于新挂载。
- 已绑定资产必须提供迁移目标和差异说明。
- 废弃不等于删除历史记录。
- 删除存储前必须确认没有活动挂载和应用资产引用。
- Agent 移除旧原子操作 Schema 前必须确认所有已固定插件版本均已迁移。

提交 Agent 插件相关变更时，审查者必须逐项确认：

- [ ] 现有原生 Handler、工作流 DSL 或原子操作不能更简单地解决。
- [ ] 没有新增产品名称、操作系统或版本硬编码分派。
- [ ] Manifest 数据结构完整且没有隐藏配置。
- [ ] 普通变量、SecretRef 和 Artifact 已正确分离。
- [ ] 权限符合最小权限原则。
- [ ] Shell 和命令字符串拼接被禁止。
- [ ] 所有副作用都有明确回滚。

## 26. 故障排查

- `PLUGIN_PERMISSION_DENIED`：检查插件是否启用、高风险权限是否审批，以及变量展开后的路径、程序、服务和网络目标是否在声明范围内。
- `AGENT_PLUGIN_MOUNT_INCOMPATIBLE`：检查 Agent 平台、架构、在线状态、`agent.plan.validate`/`agent.plan.execute` Capability、Token/Policy/Nonce 状态，以及插件声明的原子操作 Schema 版本。
- `AGENT_PLAN_SIGNATURE_INVALID`：检查计划摘要、`AgentCapabilityTokenV1`、`PolicyAuthorityDecisionV1`、Nonce、防重放和撤销状态，以及目标 Agent、租户、运行和步骤绑定是否匹配；禁止依赖代码内置或环境缺失时的默认签名密钥。
- `PLUGIN_PERMISSION_DENIED` 或 `path is outside allowed roots`：检查应用资产绑定的 `file` 类型变量是否以精确绝对路径进入计划的 `filesystem` 权限快照，并确认当前执行使用的是重新编译的新 Run，而不是旧权限快照。
- PREFLIGHT 只显示 `prepare` 操作：检查控制面是否把完整 APPLY 操作编译到 `executionMode=PREFLIGHT` 的计划，并检查 Agent 是否使用专用非破坏性预演分支。
- PREFLIGHT 长期停留在 `RUNNING`：检查执行步骤是否仍走 `agent_task_enqueued` / `directFallback`，检查直连 HTTP 请求是否缺少超时，并读取 action 进度中的 `currentOperationId`；最终执行链只允许 Agent v2 直连合同，禁止回退 Agent 拉取队列。
- `Agent task 缺少 actionType`：检查请求是否符合 Agent v2 的类型化 Plan Schema；历史 `type` 字段不得在运行时转换或兼容执行。
- `file.atomic_replace` 在 PREFLIGHT 返回 `file content is required`：检查部署产物是否根据 `pluginRuntimeCapability.pluginBindingId` 解析 Certificate Artifact Binding，并确认旧平铺的 `certificatePem/privateKeyPem/pfxBase64` 已转换为标准 Artifact 输入。
- `AGENT_PLAN_PREFLIGHT_TIMEOUT`：按错误中的 operation ID 检查文件系统、服务状态或 TLS 端点；不得通过无限提高控制面等待时间掩盖阻塞操作。
- `AGENT_PLAN_EXPIRED`：检查控制面与目标宿主的时间同步状态后重新派发执行计划。
- `AGENT_ROLLBACK_FAILED`：读取 Agent 原子计划账本和操作结果，按 `MANUAL_INTERVENTION` 处理，不得自动重复覆盖现场。

## 27. 规范同步要求

修改以下任一内容时，必须检查并同步更新本规范：

- Agent 插件 DTO 或 Manifest Schema。
- 变量类型、SecretRef 或 Artifact 绑定规则。
- 权限 Scope 或风险等级。
- 原子操作类型、输入 Schema 或阶段。
