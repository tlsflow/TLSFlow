# Agent 插件开发规范

## 1. 文档目的

本文档规定 GCAC Agent 插件的运行协议、原子操作、安全边界、设计、开发、校验、测试、发布、升级和废弃要求。本文件是 Agent 插件的唯一主规范。

Agent 插件用于组合受控原子操作，在 Windows 或 Linux Agent 上完成非标准 HTTPS 服务的证书部署。插件不是任意脚本包，不是远程终端，也不是新的产品 Handler。任何实现不得以“兼容特殊场景”为理由绕过权限、签名、版本、审计和回滚规则。

本规范与以下文档共同构成 Agent 插件的正式契约：

- `docs/项目规范/20260723-工作流模板管理及编写规范.md`：工作流 DSL 规范。Agent 插件不是工作流 DSL 的 step 类型。
- `docs/项目规范/20260707-国际化规范.md`：前端用户文案规范。
- `docs/项目规范/20260707-主题变量规范.md`：前端样式和设计令牌规范。

## 2. 核心原则

### 2.0 默认禁用

所有内置和用户插件首次发现、导入或升级到新版本时，默认不得参与任何业务选择。缺少租户级目录启用记录等价于 `disabled`。手动启用和权限审批是两个独立条件：Agent 插件必须同时满足包状态、权限审批和目录启用；DSL 模板插件必须同时满足文件校验和目录启用。

### 2.1 插件只描述，不直接执行

插件负责声明：

- 适用平台和 Agent Capability。
- 用户可配置变量。
- SecretRef 引用槽位。
- 所需证书 Artifact。
- 文件、程序、服务和网络权限。
- 原子操作及其执行阶段。
- 失败后的回滚操作。

插件不得包含自定义二进制、动态库、解释器、内嵌脚本或下载后执行逻辑。实际执行只能由 Agent 已注册的原子操作 Registry 完成。

### 2.2 默认拒绝

出现以下任一情况时必须拒绝导入、启用、挂载、编译或执行：

- Manifest 字段缺失、类型错误或引用不存在。
- 插件平台、架构或 Capability 与 Agent 不兼容。
- 高风险权限未经审批。
- 变量展开后的实际目标超出权限声明。
- 插件版本、包哈希或签名不匹配。
- 执行计划过期、被篡改或目标 Agent 不匹配。
- 插件包含副作用操作但没有回滚。
- 插件请求 Shell 或未注册的原子操作。

禁止用默认值、兼容分支或 Mock 执行掩盖上述错误。

### 2.3 向后兼容

- 未设置 Agent 部署模式的历史应用资产继续按 `NATIVE_HANDLER` 处理。
- 已发布并被应用资产、挂载或执行记录引用的插件版本不可原地修改。
- 新增能力必须发布新插件版本或新原子操作 Schema 版本。
- Agent 必须明确上报支持的动作及 Schema 版本，控制面不得根据操作系统名称猜测能力。

## 3. 目录和文件组织

### 3.1 内置插件

系统内置 Agent 插件位于：

```text
backend/src/modules/plugins/builtin-agent-plugins/
```

内置插件随代码发布并受 Git 跟踪。内置插件必须与用户上传插件使用同一套 Manifest 校验、权限审批、资产绑定、计划编译和 Agent 执行链路，不得创建旁路。

### 3.2 用户插件

用户插件通过 Agent 插件包 API 导入，并持久化到：

```text
data/agent-plugins/
```

目录规则：

- `data/agent-plugins` 是用户 Agent 插件的唯一运行期文件目录。
- `data/workflows` 继续只用于用户工作流 DSL，不保存 Agent 插件。
- 用户 Agent 插件不得与工作流 DSL 文件混放。
- 插件仓储负责把插件包 ID、版本和存储键解析为该目录下的相对路径。
- 业务代码只能依赖插件仓储提供的存储键或相对路径，不得直接拼接宿主绝对路径。
- 插件包内容、Manifest、签名和包哈希必须按版本隔离保存，已发布版本不得被覆盖。

推荐目录结构：

```text
data/agent-plugins/
└── <pluginId>/
    └── <version>/
        ├── manifest.json
        ├── package.bin
        └── package-metadata.json
```

工作流 DSL 加载器只能扫描 `data/workflows/`；Agent 插件加载器只能扫描 `data/agent-plugins/`。两套加载器禁止跨目录扫描，也禁止按文件内容猜测协议类型。

### 3.3 禁止的目录

不得把 Agent 插件放入以下目录：

- `backend/src/modules/workflow-templates/builtin-workflows`
- `data/workflows`
- `docs/工作流样例`
- `docs/workflows`

Agent 插件和工作流 DSL 是两个独立协议。用户 Agent 插件只能保存到 `data/agent-plugins/`，用户工作流 DSL 只能保存到 `data/workflows/`。两者必须使用独立目录、独立加载器和独立 Schema，禁止按文件内容猜测协议类型。

## 4. Manifest 基础结构

Agent 插件 Manifest 使用：

```json
{
  "apiVersion": "gcac.agent-plugin/v1",
  "kind": "AgentDeploymentPlugin",
  "pluginId": "example.product.certificate",
  "name": "example-product-certificate-deployment",
  "publisher": "Example Publisher",
  "version": "1.0.0",
  "metadata": {},
  "compatibility": {},
  "variables": {},
  "artifactInputs": {},
  "permissions": [],
  "operations": [],
  "rollback": []
}
```

### 4.1 `apiVersion`

- 第一版固定为 `gcac.agent-plugin/v1`。
- 不得用插件版本替代协议版本。
- 协议字段发生不兼容变化时必须发布新的 `apiVersion`。

### 4.2 `kind`

固定为 `AgentDeploymentPlugin`。

### 4.3 `pluginId`

- 必须全局稳定且不可随显示名称变化。
- 推荐使用反向域名或组织前缀，例如 `com.example.rabbitmq.pem`。
- 发布后不得复用同一 `pluginId` 表示完全不同的产品或部署语义。

### 4.4 `name`

- 使用稳定的英文短横线命名。
- 用于日志、目录和排障，不作为用户唯一识别依据。
- 用户界面优先显示 `metadata.displayName`。

### 4.5 `version`

必须使用语义化版本：

```text
MAJOR.MINOR.PATCH
```

- `MAJOR`：变量、Artifact、权限或行为存在不兼容变化。
- `MINOR`：向后兼容地增加变量、平台或操作能力。
- `PATCH`：不改变外部契约的缺陷修复。

相同 `pluginId + version` 的 Manifest 和包内容必须保持不可变。

## 5. Metadata 规范

`metadata` 可包含：

- `displayName`：面向用户的名称。
- `description`：说明适用场景和部署结果。
- `category`：产品或使用场景分类。
- `tags`：用于目录检索。
- `maintainer`：维护者或组织。
- `homepage`：项目主页或内部文档入口。

Metadata 不得包含：

- 明文密码、Token、私钥或证书内容。
- 宿主实际路径、IP 地址或客户名称。
- 用于驱动执行分支的隐藏配置。

执行逻辑必须来自正式字段，不能通过标签或描述文本推断。

## 6. 兼容性声明

示例：

```json
{
  "compatibility": {
    "platforms": ["WINDOWS", "LINUX"],
    "frameworks": ["NGINX", "IIS", "CUSTOM"],
    "architectures": ["amd64", "arm64"],
    "requiredCapabilities": ["agent.atomic_plan.execute"],
    "operationSchemaVersions": {
      "file.atomic_replace": ["1.0"],
      "service.control": ["1.0"],
      "tls.verify": ["1.0"]
    }
  }
}
```

规则：

1. `platforms` 必填，只允许 `WINDOWS` 和 `LINUX`。
2. `frameworks` 可选，值使用大写框架标识；声明后，应用资产选择器必须按当前框架过滤。
3. `architectures` 可选；声明后必须与 Agent 上报值匹配。
4. `requiredCapabilities` 必须包含插件实际依赖的能力。
5. `operationSchemaVersions` 应覆盖插件使用的全部原子操作。
6. 不得在控制面或插件代码中增加 `if Windows`、`if Linux`、产品名称或版本号硬编码分派。
7. 平台差异较大时应拆成两个插件，或者使用平台均能解释的统一变量；禁止在一个操作中塞入两套脚本。

## 7. 变量定义规范

### 7.1 支持类型

第一版支持：

- `string`
- `number`
- `boolean`
- `enum`
- `object`
- `file`
- `certificate`
- `credential`

### 7.2 变量定义

示例：

```json
{
  "variables": {
    "certificatePath": {
      "type": "file",
      "required": true,
      "description": "目标证书文件路径",
      "default": "/etc/example/tls/server.crt",
      "editableScope": "ASSET"
    },
    "verifyPort": {
      "type": "number",
      "required": true,
      "minimum": 1,
      "maximum": 65535,
      "default": 443
    }
  }
}
```

### 7.3 命名规则

- 使用英文标识符，以字母或下划线开头。
- 后续可包含字母、数字、下划线、短横线和点号。
- 名称表达业务含义，不使用 `value1`、`param2` 等无意义名称。
- 不得依赖变量名猜测资产字段或产品类型。

### 7.4 校验规则

- 必填变量必须设置 `required=true`。
- 数字应声明 `minimum` 和 `maximum`。
- 枚举必须提供非空 `enum`。
- 字符串和文件路径可使用 `pattern` 做基础格式约束。
- 默认值必须符合变量类型及校验条件。
- 未声明变量必须被拒绝，不允许静默保留。

### 7.5 编辑范围

- `ASSET`：保存于应用资产绑定，执行时默认固定。
- `EXECUTION`：允许部署执行前覆盖，但必须重新预览并生成新的签名计划。

执行阶段覆盖不得修改应用资产中保存的原始配置。

## 8. SecretRef 规范

### 8.1 基本规则

- 敏感变量必须使用 SecretRef，不得保存明文。
- `credential` 类型或 `sensitive=true` 的变量进入 `secretBindings`。
- `secretBindings` 保存 Secret ID 或稳定引用标识，不保存 Secret 内容。
- 前端编辑页面只能展示引用和元数据，不得回显明文。

### 8.2 禁止事项

- 禁止把密码放入 `variableBindings`。
- 禁止把 Secret 写入 Manifest、日志、审计详情、错误信息或文档示例。
- 禁止让 Agent 插件读取任意环境变量或系统凭据目录。
- 禁止通过命令参数、文件名或 URL 查询参数泄漏 Secret。

### 8.3 运行时处理

如果某个原子操作未来需要使用 Secret，必须先为该原子操作建立明确的 Secret 输入 Schema 和脱敏规则。不得把 SecretRef 直接当作明文传给程序。

## 9. Certificate Artifact 规范

### 9.1 输入类型

`artifactInputs` 支持：

- `certificate`
- `private_key`
- `certificate_chain`
- `bundle`
- `file`

示例：

```json
{
  "artifactInputs": {
    "certificate": {
      "type": "certificate",
      "required": true,
      "description": "服务器证书或完整证书链"
    },
    "privateKey": {
      "type": "private_key",
      "required": true,
      "description": "服务器私钥"
    }
  }
}
```

### 9.2 资产绑定

应用资产必须为每个必填 Artifact 配置：

- `certificateFormatId`
- `outputBindings`

示例：

```json
{
  "certificateArtifactBindings": {
    "certificate": {
      "certificateFormatId": "format-pem",
      "outputBindings": {
        "value": "fullchain"
      }
    },
    "privateKey": {
      "certificateFormatId": "format-pem",
      "outputBindings": {
        "value": "private"
      }
    }
  }
}
```

### 9.3 规则

- 插件不得假设证书格式或文件名。
- 插件不得读取控制面本地文件路径。
- 控制面必须在生成签名计划前验证输出键真实存在。
- 私钥 Artifact 不得写入日志或错误详情。
- Artifact 内容进入计划时必须受计划签名和过期时间保护。

## 10. 权限声明规范

### 10.1 权限结构

每条权限包含：

- `name`
- `description`
- `risk`
- `scope`
- `values`

支持的 `scope`：

- `filesystem`
- `process`
- `service`
- `network`
- `secret`
- `shell`
- `certificate_store`
- `iis`

支持的风险等级：

- `low`
- `medium`
- `high`

### 10.2 最小权限原则

示例：

```json
{
  "permissions": [
    {
      "name": "rabbitmq-tls-files",
      "description": "读写 RabbitMQ TLS 文件",
      "risk": "medium",
      "scope": "filesystem",
      "values": ["/etc/rabbitmq/tls/*"]
    },
    {
      "name": "rabbitmq-service",
      "description": "重启 RabbitMQ 服务",
      "risk": "medium",
      "scope": "service",
      "values": ["rabbitmq-server"]
    }
  ]
}
```

规则：

1. 优先声明确定路径、程序和服务名称。
2. `*` 全局通配必须标记为 `high`，并说明无法收窄的原因。
3. 变量展开后必须再次检查实际值是否匹配权限范围。
4. 权限声明只允许覆盖插件真实使用的目标。
5. 删除操作必须与写入操作使用同一文件权限边界。
6. 新版本扩大权限时必须重新审批，不能继承旧版本审批结果。

### 10.3 Shell 权限

第一版不允许 Shell。Manifest 出现以下内容必须被拒绝：

- `shell.enabled=true`
- `/bin/sh -c`
- `cmd.exe /c`
- `powershell -Command`
- 把多个命令拼接成单个字符串。

即使声明 `scope=shell`，也不代表第一版可以启用 Shell。该 Scope 仅用于显式表达和拒绝未来不兼容插件。

## 11. 原子操作规范

本章同时定义 Agent 插件的运行协议边界。Agent 插件使用 `gcac.agent-plugin/v1` Manifest，只能声明受控原子操作，不注册 IIS、NGINX、RabbitMQ、Java 等产品 Handler。所有 Agent 插件默认不启用；导入、签名校验或权限审批完成不等于可参与资产选择，必须同时满足插件安装状态、权限审批和租户目录启用状态。缺少目录启用记录按禁用处理。

### 11.1 支持的操作

第一版支持：

| 操作 | 用途 |
| --- | --- |
| `preflight.assert` | 检查路径、程序或前置条件 |
| `file.backup` | 建立可回滚备份 |
| `file.atomic_replace` | 在同一目录中写临时文件并原子替换 |
| `file.restore` | 根据备份操作 ID 恢复文件 |
| `file.set_permissions` | 设置文件权限或属主 |
| `command.execute` | 执行受控程序和参数数组 |
| `service.control` | 控制允许的系统服务 |
| `tls.verify` | 验证 TLS 服务及证书指纹 |
| `windows.certificate.inspect_pfx` | 检查 PFX、证书私钥和指纹 |
| `windows.certificate_store.import_pfx` | 幂等导入 Windows Certificate Store |
| `windows.certificate_private_key.grant` | 向 IIS 应用池身份授予私钥读取权限 |
| `windows.iis.binding.capture` | 捕获 IIS HTTPS Binding 恢复快照 |
| `windows.iis.binding.update_certificate` | 更新 IIS HTTPS Binding 证书 |
| `windows.iis.binding.restore_certificate` | 从恢复账本恢复 IIS HTTPS Binding |

### 11.2 通用字段

每个操作必须包含：

```json
{
  "id": "install-certificate",
  "name": "安装证书",
  "stage": "install",
  "operationType": "file.atomic_replace",
  "schemaVersion": "1.0",
  "timeoutSeconds": 60,
  "dependsOn": ["backup-certificate"],
  "input": {}
}
```

### 11.3 操作 ID

- 在 `operations` 或 `rollback` 各自范围内唯一。
- 发布后保持稳定，便于账本、审计和排障识别。
- 使用动作含义命名，例如 `backup-certificate`，不用数组序号。

### 11.4 依赖关系

- `dependsOn` 只能引用同一操作集合中的已存在 ID。
- 禁止循环依赖。
- 阶段顺序仍是第一约束，依赖不得让后续阶段反向依赖前序阶段。

### 11.5 `command.execute`

正确示例：

```json
{
  "operationType": "command.execute",
  "input": {
    "program": "/usr/bin/keytool",
    "args": ["-list", "-keystore", "${variables.keystorePath}"]
  }
}
```

错误示例：

```json
{
  "operationType": "command.execute",
  "input": {
    "program": "/bin/sh",
    "args": ["-c", "keytool -list && systemctl restart app"]
  }
}
```

规则：

- `program` 必须是明确的可执行文件路径或 Agent Registry 允许的程序标识。
- `args` 必须是字符串数组。
- 禁止 Shell、管道、重定向、命令替换和多命令拼接。
- 程序和展开后的参数必须进入审计，但敏感参数必须脱敏。

### 11.6 `file.atomic_replace`

- 有覆盖风险时必须先执行 `file.backup`。
- 目标路径必须在 `filesystem` 权限内。
- 临时文件必须在目标文件同一目录创建，确保原子替换语义。
- 私钥默认使用最小权限。
- 不允许把内容写到权限声明外的临时目录后跨文件系统移动。

### 11.7 `tls.verify`

- 必须显式提供 Host 和端口。
- SNI 与连接 Host 不同时必须显式设置。
- 网络目标必须在 `network` 权限内。
- 能获得目标证书指纹时，应与期望指纹比较。
- 仅“端口可连接”不能作为证书部署成功的判断。
- `skipChainValidation=true` 只允许用于证书部署后的指纹验证，并且必须同时提供 `expectedFingerprint`。
- IIS、NGINX 等部署插件必须使用证书 Artifact 中的 SHA-256 指纹，不能由用户手工复制指纹作为普通变量。

### 11.8 Windows IIS 原子操作

- `windows.certificate.*` 必须声明 `certificate_store` 权限，第一版只允许 `LocalMachine/My`。
- `windows.iis.*` 必须声明 `iis` 权限，站点和应用池名称在变量展开后再次校验。
- `windows.iis.binding.capture` 必须早于 Binding 更新执行，并把原证书 Thumbprint 写入恢复账本。
- `windows.iis.binding.restore_certificate` 必须引用捕获操作 ID，禁止插件直接提供任意旧 Thumbprint。
- PFX 密码只能来自受控 Artifact 或 SecretRef，不得写入普通日志。

## 12. 阶段规范

正常操作阶段顺序固定为：

```text
prepare → backup → install → refresh → verify
```

回滚操作使用：

```text
rollback
```

规则：

1. `prepare` 只能检查，不得修改系统状态。
2. `backup` 建立回滚材料，不得提前覆盖目标。
3. `install` 写入证书、私钥、KeyStore 或配置。
4. `refresh` 重启或重新加载服务。
5. `verify` 验证最终 TLS 服务和目标证书。
6. 核心阶段禁止 `continueOnError=true`。
7. 不得通过调整数组顺序绕过阶段约束。

## 13. 回滚规范

### 13.1 必须声明回滚的操作

使用以下任一操作时必须声明 `rollback`：

- `file.atomic_replace`
- `file.set_permissions`
- `command.execute`
- `service.control`

### 13.2 文件回滚

文件回滚应引用对应备份操作：

```json
{
  "id": "restore-certificate",
  "name": "恢复原证书",
  "stage": "rollback",
  "operationType": "file.restore",
  "schemaVersion": "1.0",
  "input": {
    "backupOperationId": "backup-certificate"
  }
}
```

### 13.3 执行规则

- 失败后按回滚数组逆序执行。
- 回滚操作必须幂等。
- 回滚失败返回 `AGENT_ROLLBACK_FAILED` 并进入 `MANUAL_INTERVENTION`。
- `MANUAL_INTERVENTION` 状态下禁止自动无限重试。
- 备份账本必须记录目标路径、原始存在状态、权限和必要的属主信息。
- 回滚操作需要前序副作用成功后才有意义时，必须使用 `input.whenOperationCompleted`；前序操作未完成时 Agent 返回成功的跳过结果。

## 14. 资产绑定规范

应用资产插件策略示例：

```json
{
  "type": "AGENT",
  "agent": {
    "mode": "PLUGIN",
    "agentId": "agent-001",
    "certificateFormatId": "format-pem",
    "plugin": {
      "pluginPackageId": "plugin-package-001",
      "pluginVersionId": "plugin-version-001",
      "variableBindings": {},
      "secretBindings": {},
      "certificateArtifactBindings": {}
    }
  }
}
```

规则：

- 必须选择目标 Agent 上状态为 `MOUNTED` 的插件。
- 必须固定 `pluginPackageId` 和 `pluginVersionId`。
- 保存前必须调用绑定预览接口。
- 插件模式不要求 SiteAsset 和 ManagedTarget。
- 原生模式仍要求 SiteAsset 和 ManagedTarget，不得因为插件功能放宽历史校验。
- 更换 Agent、插件版本、变量、SecretRef 或 Artifact 映射后必须重新预览。

## 15. 资产直选与历史挂载兼容规范

新建和编辑应用资产时，必须直接选择已启用的插件包版本。选择器必须至少按应用资产的操作系统平台和框架类型过滤；Agent 的架构和 Capability 在绑定预览及执行计划编译时再次校验。不得要求用户先进入 Agent 详情或插件目录建立挂载关系。

`mountId` 是历史兼容字段。已保存 `mountId` 的旧资产继续校验原挂载关系；新资产不得生成 `mountId`。挂载相关 API 和数据表在兼容期内保留，但不得继续作为新功能的主路径。

### 15.1 插件选择和执行前检查

- 插件已启用。
- 高风险权限已审批。
- Agent 平台和架构兼容。
- Agent 上报 `agent.atomic_plan.execute`。
- Agent 支持插件声明的原子操作 Schema 版本。

### 15.2 历史挂载快照

兼容期内，历史挂载记录必须保存：

- Agent ID。
- 插件包和版本 ID。
- 包哈希。
- 兼容性快照。
- 权限快照和审批结果。
- 挂载状态和时间。

无论是否存在历史挂载，都不得在每次执行时静默切换到插件最新版本。

### 15.3 禁用和删除

- 禁用插件时应阻止新资产选择和新执行计划编译，并禁用其历史有效挂载。
- 已被历史应用资产引用的挂载不得无提示删除。
- 删除前必须提供引用检查或明确错误。
- 历史执行记录中的插件版本和权限快照不得随挂载删除而丢失。

## 16. 执行计划规范

控制面编译的执行计划使用 `gcac.agent-plan/v1`，至少包含：

- `planId`
- `tenantId`
- `agentId`
- `executionRunId`
- `executionStepId`
- 插件包 ID、版本 ID、包哈希和 Manifest 哈希
- `issuedAt`
- `expiresAt`
- `idempotencyKey`
- 权限快照
- 变量摘要
- 正常操作和回滚操作
- 签名 Key ID 和 HMAC-SHA256 签名

执行计划必须在实际 Execution Step 创建后编译，禁止使用伪造或占位 Run/Step ID 提前签名。

## 17. 幂等和账本规范

- 同一执行步骤和同一插件输入必须生成稳定幂等键。
- Agent 必须持久化计划状态、已完成操作、操作结果、备份和回滚结果。
- 已成功计划再次到达时返回缓存结果，不重复覆盖文件或重启服务。
- 进程中断后允许根据账本继续执行尚未完成的操作。
- 幂等键相同但计划内容不同必须拒绝，不能复用旧账本。

## 18. 审计和日志规范

必须能够追踪：

- 谁上传、审批、启用、禁用插件。
- 谁把哪个插件版本挂载到哪个 Agent。
- 哪个应用资产绑定了哪个挂载和版本。
- 哪个 Execution Run/Step 生成并派发了计划。
- Agent 实际执行了哪些原子操作。
- 是否发生失败、回滚或人工干预。

日志禁止包含：

- 私钥内容。
- 密码、Token 和 Secret 明文。
- 完整 PFX、JKS、PKCS#12 或 PEM Bundle。
- 未脱敏的敏感命令参数。

## 19. 开发流程

### 19.1 新增插件

1. 确认场景不能由现有原生 Handler 或工作流 DSL 更简单地解决。
2. 列出目标文件、程序、服务、网络和 Secret 权限。
3. 定义最小变量和 Artifact 输入。
4. 使用现有原子操作编排正常阶段和回滚。
5. 运行 Manifest Schema 校验。
6. 运行兼容性、权限和安全测试。
7. 在测试 Agent 上执行部署、验证、失败回滚和重复执行。
8. 完成权限评审和发布记录。

### 19.2 新增原子操作

只有现有原子操作无法表达真实且重复出现的需求时，才允许新增原子操作。新增时必须同时完成：

- DTO 和 Schema。
- Windows/Linux 支持矩阵。
- Agent Registry 注册。
- 权限模型。
- 输入和输出 Schema。
- 幂等和回滚语义。
- 签名计划兼容性。
- 单元测试、安全测试和文档。
- Agent 构建产物更新。

不得为了单个产品增加一个只服务该产品的“原子操作”。这种需求应优先重新设计为通用文件、服务、命令或验证能力。

## 20. 测试准入规范

### 20.1 Manifest 测试

- 正常 Manifest 校验成功。
- 缺失字段和非法类型失败。
- 未声明变量和 Artifact 引用失败。
- 重复操作 ID 和循环依赖失败。
- 阶段逆序失败。
- 有副作用但无回滚失败。
- Shell 请求失败。

### 20.2 权限测试

- 允许路径成功。
- 相似前缀路径越界失败。
- `..` 路径穿越失败。
- 未声明程序、服务和网络目标失败。
- 变量展开后越界失败。
- 高风险权限未审批时启用失败。

### 20.3 签名计划测试

- 正确签名成功。
- 任一字段篡改后失败。
- 过期计划失败。
- 目标 Agent 不匹配失败。
- 包哈希或 Manifest 哈希不匹配失败。
- 重复计划命中幂等账本。

### 20.4 原子执行测试

- 文件备份和原子替换。
- 原文件不存在时的安装和回滚删除。
- 权限及属主恢复。
- 程序参数数组执行。
- Shell 绕过拒绝。
- 服务刷新失败触发回滚。
- TLS 指纹验证成功和失败。
- 回滚失败进入 `MANUAL_INTERVENTION`。

### 20.5 双平台要求

修改 Windows Agent 源码后必须立即执行：

```powershell
gofmt -w .
go test ./...
go build -o gcac-agent.exe .
```

修改 Linux Agent 源码后必须立即执行：

```bash
gofmt -w <本次修改的 Go 文件>
go test ./...
bash ./build.sh
```

不得把“请用户自行编译”作为交付步骤。

## 21. 发布准入

插件只有同时满足以下条件才允许发布或启用：

- Manifest Schema 校验通过。
- 包哈希稳定。
- 签名状态符合环境策略。
- 权限清单完成评审。
- 高风险权限完成审批。
- Windows/Linux 兼容性声明有测试证据。
- 正常部署、TLS 验证、重复执行和失败回滚通过。
- 文档说明变量、Artifact、权限和故障处理。
- 没有明文 Secret、Shell 或未注册操作。

## 22. 升级规范

- 资产默认继续使用固定版本。
- 升级前比较变量、Artifact、权限和操作差异。
- 权限扩大必须重新审批。
- 删除必填变量、修改变量类型或改变 Artifact 语义属于 `MAJOR` 版本变化。
- 升级必须重新执行绑定预览和兼容性检查。
- 禁止直接修改历史插件包、历史 Manifest 或历史执行计划。

## 23. 废弃规范

- 废弃插件应先标记不可用于新挂载。
- 已绑定资产必须提供迁移目标和差异说明。
- 废弃不等于删除历史记录。
- 删除存储前必须确认没有活动挂载和应用资产引用。
- Agent 移除旧原子操作 Schema 前必须确认所有已固定插件版本均已迁移。

## 24. 代码审查检查表

提交 Agent 插件相关变更时，审查者必须逐项确认：

- [ ] 这是生产中的真实证书部署需求，不是为假想场景增加运行时。
- [ ] 现有原生 Handler、工作流 DSL 或原子操作不能更简单地解决。
- [ ] 没有新增产品名称、操作系统或版本硬编码分派。
- [ ] Manifest 数据结构完整且没有隐藏配置。
- [ ] 普通变量、SecretRef 和 Artifact 已正确分离。
- [ ] 权限符合最小权限原则。
- [ ] Shell 和命令字符串拼接被禁止。
- [ ] 所有副作用都有明确回滚。
- [ ] 签名、过期、目标绑定和幂等规则完整。
- [ ] Windows/Linux 测试和构建产物已同步。
- [ ] 前端文案已完成八种语言同步。
- [ ] 工作流 DSL、国际化和主题变量规范已检查并记录结论。
- [ ] Spec 任务状态和验证记录已回写。

## 26. 故障排查

- `PLUGIN_PERMISSION_DENIED`：检查插件是否启用、高风险权限是否审批，以及变量展开后的路径、程序、服务和网络目标是否在声明范围内。
- `AGENT_PLUGIN_MOUNT_INCOMPATIBLE`：检查 Agent 平台、架构、在线状态和 `agent.atomic_plan.execute` Capability，以及插件声明的原子操作 Schema 版本。
- `AGENT_PLAN_SIGNATURE_INVALID`：检查控制面与 Agent 的 `GCAC_AGENT_PLAN_SIGNING_KEY` 是否一致，计划内容是否被修改，目标 Agent、租户、运行和步骤绑定是否匹配。
- `AGENT_PLAN_EXPIRED`：检查控制面与目标宿主的时间同步状态后重新派发执行计划。
- `AGENT_ROLLBACK_FAILED`：读取 Agent 原子计划账本和操作结果，按 `MANUAL_INTERVENTION` 处理，不得自动重复覆盖现场。

## 27. 规范同步要求

修改以下任一内容时，必须检查并同步更新本规范：

- Agent 插件 DTO 或 Manifest Schema。
- 变量类型、SecretRef 或 Artifact 绑定规则。
- 权限 Scope 或风险等级。
- 原子操作类型、输入 Schema 或阶段。
- 签名计划字段和签名算法。
- Agent Registry、幂等账本或回滚状态。
- 插件挂载、应用资产绑定和前端配置流程。
- 内置 Agent 插件目录和发布流程。

如果检查后无需更新，交付说明必须明确记录“已检查且无需更新”。
