# 工作流模板管理及编写规范

## 适用范围

本文档定义 GCAC 项目当前支持的工作流模板管理规则和工作流 DSL 编写标准。该 DSL 是项目内领域协议，不是行业通用标准。任何生成、保存、校验、执行工作流 DSL 的代码，都必须以本文档和后端 schema 为准。

工作流模板是数据库中的可版本化 DSL 实体。插件可以包含只读的内部工作流版本，并作为用户工作流的复制来源；工作流模板不是独立 npm 包，也不得再由运行时文件扫描器创建。

相关代码位置：

- 后端 DTO：`backend/src/modules/workflow-templates/dto/workflow-templates.dto.ts`
- 后端 schema：`backend/src/modules/workflow-templates/schema/workflow-templates.schema.ts`
- 后端运行时：`backend/src/modules/workflow-templates/domain/workflow-templates.domain-service.ts`
- 后端画布编译器：`backend/src/modules/workflow-templates/domain/workflow-canvas.compiler.ts`
- 前端画布模型：`web/src/views/workflows/workflow-canvas.model.ts`
- 前端画布编辑器：`web/src/views/workflows/WorkflowCanvasEditor.vue`

## 统一部署输入契约修订（2026-07-30）

Workflow DSL 的部署输入声明统一使用 `DeploymentInputContractV1`，Schema 唯一实现位于 `backend/src/modules/deployment-inputs/schema/deployment-input-contract.schema.ts`。Workflow 与 Agent Plugin 共享变量 Source、配置模式、生命周期、覆盖策略、HTTP/SSH Connection、Credential Slot 和 Artifact Slot；Workflow Step 只通过声明后的 `connectionRef`、Credential Slot 和 Artifact Slot 消费解析结果。

新增任何厂商插件时，宿主端不得新增变量传递、字段猜测或产品分派代码。插件只能通过 `DeploymentInputContractV1` 声明 Slot，通过 `InputBindingsV1` 保存覆盖值，并由统一 Resolver 生成 `ResolvedDeploymentInputV1`。如果新增插件需要修改资产服务、部署计划、执行器或前端表单才能传入厂商变量，说明插件合同不完整，必须拒绝合入。
标准资产上下文中的厂商扩展字段只能放入对象既有的 `metadata` 容器，Workflow 通过 `target.metadata.<field>` 等标准路径读取；禁止把 `sniCertificate`、`certkey` 等厂商字段提升为 `DeploymentAssetContextV1` 的核心属性。

运行时只接受 `ResolvedDeploymentInputV1`（统一解析后的部署输入）快照，不得重新合并用户变量、资产变量或秘密值。解析后的普通变量、Credential Slot 和 Artifact Slot 只能通过 `variables`、`credentials`、`artifacts`、`connections` 和 `asset` 结构化命名空间访问；历史 step 结果和系统值分别通过 `steps`、`system` 访问。不得将任何输入或 step 输出再次投影到模板根作用域。

正式 Source 仅允许 `asset`、`binding`、`default`、`derived`、`system`、`step_output`。普通变量类型不得包含 `credential` 和 `certificate`。`asset_ssl`、`dsl`、普通 Credential/Certificate 变量和变量内 `artifactContract` 属于 Spec 033.6 的硬切迁移对象，不得用于新增或发布新版本工作流。

工作流运行接口（模板预览、整模板试跑和单节点试跑）统一接收 `resolvedInput: ResolvedDeploymentInputV1`，不得再从调用方接收或拼接旧的 `userVariables`、`assetVariables`、`connectionBindings`、`certificateMaterials` 输入。`resolvedInput` 必须包含 `assetContext`、`variables`、`connections`、`credentials`、`artifacts`、`provenance`、`sensitivePaths`、`issues`、`executable` 和 `resolvedSha256`；`executable=false` 或存在阻断问题时，运行在进入任何 DSL step 前失败。Step 输出只能通过 `stepOutputs` 进入后续上下文，系统派生值只能通过 `systemValues` 进入上下文。旧字段仅允许留在迁移测试 Fixture 中，不得作为生产 API 兼容入口恢复。

部署输入的阶段语义固定如下：配置保存使用 `save`，创建或更新计划以及 Dry-run 使用 `preflight`，正式执行使用 `execute`。这些入口必须复用同一个生产解析编排服务，由它组合固定 Contract、标准 Asset Context、Effective Binding、Credential Snapshot、Artifact Snapshot 和 `UnifiedDeploymentInputResolver`；任何入口都不得复制合并顺序或重新解释 Source。对于不含运行时注入值和 Step 输出的相同输入，`preflight` 与 `execute` 的 `resolvedSha256` 必须一致。

Runtime Adapter 只负责根据 `AGENT_ATOMIC` 或 `WORKFLOW_DSL` 选择执行协议、固定版本身份、执行目标和路由。Adapter 必须显式接收 `ResolvedDeploymentInputV1` 并原样写入 `resolvedDeploymentInput`；`workflowRequest` 只允许保留 WorkflowTemplate/WorkflowVersion、PluginVersion、Binding、Capability、Runner、Gateway 和资源锁等执行身份，不得携带 `parameterBindings`、`variableBindings`、`connectionBindings`、`credentialBindings`、`certificateArtifactBindings` 或秘密值。缺少或无法校验 `resolvedDeploymentInput` 时，必须在调用 Agent、Gateway、SSH 或 HTTP 等外部 Runtime 前失败关闭。

### 部署输入界面与 Slot 最小化

`DeploymentInputContractV1` 同时定义运行时输入和通用配置界面。前端必须只依据 `configurationMode`、`bindingPolicy`、`source` 与 Projection 渲染，禁止按模板名称、厂商或 Runtime 类型编写展示分支。

- 默认区只显示 `configurationMode=required && bindingPolicy=required_binding` 的变量和连接字段，以及 `configurationMode=required` 的 Credential / Artifact Slot。
- `bindingPolicy=fixed` 或来源为 `asset`、`derived`、`system`、`step_output` 的字段不得展示编辑控件、不得写入 `InputBindingsV1`；它们只能在高级区显示有效值和来源。
- `bindingPolicy=default_overridable` 的字段进入高级区；用户可按需覆盖，但默认值已能满足执行时不得在默认区要求重复填写。
- `configurationMode=runtime` 仅作为高级区运行时说明，不得提供编辑控件。
- Workflow 作者应避免声明未被运行步骤消费的 Slot；历史或用户模板是否清理由模板评审和兼容性评估决定，前端不得据此添加工作流特判。

## 工作流来源与文件保留

运行时创建入口只有一种：从已启用 `WORKFLOW_DSL` PluginVersion 的 `certificate.deploy` 或 `certificate.rollback` 能力复制。通用空白创建、文件模板扫描、文件模板创建和文件模板套用 API 均不得暴露。

- `backend/src/modules/workflow-templates/builtin-workflows` 中的历史内置文件继续受 Git 跟踪，但只作为发布资源和迁移证据保留，不参与运行时扫描或用户选择。
- `data/workflows` 中的用户文件不得因升级删除或改写，但不再由工作流页面扫描。后续导入流程必须先形成受控 PluginVersion 或显式迁移为数据库工作流。
- 禁止新增 `docs/工作流样例`、`docs/workflows` 等第三套 DSL 来源。
- 插件来源查询只返回 `ENABLED`、`WORKFLOW_DSL`、能力为 `certificate.deploy`/`certificate.rollback`、存在 PluginWorkflowBinding、源版本已发布且内容哈希一致的候选项。
- `AGENT_ATOMIC` 插件不能转换为工作流。`WORKFLOW_DSL` 插件可以同时声明 `certificate.deploy` 和 `certificate.rollback`，两者应绑定同一个内部 WorkflowVersion；回滚使用该 DSL 的 `rollback` 分支，不由宿主拼接第二份 DSL。

工作流来源字段：

| origin | 所有者与用途 | 编辑规则 |
| --- | --- | --- |
| `user` | 用户自行维护的工作流 | 用户可编辑、发布、停用 |
| `plugin_internal` | PluginVersion 内部不可变工作流 | 普通用户只读，不得重命名、建草稿、发布或停用 |

插件复制来源不再是第三种 origin。由插件生成的 `origin=user` WorkflowVersion 可以保存可选 `pluginSource`：Plugin ID、PluginVersion ID、Capability、源 WorkflowTemplate ID、源 WorkflowVersion ID、源内容哈希和复制时间。该字段只用于审计和用户显式套用，不参与运行时回查。

正式工作流管理列表 `GET /api/v1/workflows` 必须返回 `plugin_internal` 和 `user` 两类记录，并按授权过滤；工作流执行选择、从插件生成草稿的目标筛选仍必须只允许 `user`。历史 `legacy`、`plugin_derived` 记录必须通过递增迁移归并为 `user`，不得继续作为当前 API 来源枚举。

`GET /api/v1/workflow-templates` 是迁移期兼容接口，不得作为前端或新业务主链入口；正式业务使用 `/api/v1/workflows`。

正式工作流列表对 `plugin_internal` 按“插件 ID + 工作流资源路径”合并历史重复记录，只保留一个展示行；展示行和当前版本必须按 DSL `metadata.version` 的 SemVer（语义化版本）选择最新已发布版本。数据库整数 `WorkflowTemplateVersion.version` 仅用于内部存储顺序，不得作为插件内置工作流的用户可见版本，也不得参与最新版本判断。历史数据库记录不删除；版本查询必须合并同组记录，并按 DSL SemVer 去重和倒序展示，避免破坏已有 Binding 和执行历史。

内置插件新 patch 版本启动注册完成后，宿主必须跨业务租户把同一 major/minor 版本线上的旧 PluginVersion 引用升级到最新版本；内置插件的 `SYSTEM` 存储归属不得限制业务资产、PluginBinding、CapabilityAssignment、Host Channel 或 DeviceAsset 的引用更新。插件内置版本页只读，不提供新增版本、编辑版本说明或切换当前版本操作；从插件派生用户工作流时仍可显式选择历史 DSL SemVer。

应用资产创建和编辑页面选择固定 WorkflowVersion 时，插件内置工作流的下拉选项同样必须显示 DSL SemVer，不得显示数据库整数版本；同一 SemVer 的历史重复记录只显示一次。选项提交值仍使用不可变 `workflowVersionId`，归并时必须优先保留资产当前已固定的版本 ID，其次保留工作流当前版本 ID，避免历史资产回显为空或被静默改绑。

正式工作流列表项必须为插件内置工作流返回 `capabilities` 能力键集合，并从同一“插件 ID + 工作流资源路径”归并组的全部 Binding 计算；同一 DSL 同时声明 `certificate.deploy` 和 `certificate.rollback` 时，列表中只能显示一条插件内置工作流记录，且能力集合必须同时包含部署和回滚。用户工作流仍返回 `origin=user`，不要求依赖插件能力字段。

工作流管理页默认只显示用户工作流和包含 `certificate.deploy` 的插件内置工作流。连接测试、发现等非部署工作流仍由 `GET /api/v1/workflows` 返回，但必须通过默认关闭的“显示非部署工作流”开关显式展示；前端不得根据工作流名称猜测类型。

前端来源展示必须通过 vue-i18n 输出：`plugin_internal` 使用“插件内置”对应的语言 key，`user` 使用“自定义”对应的语言 key。接口不得把未解析的 i18n key 作为用户可见文案返回或直接渲染。

工作流运行必须显式选择 `executionBranch=deploy|rollback`。`deploy` 执行同一 WorkflowVersion 的 `steps`，`rollback` 执行同一 WorkflowVersion 的 `rollback` 数组；rollback 不是主流程的线性 stage，也不是独立的第二份工作流。

## 模板身份与元数据

模板身份由 DSL 的 `metadata.name` 决定，必须使用稳定、唯一、全小写的英文标识和短横线命名。发布后不得因为显示名称、Logo、平台或执行方式变化而修改；`metadata.displayName` 只用于界面展示，不作为关联主键。

推荐的模板元数据如下：

| 字段 | 必填 | 说明 |
| --- | --- | --- |
| `name` | 是 | 稳定模板 ID |
| `displayName` | 否 | 面向用户的名称 |
| `description` | 否 | 模板能力和适用场景说明 |
| `version` | 新模板必填 | SemVer 模板版本，例如 `1.1.0` |
| `logoUrl` | 否 | HTTP(S) URL 或本地 Web 路径 |
| `platforms` | 推荐 | 目标平台或设备标识 |
| `updateMethods` | 推荐 | 更新通道：`ssh`、`curl`，混合模板可同时声明 |
| `maintainer` | 推荐 | 维护团队或责任人 |
| `homepage` | 否 | 文档、发布记录或维护入口 |
| `category` | 否 | 模板分类 |
| `tags` | 否 | 搜索和能力标签 |

`platforms` 和 `updateMethods` 是声明字段，不是权限放行字段。后端仍需在执行前检查资产能力、凭据类型、连接参数和目标平台，不得仅凭模板元数据执行。

## 模板版本与发布

- 新模板从 `1.0.0` 开始；预发布版本必须使用合法 SemVer。
- 修复错误或不改变输入输出契约的调整递进 patch；增加兼容能力、平台或可选步骤递进 minor；改变变量契约、执行语义、必需凭据或回滚行为递进 major。
- 原模板文件不可覆盖后继续使用旧版本号。数据库 `WorkflowTemplateVersion.version` 是工作流编辑历史的整数版本，与模板 SemVer 不同。
- 内置模板必须经过代码评审、Schema 校验、执行计划预览、回滚检查和平台试跑后随版本发布。
- 从插件创建工作流后，复制内容必须形成 `origin=user` 独立草稿；后续源插件停用、升级或删除不影响该用户工作流执行。
- 发布新的 `WORKFLOW_DSL` PluginVersion 时，宿主自动创建新的 `plugin_internal` WorkflowVersion 和 Binding；已经存在的 `origin=user` 工作流只允许用户显式套用新版本，不得自动更新。
- 为已有工作流从插件生成草稿时，必须保留目标工作流自己的稳定 `metadata.name`。

### 版本治理边界

工作流版本管理必须同时保留三种互不替代的版本事实：

| 版本 | 使用位置 | 管理规则 |
| --- | --- | --- |
| Manifest 插件版本 | PluginVersion 的 `manifest.version` | 插件包的不可变 SemVer；同一 `pluginId + version` 内容不可覆盖 |
| Workflow DSL 版本 | 内置 DSL 的 `metadata.version` | Workflow 内容的不可变 SemVer；内容变化必须显式递进 |
| 数据库工作流版本 | `WorkflowTemplateVersion.version` | 同一 WorkflowTemplate 的编辑/发布历史整数；每次新草稿或发布按数据库规则递增 |

- 内置插件的 Manifest 与 DSL 版本必须通过 `scripts/update-plugin-version.mjs` 更新；运行时导入不得自动猜测或递增 DSL 版本。
- 插件版本冲突、资源映射错误或 DSL 发布失败不得让整个后端启动失败。启动器必须逐项记录结构化告警并继续处理其他插件；数据库连接、应用构造和路由注册等核心失败仍然中止启动。
- 插件版本管理界面和 API 必须展示全部可见版本、状态、包/资源/Workflow 哈希以及五类运行引用数量。不得把最高 SemVer 当成“当前运行版本”；当前版本必须根据实际运行引用或明确状态判断。
- 版本切换只能由管理员显式执行，且必须在一个事务内同步更新插件绑定、能力指派、主机管理通道、服务资产元数据和设备资产插件版本引用。任何一步失败都必须回滚。
- 版本切换不修改历史 PluginVersion、历史 DSL 或用户 `origin=user` 工作流。升级用户工作流只能通过显式套用创建新的不可变草稿/版本。
- DSL 正式文件来源仍只有 `backend/src/modules/workflow-templates/builtin-workflows` 和 `data/workflows`；不得新增第三套样例目录，也不得通过文件扫描器绕过 PluginVersion 发布流程。

## 模板安全与扩展边界

- 禁止在 DSL 模板中写入明文密码、Token、私钥或生产凭据。
- Logo 和 homepage 只用于展示，不能参与执行、签名或权限判定。本地 Logo 禁止使用 `file://`、`data:` 和包含 `..` 的越界路径。
- 模板失败时必须保留结构化校验错误，不能伪装成可用模板。
- 插件复制来源必须读取 WorkflowVersion.pluginSource，不得依赖工作流名称、厂商、平台或 Agent 类型推断。

前端动作约定：

- “从插件新建工作流”：复制一个允许的插件能力源版本，创建 `origin=user` 草稿并写入可选 `pluginSource`。
- “从插件生成草稿”：仅为 `origin=user` 工作流复制一个插件能力源版本，创建新的 draft version；来源选择必须返回所有可访问的 ENABLED 插件版本，并显示插件版本和工作流整数版本；目标工作流不能是 `plugin_internal`。

版本规则：

- 从插件生成草稿不会修改历史版本，本质上是创建新的不可变版本。
- 内容与同一工作流已有版本完全一致时不得因为“插件来源”额外创建重复版本；只有用户明确创建新草稿且版本策略允许时才产生新版本。
- 套用到已有工作流时，目标工作流自己的稳定标识 `metadata.name` 必须保留。
- PluginVersion 使用 Manifest SemVer；数据库中的 `WorkflowTemplateVersion.version` 是工作流编辑历史的递增整数，两者不得混用。
- 只修复向后兼容的问题递进 patch；增加向后兼容能力递进 minor；产生不兼容行为递进 major。禁止更新模板内容但保留原版本号。
- 数据库中的 `WorkflowTemplateVersion.version` 是工作流草稿/发布历史的递增整数，与文件模板插件的 `metadata.version` 是两套不同版本，不得混用。

## 顶层结构

```json
{
  "apiVersion": "gcac.workflow/v1",
  "kind": "CurlSshWorkflow",
  "metadata": {
    "name": "nginx-cert-update",
    "displayName": "Nginx 证书更新",
    "description": "通过 SSH 更新 Nginx 证书文件并验证 HTTPS 服务。",
    "version": "1.0.0",
    "logoUrl": "/plugin-logos/nginx.svg",
    "platforms": ["linux"],
    "updateMethods": ["ssh"],
    "maintainer": "GCAC",
    "homepage": "https://example.com/plugins/nginx-cert-update",
    "category": "certificate",
    "tags": ["nginx", "certificate"]
  },
  "inputContract": {
    "apiVersion": "gcac.deployment-input/v1",
    "variables": {},
    "connections": {},
    "credentials": {},
    "artifacts": {}
  },
  "steps": [],
  "rollback": []
}
```

字段要求：

- `apiVersion` 必须是 `gcac.workflow/v1`。
- `kind` 必须是 `CurlSshWorkflow`。
- `metadata.name` 必填，必须是稳定英文标识。
- `metadata.displayName` 可选，用于插件市场显示名称。
- `metadata.description` 可选，用于插件卡片和详情说明。
- `metadata.version` 可选以兼容历史模板；新建模板必填，格式必须符合 SemVer，例如 `1.0.0`、`1.2.0-beta.1`。
- `metadata.logoUrl` 可选，支持 `http://`、`https://` 远程 URL，也支持 `/plugin-logos/example.svg`、`plugin-logos/example.svg` 这类前端可访问的本地 Web 路径。
- `metadata.logoUrl` 禁止使用 `file://`、`data:`、任意其他协议或包含 `..` 的越界路径。这里的“本地路径”是浏览器可访问的静态资源路径，不是服务器任意磁盘绝对路径。
- `metadata.platforms` 用于声明插件面向的平台，必须是非空字符串数组。推荐使用稳定的小写标识，例如 `linux`、`windows`、`synology-dsm`、`apache`、`nginx`，禁止把展示文案当平台标识。
- `metadata.updateMethods` 用于声明插件实际使用的更新通道，当前只允许 `ssh`、`curl`。它描述模板怎样连接并修改目标，不应根据标签或步骤名称猜测。
- `metadata.maintainer` 可选，用于标识维护团队或责任人；内置插件推荐统一填写 `GCAC`，用户插件应填写实际维护者。
- `metadata.homepage` 可选，必须是 HTTP(S) URL，用于指向插件说明、发布记录或维护入口。
- `metadata.category` 和 `metadata.tags` 可选，用于插件市场分类、搜索和能力识别。
- `inputContract` 必填，是变量、Connection、Credential 和 Artifact 的唯一声明位置。顶层 `variables` 和 `connections` 已删除，Schema 必须拒绝。
- `steps` 必填，必须是非空数组。
- `rollback` 可选，用于主流程失败后的回滚步骤。

## 插件管理规范

历史 DSL 文件不再服务运行时模板选择。内置文件仍位于 `backend/src/modules/workflow-templates/builtin-workflows`，用户文件仍位于 `data/workflows`，但工作流实例和版本只写入数据库；用户首次创建来源只接受统一 PluginVersion 的受控能力。

内置 `WORKFLOW_DSL` 插件可以将正式 DSL 文件作为包资源导入不可变 PluginVersion，但插件目录不得再拼接 Workflow Template 或 Agent Deployment 旧目录项。用户插件统一通过 PluginVersion 导入接口安装；`data/agent-plugins` 不再作为插件市场扫描目录。

## 资产执行绑定

- 受管目标 `MANAGED_TARGET + PLUGIN` 的唯一事实来源是 `CapabilityAssignment + PluginBinding`。
- 受管目标 `MANAGED_TARGET + WORKFLOW_OVERRIDE` 的唯一事实来源是 `WorkflowExecutionBinding`，对应 ApplicationAsset 的 ACTIVE Assignment 必须停用。
- 非受管目标固定为 `WORKFLOW + WORKFLOW`，只引用 `WorkflowExecutionBinding`，不得创建 PluginBinding 或 CapabilityAssignment。
- 插件执行与工作流执行严格互斥；DeploymentPlan 快照也必须恰好包含一种 `ResolvedExecutionSource`。
- `LATEST_PUBLISHED` 必须在计划创建阶段解析并固定为具体 WorkflowVersion，执行和重试不得回查最新版本。
- WorkflowExecutionBinding 统一保存版本策略、Runner、Gateway、连接、变量、凭据引用和证书产物绑定；不得使用 PluginBinding 保存普通工作流配置。

设备管理 DSL 的 Manifest、动态表单、标准发现、证书产物、Promotion 和宿主零厂商规则见 `docs/项目规范/20260725-统一设备与工作流插件开发规范.md`。

### 身份与版本

- `metadata.name` 是插件稳定 ID。发布后不得随展示名称、平台或实现调整而变化。
- `metadata.version` 是插件发布版本，采用 SemVer；数据库工作流整数版本不是插件版本。
- 修改执行步骤、变量契约、回滚逻辑、平台范围、更新方式、Logo、说明或维护信息，都必须递进插件版本。
- 插件文件不得原地覆盖后仍保留旧版本号；否则无法审计某个工作流究竟来自哪次发布。

### 平台与更新通道

- `platforms` 描述适用目标，例如操作系统、设备产品或服务类型。一个插件可以面向多个平台，但不应使用 `all` 掩盖未验证的平台。
- `updateMethods` 描述真实执行通道。包含 SSH/SFTP/SCP 节点的插件声明 `ssh`；包含 HTTP/CURL 节点的插件声明 `curl`；混合流程同时声明两者。
- 平台兼容性必须由模板作者明确维护。运行前仍需根据资产能力、凭据类型和连接方式做后端校验，插件元数据不能替代执行前检查。

### 发布与更新

- 内置插件通过代码评审和系统版本发布；文件、Logo、测试和规范必须在同一变更中提交。
- 用户工作流模板通过导入或替换 `data/workflows` 中的 DSL 文件更新；用户插件必须通过统一插件包导入接口发布不可变 PluginVersion，禁止恢复 `data/agent-plugins` 目录扫描和旧 Agent 包启停 API。
- 插件更新只影响插件市场中的后续创建操作，不自动改写已经创建的工作流，也不修改历史工作流版本。
- 需要升级现有工作流时，必须由用户显式“套用模板”，创建新的不可变 draft version，再验证和发布。

### 使用状态

- 当前“正在使用”以插件稳定 ID `metadata.name` 与数据库工作流 `name` 的匹配关系判定。
- 从插件创建工作流时保留 `metadata.name`，因此可以在不增加新数据库字段的情况下统计使用状态。
- 如果未来允许一个插件创建多个不同稳定 ID 的工作流，应新增明确的 `sourcePluginId` 和 `sourcePluginVersion` 持久化字段，不能继续依赖名称猜测。

### 安全与质量

- 插件不得包含明文 Secret、私钥或真实生产凭据。
- 远程 Logo 和主页只是展示信息，不参与执行、签名或权限判定。
- 新插件必须至少通过 Schema 校验、执行计划预览、回滚检查和目标平台真实试跑后，才能标记为可发布。

## 导入与覆盖

前端工作流编辑器支持在 DSL 面板中直接导入 DSL JSON，或选择本地 DSL 文件覆盖当前画布草稿。

规则如下：

- 导入入口位于 `web/src/views/workflows/WorkflowCanvasEditor.vue` 的 DSL 面板。
- 导入动作只覆盖浏览器中的当前画布草稿，不会自动保存到后端。
- 导入完成后，必须显式点击“保存草稿”，才会创建新的工作流版本。
- 导入 DSL 时，顶层结构必须满足：
  - `apiVersion = gcac.workflow/v1`
  - `kind = CurlSshWorkflow`
  - `metadata` 为对象
  - `inputContract` 为 `DeploymentInputContractV1` 对象
  - `steps` 为非空数组
- 当前画布会把 DSL 转成纵向阶段流程图，并自动重新排列节点。

画布草稿本身也必须硬切到统一输入契约：

- Canvas 根字段只允许保存 `inputContract`、`nodes`、`edges`、视口和纯 UI 草稿状态；不得保存第二份顶层 `variables` 或 `connections`。
- `inputContract` 必须是完整的 `gcac.deployment-input/v1`，同时包含 `variables`、`connections`、`credentials` 和 `artifacts` 四个对象。后端画布校验与编译接口均拒绝缺失契约或旧根字段，禁止从节点或旧变量表反向推导兼容契约。
- 普通变量类型只允许 `string`、`number`、`boolean`、`enum`、`object`、`array` 和 `file`。Credential 和 Artifact 必须分别放入独立 Slot，禁止伪装成普通变量。
- HTTP、SSH、SFTP、SCP 以及回滚节点只保存命名 `connectionRef`；Host、Port、Username、TLS、Host Key 和 `credentialSlot` 只在 `inputContract.connections` 声明。
- 前端导入正式 DSL 时直接复制 `inputContract`；再次保存时后端编译器原样校验该契约，不提供旧 DSL 或旧 Canvas 双读。

兼容说明：

- 画布当前主要可视化编辑主流程节点、阶段、变量和常用节点字段。
- 对于画布暂未直接暴露的高级字段，例如：
  - `http.request.headers`
  - `retry`
  - `extract`
  - 高级 `assert`
  - 自定义 `rollback`
- 导入时画布会尽量保留这些字段；再次保存或试跑时必须交给后端画布编译器生成正式 DSL，避免前端成为 DSL 事实源。
- 但如果用户在画布中把对应节点类型改掉，或删除原节点，这些透传字段也会随之丢失。这是当前版本的已知边界。

## 阶段规范

每个 step 可以声明 `stage`：

```json
{
  "name": "reload_nginx",
  "type": "ssh",
  "stage": "refresh"
}
```

支持的阶段：

| stage | 中文名 | 用途 |
| --- | --- | --- |
| `prepare` | 准备 | SSH 认证登录、CURL 认证、凭据获取、前置上下文准备 |
| `backup` | 备份 | 保存变更前状态、生成回滚材料 |
| `install` | 安装 | 上传、写入或替换证书/配置/文件 |
| `refresh` | 刷新 | 重载服务、刷新缓存、触发生效 |
| `verify` | 验证 | 检查 HTTP 状态、证书指纹、服务状态、人工验收 |

执行规则：

- 只要 `steps` 中任一 step 声明了 `stage`，后端按固定阶段顺序执行：`prepare` → `backup` → `install` → `refresh` → `verify`。
- 同一阶段内保持原始数组顺序。
- 没有声明 `stage` 的旧模板保持原始数组顺序，保证兼容。
- 新增 DSL 必须显式声明 `stage`。

## 变量规范

### Agent 发现资产字段

工作流变量需要使用 Agent 已发现的站点配置时，必须通过统一输入契约声明 `source.kind=asset`，并使用 `source.path` 指向 `DeploymentAssetContextV1` 的正式字段。取值优先级固定为：单次执行覆盖 → 应用资产 Binding → Agent 发现资产字段 → DSL 默认值。资产字段存在时不得被 `default` 静默覆盖；资产字段缺失且变量声明了 `default` 时，Resolver 才能回退默认值。

Agent 管理的证书部署工作流统一读取 `target.certificateLocation`：

| 用途 | `source.path` |
| --- | --- |
| PEM 证书路径 | `target.certificateLocation.certificatePath` |
| PEM 私钥路径 | `target.certificateLocation.privateKeyPath` |
| KeyStore 路径 | `target.certificateLocation.keystorePath` |
| 框架站点配置文件 | `target.certificateLocation.sourceConfigPath` |
| 服务名 | `target.certificateLocation.serviceName` |
| 程序路径 | `target.certificateLocation.programPath` |

Apache 证书切换工作流必须把 `apacheServiceName`、`apacheSiteConfigPath`、`certificateFilePath` 和 `certificateKeyFilePath` 分别绑定到上述服务名、配置文件、证书和私钥字段。历史默认值可以继续保留用于旧 Agent 或未发现目标，但当 `confidence=EXACT` 的发现位置与默认值冲突时，宿主必须以 `DEPLOYMENT_INPUT_DEFAULT_OVERRIDES_DISCOVERED_LOCATION` 拒绝创建部署计划。

普通变量定义只写在 `inputContract.variables` 中：

```json
{
  "certificateFilePath": {
    "type": "string",

    "default": "/etc/ssl/certs/site.pem",

  "backupRoot": {

    "required": true,
    "default": "/var/backups/gcac-certs",
    "description": "证书备份根目录"
  },
  "frameworkType": {
    "type": "enum",
    "required": true,
    "default": "NGINX",
    "enum": ["NGINX", "APACHE", "TOMCAT", "IIS", "CUSTOM"],

  },

    "required": false,

```

支持的变量类型：

- `string`
- `number`
- `boolean`
- `enum`
- `object`
- `array`，用于 `foreach.itemsPath` 消费的有序集合，禁止继续用 `object` 伪装数组
- `file`

Credential（凭据）和 Artifact（产物）不是普通变量类型，必须分别声明在 `inputContract.credentials` 和 `inputContract.artifacts`。禁止在 `variables` 中重新声明或复制同名占位变量。

工作流 DSL 不提供证书 TLS 验证步骤。所有 `certificate.deploy` 和 `certificate.rollback` 工作流完成设备写入后，由部署宿主追加独立 `VERIFY` 节点并调用 `certificate.verify/v1` 能力；默认由平台后端发起，部署目标明确指定 Gateway Agent 时由该 Gateway 发起。插件和 DSL 禁止声明 `tls_probe`、自行比较远端证书指纹或用厂商控制面查询代替外部 TLS 握手验证。

证书工作流的边界固定如下：

- DSL 只允许描述证书材料写入、设备绑定更新、配置检查、服务生效和回滚，不允许新增任何证书部署后网络验证 step。
- 禁止变量或输出字段 `verifyHost`、`verifyPort`、`verifyServerName`、`remoteCertificateSha256`、`remoteFingerprintSha256`、`localCertificateSha256`；连接地址、SNI、端口和目标指纹由宿主从受管目标快照生成 `certificateVerification`。
- 工作流 `extract` 只能提取厂商操作回执和资源标识，不得提取远端证书指纹后写入 `verify`；设备控制面返回的 Thumbprint 只能作为部署审计证据，不能替代宿主 TLS 握手。
- Workflow Runtime 不得自行追加 VERIFY，也不得调用 Gateway；Execution 宿主在 CUSTOM 成功后统一追加并主动派发 `CONTROL_PLANE_TLS` 或 `GATEWAY_FORWARD/probe.tls`。
- 代码审计必须确认 DTO、Schema、Domain Runtime、画布模型和所有内置工作流均不接受 `tls_probe`，结果同步服务不读取 Workflow extracted 指纹作为验证结果。

恢复工作流必须使用 `checkpoint_verify` 在首个远端写操作前校验恢复账本快照的规范化 SHA-256。`valuePath` 指向待恢复快照，`expectedHash` 引用账本保存的哈希；不一致时工作流失败关闭并进入人工介入，插件不得自行忽略或覆盖哈希。

变量引用格式：

```text
{{artifacts.serverCert.outputs.certFile.content}}
{{variables.certificateFilePath}}
{{credentials.apiCredential.username}}
{{steps.prepare_auth.extracted.accessToken}}
{{steps.login.output.body.token}}
```

规则：

- 变量名必须是英文标识符：`^[a-zA-Z][a-zA-Z0-9_]*$`。
- 引用变量前必须先在 `inputContract.variables` 中声明，或由上游 extractor 产出。
- Credential Slot 只声明允许的凭据种类和配置要求，用户绑定只保存 `{ credentialId }`；后续节点通过 `{{credentials.<slot>}}` 引用运行时快照。
- Artifact Slot 必须使用 `artifactContract.outputs` 声明所需产物；后续节点通过 `{{artifacts.<slot>.outputs.<output>.content}}` 或 `contentBase64` 引用真实内容。
- Credential Slot 和敏感 Artifact 输出默认按敏感数据处理，不得进入普通变量、日志或用户可见快照。
- 推荐证书 Artifact Slot 使用业务语义命名，例如 `serverCert`、`clientCert`；不要把所有证书都硬编码成 `certificate`。
- `certificate.pem`、`certificate.privateKey` 是早期兼容字段，新模板不得继续使用；新模板必须使用 `outputs`。
- PEM 产物输出项中，`public` 表示叶子证书，`fullchain` 表示叶子证书加证书链且不包含私钥，`chain` 表示单独证书链，`private` 表示私钥，`bundle` 表示格式配置生成的合并 PEM，可能包含私钥。给 Web 服务的 `certFile` 槽位优先绑定 `fullchain`。
- 证书部署目的路径必须在 DSL 中显式声明。表单友好的模板优先使用 `certificateFilePath`、`certificateKeyFilePath`、`backupRoot` 这类标量变量；只有确实需要成组路径结构时才使用 `certificatePaths` 对象。
- 禁止把密码、token、私钥、PFX 明文写进 DSL。

### 应用资产目标变量约定

工作流类型的应用资产可以从 DSL 变量定义中生成资产目标表单，避免资产创建页面和工作流模板重复维护同一组站点信息。证书部署类工作流只要需要绑定到具体站点，就必须优先声明以下变量名；变量名是平台约定，不要在模板中改成同义词。

| 变量名 | 类型 | 是否必填 | 说明 |
| --- | --- | --- | --- |
| `frameworkType` | `enum` | 是 | 框架类型。枚举固定为 `NGINX`、`APACHE`、`TOMCAT`、`IIS`、`CUSTOM`。 |
| `siteName` | `string` | 是 | 用户可见站点名，用于应用资产列表和部署计划摘要。 |
| `bindingInformation` | `string` | 否 | 站点绑定信息，例如 `*:443:example.com`、`0.0.0.0:8443:api.example.com`。 |
| `hostHeader` | `string` | 否 | HTTP Host 头。Web 站点通常填域名；无 Host 头的 TCP/TLS 场景可以留空。 |
| `port` | `number` | 是 | 应用资产访问端口。 |
| `protocol` | `enum` | 是 | 应用资产访问协议。常用值为 `HTTP`、`HTTPS`、`TLS`、`CUSTOM`。 |
| `verifyUrl` | `string` | TLS 证书部署必填 | 后端探测和工作流验证共用的 URL；HTTPS 站点必须能通过该 URL 拿到远端证书。 |
| `sniName` | `string` | 否 | TLS SNI 名称；未填写时后端可回退到 `hostHeader` 或 `verifyUrl` 主机名。 |

规则：

- `frameworkType/siteName/bindingInformation/hostHeader/port/protocol/verifyUrl/sniName` 是资产目标信息的唯一 DSL 变量来源。新模板不得再新增 `verifyHost`、`verifyPort`、`virtualHostServerName` 等同义变量；旧模板迁移时应保留运行兼容，但表单展示和后端探测以本节变量为准。
- 同时支持独立应用资产（standalone ApplicationAsset）的模板，固定 `siteName` 必须来源于 `application.serverName`；独立应用资产没有 `site` 上下文，禁止使用 `site.name` 作为必填固定来源。
- `verifyUrl` 用于平台后端探测，不能只服务于工作流内部 HTTP step。内网、专线或 SNI 特殊场景，应通过 `verifyUrl`、`hostHeader`、`sniName` 明确表达，不要把解析逻辑藏在脚本中。
- `bindingInformation` 是展示和审计字段，不应参与私钥、证书内容或凭据拼接。
- 当 `bindingInformation` 可能未持久化在站点资产中时，DSL 必须声明为 `source.kind=derived`、`resolver=binding_information` 和 `bindingPolicy=fixed`，不得把高级设置中的只读变量当作用户必填项。解析器依次使用 `site.bindingInformation`、`target.bindingKey`，两者均为空时按 `${listenIp ?? '*'}:${port}:${hostHeader ?? serverName}` 合成稳定值；因此即使站点没有独立 Host Header，也不得因模板引用 `bindingInformation` 而在渲染阶段报告变量缺失。
- `frameworkType` 使用大写枚举值，与应用资产、站点资产、ManagedTarget 中的 ProviderType 保持一致。
- 如果工作流不面向 Web/TLS 站点，而是设备 API 或自定义部署，仍应声明 `frameworkType = CUSTOM`、`siteName`、`protocol = CUSTOM`；只有无法通过 URL 探测远端证书时，才允许省略 `verifyUrl`。

证书产物 Slot 合同示例（位于 `inputContract.artifacts`）：

```json
{
  "serverCert": {
    "kind": "certificate",
    "required": true,
    "configurationMode": "required",
    "lifecycle": "runtime_injected",
    "artifactContract": {
      "outputs": {
        "certFile": {
          "role": "public_certificate",
          "required": true,
          "format": "pem",
          "encoding": "utf8"
        },
        "keyFile": {
          "role": "private_key",
          "required": true,
          "format": "pem",
          "encoding": "utf8",
          "sensitive": true
        },
        "chainFile": {
          "role": "certificate_chain",
          "required": false,
          "format": "pem",
          "encoding": "utf8"
        }
      }

  }

```

应用资产只保存版本化的 `workflow.inputBindings`。证书产物映射位于 `workflow.inputBindings.artifacts`，把 `inputContract.artifacts` 中的 Slot 映射到证书格式配置输出；不得再保存独立的 `certificateArtifactBindings`：


## 运行时上下文

后端执行时会维护运行时上下文，后续 step 可以通过明确的 `steps.<stepName>` 路径引用前面 step 的输出。

运行时只提供标准顶层命名空间：

- `variables`：模板声明并由统一输入绑定的普通变量。
- `connections`：结构化连接绑定。
- `credentials`：运行时凭据绑定，只暴露凭据元数据和 SecretRef。
- `artifacts`：证书等产物绑定，输出位于 `artifacts.<slot>.outputs`。
- `asset`：标准应用资产快照。
- `steps`：按 step 名称索引的历史 step 快照。
- `system`：平台生成的运行上下文。

禁止恢复 `previous`、根级变量、根级 extractor 输出或根级证书/凭据别名。

快照结构：

```json
{
  "name": "prepare_auth",
  "type": "http",
  "stage": "prepare",
  "status": "success",
  "output": {
    "statusCode": 200,
    "body": {
      "token": "..."
    }
  },
  "extracted": {
    "accessToken": "..."
  }
}
```

引用规则：

- 优先通过 extractor 提取稳定输出，例如 `accessToken`，后续必须写 `{{steps.prepare_auth.extracted.accessToken}}`。
- 不提供“上一步”隐式引用；即使引用紧邻上一步，也必须使用明确的 step 名称。
- 需要引用指定 step 的结果时，可以写 `{{steps.prepare_auth.extracted.accessToken}}` 或 `{{steps.install_cert.output.body.transferResults[0].hash}}`。
- `sensitive: true` 的 extractor 保存真实值供下游渲染，但 `renderedSteps`、`stepResults`、`stepOutput` 和 `logs` 中必须脱敏展示。
- 执行器必须分离“仅供当前工作流调用链使用的原始响应”和“允许持久化或返回前端的脱敏结果”；禁止把 `[REDACTED]`、`[SECRET_CAPTURED]` 等展示占位符写回运行时变量。
- 正式执行必须在内部 step 状态变化时发布运行进度快照，状态统一使用 `queued`、`running`、`success`、`failed`、`skipped`；禁止等整个工作流结束后一次性补写全部 step 结果。
- `dry-run` 预览必须复用正式执行的逐 step 进度发布机制；即使不发送真实请求或执行真实变更，也必须按 `queued`、`running`、`success`、`failed`、`skipped` 更新前端，不得使用定时动画伪造任务推进。
- `dry-run` 完成后必须返回结构化检查结论。HTTP 节点至少说明已解析的方法、目标地址、响应断言数量和变量提取数量；SSH/文件传输节点至少说明目标主机、操作类型以及未建立真实连接或写入文件的边界。
- 运行进度快照与最终运行结果使用相同的脱敏边界，任何 Token、Secret、私钥或敏感 extractor 原始值都不得进入持久化快照、SSE 事件和前端展示数据。

## 凭据绑定规范

工作流 DSL 不允许用户手写 `secret://...`。工作流通过 `inputContract.credentials` 声明 Credential Slot，用户配置和 PluginBinding 只在 `InputBindingsV1.credentials` 保存 `credentialId`；宿主在运行时从全局 CredentialProfile 解析为 `RuntimeCredentialV1`：

```json
{
  "sshCredential": {
    "credentialId": "cred_device_login",
    "kind": "USERNAME_PASSWORD",
    "username": "root",
    "secretRefs": {
      "password": "secret://password/sec_device_login#current"
    }
  }
}
```

字段规则：

- `credentialId`：全局 CredentialProfile 编号，例如 `cred_device_login`。
- `kind`：凭据类型，支持 `USERNAME_PASSWORD`、`SSH_KEY`、`BEARER_TOKEN`、`API_KEY`、`CLIENT_CERTIFICATE`。
- `username`：用户名密码或 SSH 私钥凭据的账号名。
- `delivery`：API Key 的名称和传递位置。
- `secretRefs`：由宿主解析的 Slot 到 SecretRef 映射，只存在于运行时对象和部署计划快照，不由用户手写。

执行适配规则：

- 设备实时动作从 CredentialProfile 解析 `#current` SecretRef。
- 部署计划编译时必须把 `#current` 固定为精确 Secret 版本，执行时不得重新读取当前版本。
- Runtime 只在 `credentials.<slot>` 注入 `RuntimeCredentialV1`；普通变量不得承载 Credential，所有入口均拒绝裸 SecretRef 和旧 `{ id, kind, type }` 对象。

工作流运行时执行器必须通过静态 Executor Registry（执行器注册表）解析，禁止在主执行流程中按产品或平台增加条件分支：

- 当前注册的执行器标识为 `017.CURL_HTTP`、`015.SSH`、`workflow.condition`、`workflow.transform`、`workflow.wait`、`workflow.manual`。
- 同一执行器标识重复注册时，装配必须失败，禁止后注册项静默覆盖已有实现。
- DSL 引用了未注册的执行器时，运行时必须返回 `WORKFLOW_EXECUTOR_NOT_REGISTERED`，禁止返回 planned success（计划成功）或伪造执行成功。
- SSH 与 CURL 的请求、凭据、幂等、提取和断言语义保持不变；Registry 只负责稳定解析执行实现，不改变 DSL step 类型和字段。
- 这个内部引用只提供给 SSH/CURL 执行器，不再作为工作流 DSL 编写内容。

禁止写法：

```json
{
  "password": "plain-text-password",
  "privateKey": "-----BEGIN PRIVATE KEY-----..."
}
```

## HTTP/CURL Step

HTTP step 用于认证、调用接口、提取会话参数、验证状态等。

```json
{
  "name": "prepare_auth",
  "type": "http",
  "stage": "prepare",
  "request": {
    "method": "POST",
    "connectionRef": "managementApi",
    "url": "https://{{connections.management.host}}:{{connections.management.port}}/api/login",
    "auth": {
      "type": "bearer",
      "credential": "{{credentials.apiCredential}}"
    },
    "timeoutSeconds": 30
  },
  "extract": [
    {
      "name": "accessToken",
      "type": "firstOf",
      "paths": [
        "$.body.token",
        "$.body.access_token",
        "$.body.data.token"
      ],
      "sensitive": true
    },
    {
      "name": "sessionId",
      "type": "firstOf",
      "paths": [
        "$.headers.x-session-id",
        "$.body.sessionId",
        "$.body.data.session.id"
      ],
      "sensitive": true
    },
    {
      "name": "tenantId",
      "type": "outputPath",
      "path": "$.body.data.tenant.id"
    }
  ],
  "assert": [
    {
      "type": "statusCode",
      "equals": 200
    }
  ]
}
```

`request` 支持：

- `method`: `GET`、`POST`、`PUT`、`PATCH`、`DELETE`
- `url`
- `connectionRef`：必填的命名 HTTP Connection Slot。必须引用 `ResolvedDeploymentInputV1.connections` 中 `transport=http` 的完整连接；引用 SSH Connection、未知 Slot 或缺少 host/port 时在执行前失败。
- `query`
- `headers`
- `headerRefs`

`request.tls.verify` 支持布尔常量；未显式声明时使用 Connection 快照中的 `tls.verifyPeer`。不得通过普通变量、字符串拼接或任意表达式绕过 TLS 策略。`verify=false` 时仍必须同时声明 `allowInsecure=true`，并由宿主权限和审计策略决定是否允许执行。

当 `request.connectionRef` 对应的 HTTP Connection 声明了 `tls.verifyPeer` 或 `tls.serverName`，且 Step 未显式声明 `request.tls` 时，Runtime Adapter 使用 Connection 快照中的 TLS 配置。Step 显式 TLS 配置优先，但不得绕过统一 Resolver 已产生的校验问题。HTTP、SSH、SFTP、SCP 均不得从普通变量猜测地址、端口或连接类型。
- `bodyType`: `json`、`form`、`multipart`、`raw`、`none`
- `body`
- `form`
- `formCredentialRefs`
- `multipart`
- `auth`
- `tls`
- `timeoutSeconds`
- `maxResponseBytes`
- `successStatusCodes`
- `failOnNon2xx`

HTTP auth 支持：

- `none`
- `basic`：必须提供 `username` 和 `credential`。`credential` 必须是 `USERNAME_PASSWORD` 凭据或 credential 变量引用。
- `bearer`：必须提供 `credential`，通常使用 `BEARER_TOKEN` 凭据。
- `api_key`：必须提供 `credential`、`name` 和 `in`，通常使用 `API_KEY` 凭据。

Secret Header 规则：

- 普通 Header 写在 `request.headers`。
- Secret Header 必须使用 `request.headerRefs`，值可以引用 `{{credentials.credential.secretRefs.<slot>}}`。
- 宿主渲染时若发现普通 Header 的完整值为 SecretRef，会提升到 CURL `headerRefs` 后再执行，禁止把 SecretRef 字符串直接发送给目标设备。

表单密文字段规则：

- 普通表单字段写在 `request.form`，只允许字符串、数字和布尔值。
- 密文字段写在 `request.formCredentialRefs`，值必须是 credential 变量引用或结构化 credential 绑定对象。
- 后端运行前把 `formCredentialRefs` 转换为 CURL 执行器内部的 `formSecretRefs`，DSL 文件中禁止保存 `secret://...`。
- 典型用途是设备登录接口需要 `account` / `passwd` 这类 form 字段时：账号可以来自 `{{credentials.credential.username}}`，密码必须通过 `formCredentialRefs.passwd` 注入，不能写进 `form`。

示例：

```json
{
  "request": {
    "method": "POST",
    "connectionRef": "management",
    "url": "https://{{connections.management.host}}:{{connections.management.port}}/webapi/entry.cgi",
    "bodyType": "form",
    "form": {
      "api": "SYNO.API.Auth",
      "version": 7,
      "method": "login",
      "account": "{{credentials.synologyCredential.username}}"
    },
    "formCredentialRefs": {
      "passwd": "{{credentials.synologyCredential}}"
    }
  }
}
```

`cookie`、`custom_header`、`mtls` 仍属于执行器内部能力，日常工作流编辑器暂不暴露；如后续要支持，必须先补齐密文保存或凭据绑定模型，不能把明文或用户手写 SecretRef 写进 DSL。

Basic 认证示例：

```json
{
  "auth": {
    "type": "basic",
    "username": "{{credentials.apiCredential.username}}",
    "credential": "{{credentials.apiCredential}}"
  }
}
```

SSH/SFTP/SCP 通过连接定义中的 `credentialSlot` 关联 Credential Slot，步骤只引用连接：

```json
{
  "connectionRef": "targetSsh"
}
```

前端编辑器凭据绑定约定：

- `web/src/views/workflows/WorkflowCanvasEditor.vue` 只为 `inputContract.credentials` 中声明的 Credential Slot 读取并筛选全局 CredentialProfile；不得把实际 CredentialProfile、`credentialId` 或 SecretRef 写入节点配置或普通变量。
- HTTP `basic`、`bearer`、`api_key` 的 `request.auth.credential` 必须引用 `{{credentials.<slot>}}`；SSH、SFTP、SCP 不声明节点级凭据，只通过 Connection 的 `credentialSlot` 关联。
- 前端界面不允许用户手填 `SecretRef` 字符串。运行态试跑选择 CredentialProfile 后，前端只把解析后的 `ResolvedDeploymentInputV1.credentials` 交给现有运行接口，Canvas 和正式 DSL 中不保存该选择。
- 用户点击保存草稿、单节点模拟运行、单节点真实试跑时，前端只能提交画布草稿；后端 `workflow-canvas.compiler.ts` 必须输出正式 DSL 字段：
  - HTTP Basic -> `request.auth.username` + `request.auth.credential`
  - HTTP Bearer -> `request.auth.credential`
  - HTTP API Key -> `request.auth.credential` + `request.auth.name` + `request.auth.in`
  - SSH/SFTP/SCP -> `connectionRef`
  - `inputContract.credentials.<slot>` -> `inputBindings.credentials.<slot>` 只保存 `credentialId`，执行时注入 `{ credentialId, kind, username?, delivery?, secretRefs }`
- 后端运行前再把 Credential Slot 物化为执行器内部 Secret 引用，绝不把密码、token、私钥明文写进 DSL。

## 单节点试跑错误输出

单节点模拟运行和真实试跑必须先由后端把画布编译为正式 DSL，再交给运行接口；不允许在 DSL 中增加调试专用字段。

当真实 SSH、SFTP、SCP 或 HTTP 执行失败时，后端必须把失败作为结构化运行结果返回，不能只向上抛出一条字符串异常：

- `stepResult.status` 必须是 `failed`。
- `stepResult.errorCode` 保存稳定错误码，例如 `SSH_CONNECT_FAILED`、`SSH_AUTH_FAILED`。
- `stepResult.errorMessage` 保存用户可读错误，例如 `SSH 连接失败`。
- `stepOutput.body.detail` 保存排障上下文，例如：
  - `target`：目标地址和端口。
  - `stage`：失败阶段，例如 `connect`、`auth`。
  - `category`：错误分类，例如 `network`、`authentication`。
  - `cause`：底层失败原因。
  - `suggestion`：下一步检查建议。

前端运行态面板必须优先展示上述结构化失败详情，然后再展示原始 `stepOutput` 和日志。这样真实 SSH 试跑失败时，用户能看到是网络、端口、防火墙、SSH 服务端还是认证配置问题，而不是只看到 `SSH 连接失败`。

每次单节点试跑或完整工作流执行都必须生成独立的运行 ID。SSH/CURL 执行适配层用运行 ID、节点名和 attempt 组合生成内部幂等键，DSL 作者不能在工作流文件中手写或复用执行器 `idempotencyKey`。

## Transform Step

Transform step 用于把上游 HTTP/SSH/SFTP/SCP 的结构化输出转换为新的工作流上下文变量。第一版只支持 `engine: "jsonata"`。

典型用途：

- 从列表接口返回的数组中筛选目标对象 ID。
- 把 `certificates[].services` 映射成后续 HTTP form 需要的 JSON 字符串。
- 把多个上游变量合并成后续 step 的输入对象。

列表接口字段名或包裹层可能随设备版本变化时，先用 `firstOf` 从完整 step 输出中提取候选数组，例如依次读取 `$.body.data.certificates`、`$.body.certificates`、`$.body.data.items`、`$.body.items`、`$.body.data`。不要把这种设备差异写成宿主代码里的专用解析逻辑。

示例：

```json
{
  "name": "build_service_bindings",
  "type": "transform",
  "stage": "refresh",
  "transform": {
    "engine": "jsonata",
    "input": {
      "certificateDescription": "{{variables.certificateDescription}}",
      "certificates": "{{steps.list_synology_certificates_after_import.extracted.synologyCertificatesAfterImport}}",
      "previousCertificateId": "{{steps.select_previous_certificate.extracted.previousCertificateId}}",
      "previousCertificateServices": "{{steps.select_previous_certificate.extracted.previousCertificateServices}}"
    },
    "outputs": {
      "newCertificateId": {
        "expression": "$filter(certificates, function($c){$c.desc = certificateDescription})[0].id"
      },
      "serviceBindingsJson": {
        "expression": "[$map(previousCertificateServices, function($service){{\"service\":$service,\"old_id\":previousCertificateId,\"id\":newCertificateId}})]",
        "format": "jsonString"
      }
    },
    "timeoutMs": 200,
    "maxInputBytes": 1048576,
    "maxOutputBytes": 1048576
  }
}
```

字段规则：

- `transform.engine` 必须是 `jsonata`。这是第一版唯一启用的转换引擎。
- `transform.input` 可选，必须是 JSON 可序列化结构。字符串值支持 `{{variable}}` 渲染；如果整个字符串就是单个变量引用，会保留变量原始类型，不会强制转成字符串。
- `transform.outputs` 必填，必须是非空对象。对象 key 会成为当前 step 的提取结果，后续 step 必须用 `{{steps.<stepName>.extracted.<outputName>}}` 引用，例如 `{{steps.build_service_bindings.extracted.serviceBindingsJson}}`。
- 前一步 transform 输出不得通过不存在的 `steps.<name>.output` 路径引用；后续 step 必须使用 `steps.<name>.extracted.<outputName>`。
- `outputs.<name>.expression` 必填，最大 4096 字符。
- `outputs.<name>.format` 可选：
  - `raw`：默认，保留 JSONata 输出的原始 JSON 值。
  - `jsonString`：把 JSONata 输出序列化为 JSON 字符串，适合 HTTP form 中必须传字符串的字段。
- `outputs.<name>.optional` 可选。未设置或为 `false` 时，表达式输出 `null` / `undefined` 会让 step 失败。
- `outputs.<name>.sensitive` 可选。为 `true` 时输出值进入脱敏路径。
- `timeoutMs` 可选，范围 `1-1000`，默认 `200`。
- `maxInputBytes` 可选，范围 `1-1048576`，默认 `262144`。
- `maxOutputBytes` 可选，范围 `1-1048576`，默认 `262144`。
- JSONata 注册纯计算函数 `$x509Sha256(base64FileContent)`：输入必须是 Base64 编码的 PEM 或 DER 证书文件内容，输出小写 64 位 SHA-256 指纹。该函数只解析内存输入，不访问文件或网络。

发现集合输出规则：

- 标准发现结果中的 `capabilities`、`frameworks`、`sites`、`certificates`、`certificateBindings` 和 `warnings` 必须始终显式输出数组，包括零项和单项结果。
- JSONata 的 `$map(...)`、`$append(...)` 会按序列语义折叠结果：零项可能得到 `undefined`，单项可能得到对象，多项才得到数组。插件不得依赖宿主把对象自动修正为数组。
- 构造发现集合时必须使用 `[$map(...)]`、`[$append(...)]` 或 `$append([], ...)` 等显式数组写法，并为零项、单项和多项分别补测试。

安全边界：

- JSONata 表达式只接收 `transform.input` 和同一 transform step 内已经生成的前序输出。
- 输出只写入工作流运行上下文，不允许访问文件、网络、环境变量或宿主进程对象。
- 后端不向 JSONata 注册任何自定义 I/O 函数。
- 禁用 `$eval(...)`、`$assert(...)`、`$error(...)`。
- 表达式长度、输入大小、输出大小和执行时长都必须受限。
- JSONata 求值必须在隔离 worker 中执行；超时后终止 worker，不能让复杂表达式卡死主执行线程。

扩展原则：

- 可以在后续版本增加 JMESPath、CEL 等转换引擎，但必须继续通过 `engine` 显式声明。
- 禁止为了某个设备或厂商补宿主专用转换代码。数据转换能力必须沉淀为通用 transform step 或通用表达式引擎能力。
- 如新增转换引擎，必须先补 schema、运行时安全边界、前端编辑器字段和本文档。
- 设备发现转换不得把厂商原始名称直接拼入稳定键。必须在 transform 中生成确定性的 ASCII 安全键，并对对象稳定键及所有父子引用执行同一转换；显示名称继续保留厂商原值。
- 设备发现中的证书对象必须分别映射厂商提供的生效时间和到期时间为 `notBefore`、`notAfter`，禁止只保留其中一个时间字段。
- 厂商证书清单未直接返回可靠 SHA-256 指纹时，插件必须通过厂商只读文件接口取得公钥证书内容，并使用 `$x509Sha256(...)` 生成指纹；禁止使用证书名称、主题或到期时间冒充稳定关联依据。

## Foreach Step

Foreach step 用于按顺序遍历运行时数组，并对每个元素执行同一组子步骤。它解决设备发现结果、站点列表、证书绑定列表等动态集合无法在模板编写期确定数量的问题。

```json
{
  "name": "bind_virtual_servers",
  "type": "foreach",
  "stage": "install",
  "foreach": {
    "itemsPath": "asset.virtualServers",
    "itemVariable": "virtualServer",
    "indexVariable": "virtualServerIndex",
    "maxItems": 200,
    "continueOnError": false,
    "steps": [
      {
        "name": "bind_certificate",
        "type": "http",
        "request": {
          "method": "PUT",
          "connectionRef": "management",
          "url": "https://{{connections.management.host}}:{{connections.management.port}}/api/virtual-servers/{{virtualServer.name}}/certificate",
          "body": {
            "index": "{{virtualServerIndex}}",
            "fingerprint": "{{artifacts.cert.outputs.fingerprintSha256}}"
          }
        }
      }
    ]
  }
}
```

字段和执行规则：

- `foreach.itemsPath` 必填，使用点号路径读取当前工作流上下文，结果必须是数组。
- `render_only`（仅渲染）模式下，如果 `itemsPath` 指向已规划前序步骤的 `steps.*.output` 或 `steps.*.extracted`，而该输出只有正式执行后才能产生，运行时必须把 foreach 标记为延迟展开并保留子步骤计划，不得伪造空数组或执行远端请求。正式执行、Mock 执行以及非运行时输出路径仍必须严格校验数组类型；路径写错或结果不是数组时必须失败关闭。
- `foreach.itemVariable` 必填，每轮保存当前元素；`foreach.indexVariable` 可选，每轮保存从 `0` 开始的数组索引。
- 循环变量只在当前 foreach 子步骤中有效。循环结束或失败后，运行时必须恢复进入 foreach 前的同名上下文值。
- `foreach.steps` 必须是非空步骤数组，可以使用循环变量，也可以继续使用外层变量、上游提取结果和 `steps.*` 快照。
- 子步骤严格按数组顺序执行。`continueOnError` 默认为 `false`，任一子步骤失败后立即停止当前 foreach，不再执行剩余子步骤和后续元素。
- `continueOnError` 为 `true` 时，当前元素的剩余子步骤仍停止，但 foreach 会继续处理后续元素；失败子步骤必须保留在 `children`、迭代结果和日志中，foreach 顶层允许成功结束。该模式只用于发现、采集等允许部分数据缺失的尽力而为任务，不得用于部署、变更或回滚链路。
- `maxItems` 可选，范围 `1-1000`，默认 `100`。运行时数组超过上限时必须在发送任何远程请求前拒绝执行。
- foreach 最多嵌套三层。超过限制必须在模板校验阶段拒绝，不能把无界递归留到运行时。
- foreach 本身形成一个顶层业务步骤；每轮和子步骤结果记录在该步骤输出与日志中。后续 Execution Step 投影必须保留迭代索引和子步骤身份。
- foreach 不改变 Secret 规则。循环日志、子步骤计划和聚合输出必须继续执行统一脱敏，禁止把密码、Token、私钥或 SecretRef 原文写入日志。
- foreach 不提供并行执行语义。需要并行时必须由后续受控调度能力显式实现，不能依赖模板作者假设并发顺序。

## Checkpoint Step

Checkpoint step 用于在设备写操作前保存可验证的远端状态摘要，为宿主重启恢复、失败回滚和人工介入判断提供依据。Checkpoint 不是任意数据快照，禁止保存完整 HTTP 响应、证书正文、私钥、密码、Token 或 SecretRef。

```json
{
  "name": "checkpoint_before_binding",
  "type": "checkpoint",
  "stage": "backup",
  "checkpoint": {
    "name": "before-binding",
    "capture": {
      "bindingDigest": "currentBindingDigest",
      "remoteCertificateFingerprint": "remoteCertificateFingerprint",
      "backupArtifactRef": "backupArtifactRef"
    },
    "normalizedHash": true,
    "requiredForRollback": true
  }
}
```

字段和执行规则：

- `checkpoint.name` 必填，在同一恢复账本内必须唯一；同名 checkpoint 只能幂等重放，内容哈希变化时失败关闭。
- `checkpoint.capture` 必须是非空对象。key 是账本字段名，value 是工作流上下文点号路径，不使用 `{{...}}` 包裹。
- `render_only` 模式下，引用前序步骤运行时输出的 capture 可以标记为延迟捕获，只展示来源路径，不生成伪造哈希；正式执行时仍必须取得真实值并生成规范化哈希。
- 捕获路径必须存在。路径指向敏感变量、凭据、私钥、二进制内容、SecretRef 或带敏感字段名的对象时必须拒绝执行。
- `normalizedHash` 默认按规范化 JSON 计算 SHA-256；对象 key 顺序不能影响哈希。
- `requiredForRollback` 表示该 checkpoint 是自动回滚的必要前置条件。恢复分类发现非幂等步骤中断且存在必要 checkpoint 时进入 `ROLLBACK_REQUIRED`，否则进入人工介入。
- 插件工作流执行前必须创建 Recovery Ledger（恢复账本），固定 `pluginVersionId`、`workflowVersionId`、`capabilityKey`、目标哈希、计划哈希和输入哈希。
- 账本只记录已完成业务步骤 ID、补偿步骤 ID、checkpoint 摘要和状态，不保存秘密材料。
- 宿主重启后，幂等步骤可以分类为 `RESUMABLE`；非幂等步骤不能自动重放。固定版本或任一哈希不一致时必须拒绝恢复。
- 运行状态包括 `ACTIVE`、`COMPLETED`、`ROLLBACK_RUNNING`、`ROLLED_BACK`、`MANUAL_INTERVENTION`。

## SSH Step

SSH step 用于远端命令、脚本、服务重载、文件操作等。

### Host Key 策略

SSH、SFTP、SCP 引用的 Connection Slot 中，`hostKey.policy` 支持三种策略：

- `trust_on_first_use`：首次连接时信任并记录目标 Host Key。当前前端画布新建节点默认使用该策略，适合单节点真实试跑和内网设备接入。
- `strict`：必须已有 Known Hosts 记录，或显式提供 `expectedHostKeyFingerprint`。适合生产模板固化后执行。
- `manual_approval_required`：发现未知 Host Key 时写入待审批记录并拒绝执行。只有接入 Host Key 审批流程后才能用于真实执行；不能作为前端新建节点默认值。

如果目标主机已经能通过普通 SSH 访问，但真实试跑返回 `HOST_KEY_APPROVAL_REQUIRED`、`HOST_KEY_UNKNOWN` 或 `HOST_KEY_MISMATCH`，说明失败点是主机身份校验，不是网络或密码。处理方式是改用 `trust_on_first_use` 完成首次登记，或填写 `expectedHostKeyFingerprint` 后使用 `strict`。

单命令：

```json
{
  "name": "test_nginx",
  "type": "ssh",
  "stage": "refresh",
  "ssh": {
    "mode": "command",
    "connectionRef": "targetSsh",
    "command": "nginx -t",
    "timeoutSeconds": 60
  }
}
```

多命令：

```json
{
  "name": "reload_nginx",
  "type": "ssh",
  "stage": "refresh",
  "ssh": {
    "mode": "command",
    "connectionRef": "targetSsh",
    "commands": [
      "nginx -t",
      "systemctl reload nginx",
      "systemctl status nginx --no-pager"
    ],
    "timeoutSeconds": 120
  },
  "assert": [
    {
      "type": "regex",
      "pattern": ".*"
    }
  ]
}
```

执行规则：

- 一个 SSH step 对应一次 SSH 会话。
- `commands` 中的命令在同一个 SSH 会话中按数组顺序执行。
- 任一命令失败后停止后续命令。
- 结果会聚合 stdout、stderr，并保留每条命令的执行结果。
- `connectionRef` 必填，只能引用 `inputContract.connections` 中声明的 SSH Connection Slot。
- 禁止在 SSH、SFTP、SCP Step 中内联 host、port、username、Credential 或 Host Key 配置。

`mode` 支持：

- `command`
- `script`
- `interactive`

当前推荐优先使用 `command` + `commands` 表达多个简单命令。

安全边界：

- 禁止把证书私钥、PFX 密码、token 等敏感内容内联到 `ssh.command`、`ssh.commands` 或 `ssh.script`。
- 需要上传证书或私钥文件时，必须使用正式 `sftp` 或 `scp` step，不能用 `cat <<EOF`、`echo`、`printf` 等 SSH 命令拼接文件内容。
- SSH 命令适合执行 `nginx -t`、`apache2ctl -t`、`systemctl reload ...` 这类远端动作，不适合承载文件传输内容。

前端画布导入规则：

- `ssh.command`、`ssh.commands`、`ssh.script` 都会映射到属性面板中的“命令”文本框。
- `ssh.commands` 导入时会按换行拼接显示，保存时仍按多行命令转回 `commands` 数组。
- `ssh.script` 导入时会完整显示脚本内容，保存时必须继续回写为 `mode: "script"` + `script`，不能降级成空 `command`。
- 导入 DSL 时，节点标题优先使用 step 的 `name`，避免复杂模板在画布上全部显示成泛化的“SSH 命令”。

## SFTP/SCP Step

SFTP/SCP step 用于正式文件传输。证书、公钥、私钥、配置片段等文件上传必须放在 `install` 阶段。

SFTP 上传证书：

```json
{
  "name": "install_certificate_pem",
  "type": "sftp",
  "stage": "install",
  "sftp": {
    "direction": "upload",
    "connectionRef": "targetSsh",
    "remotePath": "/etc/nginx/cert.pem",
    "contentRef": "{{artifacts.serverCert.outputs.certFile.content}}",
    "mode": "0644",
    "timeoutSeconds": 60
  },
  "extract": [
    {
      "name": "certificateUploadHash",
      "type": "jsonPath",
      "path": "$.transferResults[0].hash",
      "optional": true
    }
  ]
}
```

SCP 上传私钥：

```json
{
  "name": "install_certificate_key",
  "type": "scp",
  "stage": "install",
  "scp": {
    "direction": "upload",
    "connectionRef": "targetSsh",
    "remotePath": "/etc/nginx/key.pem",
    "contentRef": "{{artifacts.serverCert.outputs.keyFile.content}}",
    "mode": "0600",
    "timeoutSeconds": 60
  }
}
```

`sftp` / `scp` 字段支持：

- `direction`: `upload` 或 `download`，必填。
- `connection`: SSH 连接对象，字段与 SSH step 的 `ssh.connection` 一致，必填。
- `remotePath`: 远端路径，必填。
- `contentRef`: 上传内容引用，新模板必须写 `{{artifacts.serverCert.outputs.certFile.content}}`、`{{artifacts.serverCert.outputs.keyFile.content}}` 等证书产物槽位表达式。
- `contentEncoding`: `utf8` 或 `base64`，默认按 UTF-8 文本处理。
- `localPath`: 本地路径或虚拟产物路径；上传时可与 `contentRef` 二选一，下载时必填。
- `temporaryPath`: 临时上传路径，用于原子替换。
- `expectedHash`: 期望 SHA-256 hex。
- `expectedSize`: 期望字节数，必须是非负整数。
- `verifyHash`: 是否校验传输后 hash。
- `mode`: 远端文件权限，例如 `0644`、`0600`。
- `owner` / `group`: 远端 owner/group。
- `timeoutSeconds`: 正整数超时秒数。

校验规则：

- `upload` 至少必须提供 `contentRef` 或 `localPath`。
- `download` 必须提供 `localPath`。
- `connection.credential` 必须是凭据绑定对象或 credential 变量引用。
- 文件传输通道允许承载 `serverCert.outputs.keyFile.content` 等敏感内容，但运行计划、日志和返回 detail 必须脱敏展示。
- 如果 SFTP 可用，优先使用 `sftp`；只有明确需要 SCP 协议或目标不支持 SFTP 时，才使用 `scp`。
- 使用 `temporaryPath` 上传时，执行器先写入临时文件并校验，再通过远端 rename 替换目标文件。若目标文件已存在且目标 SFTP 服务不支持 rename 覆盖，执行器允许删除旧目标后重试 rename，并在 `transferResults[].auditDetails` 中记录 `rename_overwrite_fallback`。该降级路径不具备原子性，因此生产模板仍应优先配合 backup step 使用。

## Extractor 规范

Extractor 用于从 step 输出中提取稳定字段。`name` 是 `steps.<stepName>.extracted.<name>` 路径的末段，因此可以把任意响应字段映射成明确的 step 输出，不限于 token。

数组写法：

```json
{
  "extract": [
    {
      "name": "remoteFingerprint",
      "type": "jsonPath",
      "path": "$.fingerprint"
    }
  ]
}
```

对象写法：

```json
{
  "extract": {
    "remoteFingerprint": {
      "type": "jsonPath",
      "path": "$.fingerprint"
    }
  }
}
```

支持类型：

- `jsonPath`
- `outputPath`
- `firstOf`
- `header`
- `regex`
- `statusCode`
- `textContains`

提取结果可在后续 step 中通过 `{{steps.<stepName>.extracted.remoteFingerprint}}` 引用。

提取范围：

- `jsonPath` 从 `output.body` 读取，适合 HTTP JSON body 或 SFTP/SCP 的 `body.transferResults`。
- `outputPath` 从完整 step 输出读取，路径以 `$.` 开头，例如 `$.body.token`、`$.stdout`、`$.body.transferResults[0].hash`。
- `firstOf` 从完整 step 输出按 `paths` 顺序读取第一个非空值，适合不同设备/API 返回字段名不一致的认证场景。
- `header` 从 HTTP 响应 header 读取。
- `regex` 和 `textContains` 从 `stdout` 或响应 body 文本读取。
- `statusCode` 读取 HTTP 状态码。

示例：

```json
{
  "name": "prepare_auth",
  "type": "http",
  "stage": "prepare",
  "request": {
    "method": "POST",
    "connectionRef": "management",
    "url": "https://{{connections.management.host}}:{{connections.management.port}}/api/login"
  },
  "extract": [
    {
      "name": "accessToken",
      "type": "firstOf",
      "paths": [
        "$.body.token",
        "$.body.access_token",
        "$.body.data.token",
        "$.body.result.auth.token"
      ],
      "sensitive": true
    }
  ]
}
```

`firstOf` 规则：

- `paths` 必须是非空数组。
- 每个路径都从完整 step 输出读取，而不是只读 body。
- 按顺序返回第一个不是 `undefined`、`null`、空字符串的值。
- 如果所有候选路径都没有值，且 extractor 没有声明 `optional: true`，该 step 失败。
- 不允许靠系统自动猜字段；字段映射必须是模板的一部分。
- 一个 step 可以声明多个 extractor，例如 `prepare_auth` 同时提取 `accessToken`、`sessionId`、`csrfToken`、`tenantId`、`expiresAt`，后续分别通过 `{{steps.prepare_auth.extracted.accessToken}}`、`{{steps.prepare_auth.extracted.sessionId}}`、`{{steps.prepare_auth.extracted.tenantId}}` 引用。

## Assert 规范

Assert 用于判断 step 是否成功。

```json
{
  "assert": [
    {
      "type": "statusCode",
      "equals": 200
    },
    {
      "type": "certificateFingerprint",
      "actual": "{{steps.install_certificate.extracted.remoteFingerprint}}",
      "expected": "{{artifacts.serverCert.outputs.fingerprintSha256}}"
    }
  ]
}
```

支持类型：

- `statusCode`
- `jsonPath`
- `header`
- `contains`
- `regex`
- `certificateFingerprint`

`contains` 会先渲染 `{{变量}}`，再对 `stdout` 或响应 body 文本做包含判断；为避免 HTML 文案大小写差异造成误判，比较时忽略大小写。需要严格大小写或复杂文本规则时，必须使用 `regex`。

## Rollback 规范

`rollback` 是失败后执行的回滚步骤。

```json
{
  "rollback": [
    {
      "name": "restore_old_cert",
      "type": "ssh",
      "stage": "install",
      "ssh": {
        "mode": "command",
        "connectionRef": "targetSsh",
        "commands": [
          "cp /etc/nginx/cert.pem.bak /etc/nginx/cert.pem",
          "nginx -t",
          "systemctl reload nginx"
        ],
        "timeoutSeconds": 120
      }
    }
  ]
}
```

要求：

- 回滚步骤也必须避免明文 Secret。
- 回滚步骤应尽量可幂等。
- 回滚步骤应优先使用已有备份材料。

## 禁止事项

- 禁止把密码、token、私钥、PFX 密码明文写入 DSL。
- 禁止把证书或私钥内容塞进 `ssh.command` / `ssh.commands` / `ssh.script`；上传文件必须使用 `sftp` 或 `scp` step。
- 禁止引用未声明变量。
- 禁止新增 DSL 时省略 `stage`。
- 禁止把多个业务动作塞进一个不可读的大脚本，除非必须保持远端事务性。
- 禁止在前端生成、保存或试跑正式 DSL；前端只能编辑画布，正式 DSL 必须由后端画布编译器生成并校验。
- 禁止修改后端 schema 后不更新本文档。

## 变更同步要求

修改以下内容时必须同步更新本文档：

- `WorkflowDslV1`
- `WorkflowStep`
- `WorkflowVariableDefinition`
- step 类型、字段、校验规则
- stage 阶段定义或执行顺序
- 凭据绑定规则
- SSH/CURL 执行器适配规则
- 后端画布到 DSL 的转换规则

## 变量配置契约与连接槽位

工作流变量必须区分配置阶段和执行阶段。新 DSL 应为每个变量声明以下字段：

```json
{
  "type": "string",
  "configurationMode": "required",
  "source": { "kind": "asset", "path": "application.verifyUrl" },
  "lifecycle": "pre_execution",
  "bindingPolicy": "fixed",
  "ui": { "group": "basic", "order": 10 }
}
```

- `required`：执行前必须有值；只有需要用户绑定的来源才显示在基础配置区。
- `advanced`：由资产、DSL 默认值或受控派生值提供，默认折叠；只有 `default_overridable` 才允许用户覆盖。
- `runtime`：由证书产物、系统上下文或步骤输出在执行期间注入，配置页面不得渲染，也不得写入资产绑定。
- `source` 描述值的唯一来源；前端不得依据变量名、类型或默认值推断来源。
- `source.kind=asset` 表示字段由标准 `DeploymentAssetContextV1` 托管；`source.kind=derived` 表示字段由受控解析器生成。两者均不得被 `InputBindingsV1.variables` 覆盖。
- `lifecycle` 描述值何时可用；`runtime_injected` 和 `step_output` 必须配合 `configurationMode=runtime`。
- `bindingPolicy` 描述用户是否可以覆盖值；`required_binding` 用于必须手动绑定的基础配置，`default_overridable` 用于允许修改默认值的进阶配置，`fixed` 可用于任何由资产、派生值、系统或步骤产物唯一决定的变量。

应用资产通用目标字段必须直接引用 `target` 上下文，不得在应用资产页面重复要求用户填写：

```json
{
  "port": {
    "type": "number",
    "configurationMode": "required",
    "source": { "kind": "asset", "path": "application.port" },
    "lifecycle": "pre_execution",
    "bindingPolicy": "fixed"
  },
  "deviceBaseUrl": {
    "type": "string",
    "configurationMode": "advanced",
    "source": { "kind": "derived", "resolver": "endpoint_url" },
    "lifecycle": "pre_execution",
    "bindingPolicy": "fixed"
  }
}
```

步骤输出必须显式声明为运行时变量。例如 `newCertificateId`、`previousCertificateId`、`serviceBindingsJson` 应使用 `configurationMode=runtime`、`source.kind=step_output`、`lifecycle=step_output` 和 `bindingPolicy=fixed`，不得让用户在配置阶段手工输入。

SSH、SFTP、SCP 和 HTTP 节点可引用命名连接槽位：

```json
{
  "inputContract": {
    "apiVersion": "gcac.deployment-input/v1",
    "variables": {},
    "connections": {
      "targetSsh": {
        "transport": "ssh",
        "host": {
          "type": "string",
          "required": true,
          "configurationMode": "required",
          "source": { "kind": "binding" },
          "lifecycle": "pre_execution",
          "bindingPolicy": "required_binding"
        },
        "port": {
          "type": "number",
          "required": true,
          "configurationMode": "advanced",
          "source": { "kind": "default" },
          "lifecycle": "pre_execution",
          "bindingPolicy": "default_overridable",
          "default": 22
        },
        "username": {
          "type": "string",
          "required": true,
          "configurationMode": "required",
          "source": { "kind": "binding" },
          "lifecycle": "pre_execution",
          "bindingPolicy": "required_binding"
        },
        "credentialSlot": "sshCredential",
        "hostKey": { "policy": "trust_on_first_use" }
      }
    },
    "credentials": {
      "sshCredential": {
        "allowedKinds": ["USERNAME_PASSWORD", "SSH_KEY"],
        "required": true,
        "configurationMode": "required",
        "lifecycle": "pre_execution"
      }
    },
    "artifacts": {}
  }
}
```

节点通过 `connectionRef` 引用连接槽位。连接槽位的 `host` 来源于工作流资产绑定，不得从 Agent Host、网关或控制面节点名称推断；未声明端口时，SSH 连接解析默认使用 `22`，但投影必须明确展示该默认值。厂商特有字段（例如 Synology 证书描述、API 路径、Nginx/Apache 目标路径）应作为 DSL 变量或兼容性 Profile 的结构化字段定义，不得退化成资产页按变量名猜测的通用输入。

应用资产只使用 `workflow.inputBindings` 保存全部覆盖值：普通变量位于 `variables`，连接位于 `connections`，凭据选择位于 `credentials`，产物映射位于 `artifacts`。每个凭据绑定只允许 `{ credentialId }`；连接绑定使用标准 `host`、`port`、`username`、`tls` 和 `hostKey` 结构：

- 应用资产、Managed PluginBinding 和 Standalone PluginBinding 均只保存稳定 `credentialId`，禁止保存裸 SecretRef 或旧 `{ id, kind, type }` 对象。
- 宿主在实时动作中解析为 `RuntimeCredentialV1`；创建部署计划时固定 `credentialVersionId`、精确 `#vN` SecretRef 和快照摘要，执行时不得回查当前版本。
- 部署计划只固定并传递 `DeploymentInputSnapshotV1`；Workflow Runtime 只能消费其解析输入的 `connections`、`variables`、`credentials` 和 `artifacts`，不得恢复独立 Binding 或证书材料参数。
- 运行时必须在统一入口把 `connectionRef` 解析为 SSH 执行器连接，SSH、SFTP、SCP 和 rollback 使用同一规则；禁止各 step 类型自行猜测连接字段。
- 基础配置只展示同时满足 `configurationMode=required` 和 `bindingPolicy=required_binding` 的 `host`、`username` 和 Credential；`port`、Host Key 策略、指纹、资产来源字段和默认可覆盖字段均默认进入高级设置。字段是否折叠由 Connection Field 的 `configurationMode` 与 `bindingPolicy` 共同决定，不能按模板名称硬编码。

DSL 不提供旧凭据对象或裸 SecretRef 兼容路径。需要升级的内置模板必须新建版本并补齐显式契约；一旦使用任一契约字段，发布校验要求所有变量和连接字段完整声明。

## Agent 原子操作插件边界

Agent 原子操作插件不是工作流 DSL 的新 step 类型，也不得塞入工作流模板目录。两者共享“变量、SecretRef、证书 Artifact 和版本固定”的配置思想，但执行协议彼此独立：

- 工作流 DSL 继续使用 `backend/src/modules/workflow-templates/builtin-workflows` 和 `data/workflows` 两类来源。用户 Agent 插件独立使用 `data/agent-plugins`，不属于工作流 DSL 来源。
- Agent 插件使用 `gcac.agent-plugin/v1` Manifest，由插件目录和应用资产 `AGENT/PLUGIN` 策略管理；历史 `mountId` 仅用于兼容旧资产。
- 工作流 DSL 文件存在于正式目录只表示“已发现”，不表示“可选择”。只有通过统一 PluginVersion 发布并处于 `ENABLED` 的工作流能力，才进入插件来源、内置 WorkflowVersion 绑定和执行选择；后端创建、套用和执行接口必须再次校验启用状态。
- Agent 插件只声明受控原子操作，不注册 IIS、NGINX、RabbitMQ、Java 等产品 Handler。
- 应用资产保存插件绑定 ID、固定插件版本和唯一 `InputBindingsV1`；禁止把普通变量、连接、CredentialProfile 或 Artifact 输出映射拆成平行字段。
- 部署时控制面编译 `gcac.agent-plan/v1` 签名计划；Agent 不接受未签名、过期、目标不匹配或权限越界的计划。
- Shell 默认禁用。命令只能使用 `program + args`，文件只能操作 Manifest 权限声明覆盖的路径。

Agent 插件的运行协议和原子操作规则见 `docs/项目规范/20260722-Agent插件开发规范.md`。本节只定义工作流 DSL 与 Agent 插件的协议边界，不把 Agent 插件扩展成工作流 DSL 的 step 类型。
