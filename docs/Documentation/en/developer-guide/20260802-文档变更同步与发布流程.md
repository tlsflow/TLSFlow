# Documentation change and release process

The Chinese pages are authoritative. Translation pages are stateful mirrors. Code, Specs, project standards, and documentation must remain traceable in the same change; changing code without reviewing documentation, or changing a translation without reviewing its Chinese source, is not publishable.

## Change trigger matrix

| Change | Authoritative content to review | Evidence to add |
| --- | --- | --- |
| Plugin Manifest, Binding, Assignment, Runtime, or Promotion | The current unified plugin standard, plugin handbook, and plugin gap review | Spec, plugin code, focused tests, and maturity status |
| Device, Agent, agentless, Gateway, or execution location | Device guide, plugin target modes, and source index | Device/target code, Spec, discovery or execution tests; use `in_review` when external acceptance is missing |
| Workflow DTO, Schema, DSL, template directory, Step, variable, SecretRef, extract, or assert | The workflow template standard and workflow handbook | Schema, compiler, executor, canvas conversion, and tests |
| SSH, SFTP, SCP, CURL, recovery, or rollback | Executor/recovery page and certificate-deployment main chain | Executor tests, error boundaries, snapshot, and audit evidence |
| Certificate asset, Artifact, deployment input, plan, VERIFY, or rollback | Certificate, deployment, and certificate-deployment pages | Contract, Snapshot, plan, and execution tests |
| Internationalization or locale routing | Internationalization standard, developer page, and translation matrix | Application i18n resources, docs locale config, and checks |
| Theme variables or design system | Theme standard and developer theme page | Tokens, components, theme tests, or static checks |

When a change matches multiple rows, review every matching row.

## Synchronization order

1. Confirm current facts from active Specs, code, tests, standards, and `git status`.
2. Update the contract first when behavior, fields, states, or source directories change. Do not rewrite historical files as new facts.
3. Update the Chinese authoritative pages, source index, and status. Keep unsupported vendor or environment claims at `in_review` or `todo`.
4. Update the translation matrix. A changed Chinese source marks the translation `needs_sync`; restore `current` only after reviewing API paths, fields, states, error codes, permissions, and security limits.
5. Update navigation, locale mapping, links, and migration entries when pages move or change.
6. Remove real Secrets, tokens, private keys, passwords, production addresses, and unredacted logs from examples.
7. Run metadata, source, link, encoding, sensitive-content, and VitePress build checks. Run focused plugin or workflow tests when their code changed.
8. Record commands, commit IDs, known gaps, and recovery conditions in the Spec task or acceptance record.

## Status and history rules

- `implemented` requires current code, Spec, and verification evidence.
- `in_review` means implementation exists but external, protocol, translation, or manual evidence is incomplete.
- `todo` means the page or capability lacks sufficient facts.
- Use an absolute `lastVerified` date and update sources when facts change.
- Do not silently overwrite historical pages. Add a dated authoritative page or an explicit migration section, preserve a migration entry, and update the translation matrix.

## Release gates

Run from `docs/Documentation`:

```text
npm run docs:check
npm run docs:build
```

Workflow changes must also confirm that template sources are only `backend/src/modules/workflow-templates/builtin-workflows` and `data/workflows`. Do not add or restore a third sample directory.

## Gaps remain visible

User-plugin publisher cryptographic verification, dual-mode Promotion aggregation, execution-time `configFingerprint` comparison, real vendor deployment/rollback, Gateway, product version, execution-location acceptance, and complete Citrix insecure-TLS acceptance must remain explicitly `todo` or `in_review` until evidence exists.
