# Workflow DSL and template sources

## Protocol boundary

The only workflow protocol is `gcac.workflow/v1`, and the only `kind` is `CurlSshWorkflow`. The root object must contain:

```json
{
  "apiVersion": "gcac.workflow/v1",
  "kind": "CurlSshWorkflow",
  "metadata": {
    "name": "example-certificate-deploy",
    "version": "1.0.0"
  },
  "inputContract": {
    "apiVersion": "gcac.deployment-input/v1",
    "variables": {},
    "connections": {},
    "credentials": {},
    "artifacts": {}
  },
  "steps": []
}
```

`metadata.name` is the stable identifier. `metadata.displayName` is for presentation only. `metadata.version` uses SemVer; the database `WorkflowTemplateVersion.version` is an integer edit-history value and must not be mixed with it.

The Schema rejects unknown root fields, legacy top-level `variables` or `connections`, ordinary `credential` or `certificate` variable types, undeclared references, dangerous JSONata functions, and `foreach` nesting beyond three levels. Templates cannot carry plaintext passwords, tokens, private keys, or production credentials.

## Template sources

| Source | Purpose | Runtime rule |
| --- | --- | --- |
| `backend/src/modules/workflow-templates/builtin-workflows` | Built-in DSL resources shipped with the code | Git-tracked release resources; pages must not scan them into templates at runtime |
| `data/workflows` | User-imported or runtime-retained DSL files | Import is validated directly against the current Schema and Contract; historical formats are rejected or retired before publication and are not converted at runtime |

Do not add `docs/工作流样例`, `docs/workflows`, or another third DSL directory. File existence only proves that a resource exists; it does not prove that it is published, enabled, or selectable.

Workflow pages and APIs may select only enabled fixed-version `declarative` PluginVersions with registered Workflow capabilities. An `agent_plan` is an Agent v2 plan, not a Workflow source. An `isolated_process` capability is available only to an explicitly declared `plugin.action` step inside a normal DSL Workflow; it must not replace the Workflow executor or become a package-level dispatch path.

## Provenance and ownership

- `plugin_internal`: immutable internal WorkflowVersion generated from a PluginVersion; it is read-only to ordinary users and is selected through the published Capability binding.
- `user`: a user-maintained workflow that can be drafted, published, and disabled. It is submitted directly as DSL and is not silently upgraded from a PluginVersion.
- Historical `plugin_derived` and `legacy` records are handled only by the pre-release cleanup ledger; runtime does not read, convert, or use them as new-version sources.

## Publication and hashing

Before publication, validate the DSL, input Contract, Credential and Artifact slots, executors, stages, rollback branches, sensitive paths, and a preview or mock run. Normalize the content and calculate SHA-256. A content change creates a new immutable version; PluginVersion and WorkflowVersion are fixed at plan creation, and execution/retry never resolve legacy sources or `LATEST_PUBLISHED`.
