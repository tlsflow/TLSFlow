# 工作流 DSL 与模板来源

## 协议边界

当前唯一工作流协议是 `gcac.workflow/v1`，唯一 `kind` 是 `CurlSshWorkflow`。根对象必须包含：

```json
{
  "apiVersion": "gcac.workflow/v1",
  "kind": "CurlSshWorkflow",
  "metadata": {
    "name": "example-certificate-deploy",
    "version": "1.0.0"
  },
  "inputContract": {
    "apiVersion": "gcac.deployment-input/v1",
    "variables": {},
    "connections": {},
    "credentials": {},
    "artifacts": {}
  },
  "steps": []
}
```

`metadata.name` 是稳定标识，`metadata.displayName` 只用于展示。`metadata.version` 使用 SemVer；数据库中的 `WorkflowTemplateVersion.version` 是编辑历史整数，不能混用。

Schema 会拒绝未知根字段、旧的顶层 `variables`/`connections`、普通 `credential`/`certificate` 变量类型、未声明的引用、危险 JSONata 函数和超过三层的 `foreach` 嵌套。模板不能携带明文密码、Token、私钥或生产凭据。

## 模板来源

| 来源 | 作用 | 运行时规则 |
| --- | --- | --- |
| `backend/src/modules/workflow-templates/builtin-workflows` | 随代码发布的内置 DSL 资源 | 受 Git 跟踪，作为发布资源保留，不由页面运行时扫描创建模板 |
| `data/workflows` | 用户导入或运行期保留的 DSL 文件 | 不因升级删除或改写；导入前必须进入受控 PluginVersion 或显式迁移 |

禁止新增 `docs/工作流样例`、`docs/workflows` 或其他第三套 DSL 目录。文件存在只表示资源存在，不表示已经发布、启用或可选择。

工作流页面和 API 只能选择已启用且固定版本的 `declarative` PluginVersion，并且能力必须是标准 Workflow Capability。`agent_plan` 和 `isolated_process` 插件不能伪装成 Workflow；它们由宿主调度器分别进入 Agent v2 或 Plugin Runner 单路径。

## 来源与所有权

- `plugin_internal`：由 PluginVersion 生成的内部不可变 WorkflowVersion，只供插件内部执行，普通用户不能重命名、编辑、发布或停用。
- `user`：用户自行维护的工作流，可以创建草稿、发布、停用和显式套用插件版本。

历史 `plugin_derived`、`legacy` 记录只允许进入删除或作废审计；运行期不读取、不转换、不回退。新增接口和页面只能使用 `plugin_internal` 或 `user`，并以固定 PluginVersion、WorkflowVersion 和不可变资源摘要为准。

## 发布与哈希

工作流发布前必须依次通过：

1. DSL Schema 和变量引用校验。
2. 输入 Contract、Credential Slot 和 Artifact Slot 检查。
3. 执行器、阶段、回滚分支和敏感路径检查。
4. 预览或 Mock 试跑；真实试跑必须另有环境证据。
5. 内容规范化后计算 SHA-256。

同一内容不得因为来源展示变化重复生成版本。内容变化必须创建新的不可变版本，插件资源哈希不变时复用已发布 WorkflowVersion。运行期不得解析 `LATEST_PUBLISHED` 或旧来源；计划创建时就必须固定具体 PluginVersion/WorkflowVersion，执行和重试不得改变选择。

## 最小设计原则

工作流只描述业务步骤和声明式输入，不描述宿主数据库、Secret 存储、Agent ID 推断或厂商分派。需要厂商字段时，放入标准资产 `metadata` 或输入 Contract 的明确 Slot，不新增宿主专用字段。
