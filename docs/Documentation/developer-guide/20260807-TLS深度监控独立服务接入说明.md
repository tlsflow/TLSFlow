# TLS 深度监控独立服务接入说明

## 1. 这份文档解决什么问题

这份文档说明 GCAC `009.7` 里新增的 TLS 深度监控能力是如何落地的，包括独立服务边界、前端接入方式、结果结构、部署变量和当前实现边界。

目标很直接：

- 不把重 TLS 扫描塞进现有 `backend` 进程。
- 保留现有“监控告警”页面样式与主体不变。
- 在监控模块下新增独立的 TLS 深度监控子页，并让该子页只保留摘要和风险入口。
- 让排障人员在详情页看到完整 TLS 深度事实。

## 2. 当前实现总览

当前实现新增了一个独立目录：

```text
tls-inspector/
  src/
  test/
  Dockerfile
  README.md
```

它是一个独立 HTTP 服务，负责：

- 管理深度检测目标
- 定时触发 TLS 深度扫描
- 保存深度扫描快照
- 对外提供查询 API

现有 `backend/src/modules/monitors` 没有承载这些重扫描逻辑，轻量监控与深度监控仍然分开。

## 3. 运行边界

### 3.1 为什么单独做服务

TLS 深度监控不是简单的“探一下能不能通”，而是会做：

- 多协议握手探测
- 多套件协商探测
- 证书链提取
- 多信任视角认证路径分析
- 客户端画像兼容性模拟
- HTTPS 响应头和协议细节读取

这些操作天然更重，而且会拉长单目标处理时间。继续塞进主后端，只会让轻量监控和主业务 API 一起变慢。

### 3.2 当前进程边界

- 轻量监控：继续走 GCAC 现有 Monitors API
- 深度监控：走 `tls-inspector` 独立 API
- 前端 TLS 子页：同时读取两边摘要
- 前端详情页：只读取 `tls-inspector`

## 4. 首版实现技术路线

### 4.1 为什么没有直接上 Go

Spec 设计里预留了 Go 作为优先方向，但首版实现最终采用了：

- Node 原生 HTTP 服务
- `openssl` 子进程完成握手、协议和套件探测
- 文件型 JSON 存储保存目标与快照

原因很现实：

1. 仓库现有前端与控制面已经是 Node 生态，接入成本最低。
2. `openssl` 已经能稳定给出我们最关键的 TLS 协商事实。
3. 先把“独立服务 + 前端详情页 + 结构化结果”打通，比空谈未来 Go 重写有价值。

这不是说 Go 不行，而是首版先解决真实问题。

### 4.2 当前核心文件

- `tls-inspector/src/index.js`：HTTP API、调度器、目标管理
- `tls-inspector/src/scanner.js`：TLS 深度扫描执行器
- `tls-inspector/src/store.js`：文件存储
- `tls-inspector/src/catalog/client-profiles.js`：版本化客户端画像

## 5. API 与前端接线

### 5.1 独立服务 API

当前提供：

- `GET /healthz`
- `GET /api/v1/tls-inspector/targets`
- `POST /api/v1/tls-inspector/targets`
- `DELETE /api/v1/tls-inspector/targets/:id`
- `POST /api/v1/tls-inspector/targets/:id/inspect`
- `GET /api/v1/tls-inspector/targets/:id/latest`
- `GET /api/v1/tls-inspector/targets/:id/snapshots`
- `GET /api/v1/tls-inspector/snapshots/:id`

### 5.2 前端 API 模块

前端新增：

- `web/src/api/modules/tls-inspector.api.ts`

默认读取：

- `VITE_TLS_INSPECTOR_BASE_URL`

默认值是：

- `/tls-inspector`

这意味着推荐由网关或反向代理把 `/tls-inspector/*` 转发到独立服务。

## 6. 页面改造结果

### 6.1 监控入口拆分

文件：

- `web/src/views/monitoring/MonitorsView.vue`
- `web/src/views/monitoring/MonitorTlsOverviewView.vue`

当前入口拆分为两部分：

- `MonitorsView.vue`：继续承载既有“监控告警”列表页，样式与主体保持不变
- `MonitorTlsOverviewView.vue`：作为新的监控子页，只展示 TLS 深度摘要与风险入口

其中 TLS 子页只展示：

- 轻量探测状态
- 最近探测时间和延时
- TLS 深度风险摘要
- 风险事件入口
- `TLS 深度详情` 入口

不再在列表页展开：

- 证书链详情
- 全部协议矩阵
- 套件列表
- 兼容性模拟大表

对应路由为：

- `/monitors`：监控告警
- `/monitors/tls`：TLS 深度监控
- `/monitors/tls/:id`：TLS 深度详情

### 6.2 详情页

文件：

- `web/src/views/monitoring/MonitorTlsDetailView.vue`

当前详情页包含五个分区：

1. 概览
2. 证书认证路径
3. 协议与套件
4. 兼容性模拟
5. 协议细节

并支持：

- 自动初始化独立检测目标
- 触发重新检测
- 查看最近快照历史

## 7. 当前结果结构

每个深度快照至少包含：

- `certificate`
- `trustPaths`
- `protocols`
- `cipherSuites`
- `simulations`
- `protocolDetails`
- `riskSummary`

其中 `riskSummary` 是概览页真正依赖的轻量摘要，当前重点字段包括：

- `legacyProtocolEnabled`
- `weakCipherDetected`
- `tls13Supported`
- `trustPathIssueCount`
- `simulationFailedCount`
- `hstsTooShort`

## 8. Handshake Simulation 当前口径

GCAC 当前没有复刻 SSL Labs 私有评分器。

当前兼容性模拟使用的是：

- 版本化客户端画像
- 服务端已探测到的协议/套件事实
- 规则匹配和失败原因归纳

每条结果都会带：

- `profileId`
- `profileVersion`
- `status`
- `failureReason`
- `boundaryNote`

所以它是“可解释的近似模拟”，不是“真实终端实测”。

## 9. 多信任视角当前口径

当前五类视角分别是：

- `Mozilla`
- `Apple`
- `Android`
- `Java`
- `Windows`

当前支持情况：

- `Mozilla`：使用 Node/OpenSSL 自带可信根快照近似分析
- `Java`：使用 `keytool -list -cacerts -rfc` 导出的本机可信根快照
- `Windows`：在 Windows 运行环境下读取 `LocalMachine\\Root`
- `Apple`：当前明确返回 `unsupported`
- `Android`：当前明确返回 `unsupported`

这里最重要的不是“全都支持”，而是结果必须诚实。

## 10. 环境变量与部署

独立服务环境变量：

| 变量 | 默认值 | 说明 |
| --- | --- | --- |
| `TLS_INSPECTOR_HOST` | `0.0.0.0` | 监听地址 |

## 12. 已知边界

当前仍有明确边界：

1. 旧协议和弱套件探测依赖运行环境里的 `openssl`。
2. `Apple` 和 `Android` 信任视角还没有本地根证书快照。
3. 兼容性模拟仍然是规则推导，不是浏览器或移动系统实测。
4. 当前存储是文件型 JSON，适合首版独立部署，不适合无上限扩容。

这些边界都已经结构化暴露到结果里，没有藏起来。
