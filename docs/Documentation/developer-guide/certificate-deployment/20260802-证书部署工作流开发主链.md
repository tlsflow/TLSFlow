# 证书部署工作流开发主链

## 主链

证书部署不是一个“调用插件”的动作，而是一条必须可追踪的编排链：

```mermaid
flowchart LR
  A["证书资产与版本"] --> B["Artifact Contract"]
  B --> C["Asset Context + Binding"]
  C --> D["统一输入解析"]
  D --> E["preflight 预检"]
  E --> F["固定 Snapshot 与哈希"]
  F --> G["Plan 提交/审批"]
  G --> H["Dry-run"]
  H --> I["execute 执行"]
  I --> J["VERIFY 验证"]
  J --> K["结果同步与审计"]
  I --> L["失败"]
  L --> M["声明式 rollback"]
  M --> J
```

## 证书版本和制品

开发者不能把证书 PEM、私钥或 PFX 密码直接写入 Workflow DSL。应声明 Artifact Slot 和输出角色，例如：

- 叶子证书 PEM。
- 私钥 PEM。
- 有序中间链或 fullchain。
- PFX/PKCS#12 包及其密码。
- 目标证书 SHA-256 指纹。

部署计划必须固定证书版本和 `certificateFormatId`。`EXPLICIT` 使用用户明确选择的版本；`LATEST_AUTO` 只能在创建计划时基于用户选择的证书资产种子版本解析并固定，执行和重试不得重新选择“当前最新”。

## 目标和执行来源

证书部署工作流必须尊重四种目标模式：

| 模式 | 工作流关系 |
| --- | --- |
| 无 Agent `DeviceAsset` | 使用标准目标事实和无代理连接，不虚构 Agent PluginBinding |
| `ManagedTarget + Plugin` | 由当前 `Manifest -> PluginVersion -> Capability` 链解析出 CapabilityAssignment、PluginBinding 和固定 PluginVersion，提供原子能力 |
| `ManagedTarget + Workflow Override` | 由 WorkflowExecutionBinding 提供用户明确选择的工作流 |
| `Standalone + Workflow` | 由 ApplicationAsset 和 WorkflowExecutionBinding 提供工作流，不创建新的 Standalone PluginBinding |

一个 DeploymentPlanTarget 必须恰好有一种 `ResolvedExecutionSource`。插件和工作流不能混合传参，执行位置只说明在哪里执行，不决定使用哪个实现。

插件绑定只有一条来源链：当前 Manifest 物化 PluginVersion，PluginVersion 声明 Capability，再由目标上下文形成 CapabilityAssignment/PluginBinding。Manifest 缺失、停用、哈希不一致或未声明目标能力时必须失败关闭；不得手工升级已有绑定，不得使用历史来源、Alias 或 fallback 创建新绑定。

## 预检和快照

预检阶段需要同时检查：

1. 目标、租户、权限、Capability 和执行位置。
2. 证书版本、格式、Artifact Contract 和输出槽位。
3. Asset Context、Binding 覆盖、Credential 版本和连接字段。
4. 工作流/插件版本、输入 Contract、`resolvedSha256` 和资源哈希。
5. 计划策略、Gateway、并发锁、回滚和验证条件。

预检通过后，宿主保存脱敏 `DeploymentInputSnapshotV1` 和运行时快照引用。快照只保留结构、来源、版本、摘要和敏感路径；执行器通过 Grant 取得短时运行材料。

## 执行、验证和回滚

- Dry-run 只做预检和执行器可行性检查，不应推进正式资产状态。
- execute 使用固定 Snapshot、计划版本和执行身份，不能重新合并当前输入。
- `prepare` 负责发现和输入确认，`backup` 负责创建可回滚快照，`install` 写入证书，`refresh` 触发服务刷新，`verify` 读取目标服务或 TLS 结果。
- VERIFY 必须检查目标服务真实返回的证书指纹；仅凭本地上传成功或插件返回“成功”不能判定部署成功。
- 失败时只执行 WorkflowVersion 声明的 rollback 分支；回滚失败必须同时记录原始失败和回滚失败，并进入人工处理。
- 结果同步只有在正式验证成功或回滚成功后才能更新当前证书绑定和应用资产状态。

## 插件内部和用户派生工作流

`declarative` 插件发布时，宿主创建只读 `plugin_internal` WorkflowVersion；用户复制时创建带完整 Provenance 的用户工作流。插件升级不会自动或人工改写用户工作流绑定；历史插件对象和来源只能删除或作废并保留审计，新绑定只能沿当前 Manifest -> PluginVersion -> Capability 链创建，运行期不回查、不读取、不转换旧版本。

`agent_plan` 插件只能生成签名的 Agent v2 类型化计划；`isolated_process` 插件只能通过同 Docker 独立 Plugin Runner 和 IPC v1 执行；两者都不能转换成 Workflow Step。Runner、Policy Authority、真实厂商部署/回滚、Gateway 和产品版本外部验收仍按能力单独记录为 `TODO` 或 `IN_REVIEW`。

## 审计和禁止事项

每个计划、快照、Grant、Step、验证和回滚动作都必须保留租户、Actor、版本、幂等键、时间、结果和脱敏错误摘要。禁止：

- 在 DSL、计划 JSON、普通变量或日志中写入私钥、PFX 密码和 Token。
- 运行时回查 `LATEST_PUBLISHED` 或当前资产覆盖，改变已审批计划。
- 用 `allowInsecure: true` 规避 TLS 门禁。
- 用厂商字符串、产品名或 Agent 是否存在选择执行器。
- 用删除历史运行记录的方式掩盖失败。
- 使用 Alias、fallback、Shadow、灰度、双执行或双写维持历史路径。
